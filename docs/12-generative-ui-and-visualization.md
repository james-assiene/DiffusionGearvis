# Generative UI, the denoising view, and pixel-first perception

**Status:** decided 2026-09-12. Three additions to the design from James's requests: the shown channel becomes a *generated UI* rather than a rendered document; a widget shows the diffusion process itself, ending in the model's answer; and perception is pixel-first, with every text-assist behind a checkbox. The full framework survey (nine candidates, schemas inspected, example validated) is saved in the project as `claude/generative-ui-framework-survey-2026-09.md`; this document records the decisions and what they change.

## 1. Generative UI: A2UI v0.9.1 with an `edu` catalog

**Choice.** Google's A2UI (Apache-2.0, `a2ui-project/a2ui`, v0.9.1 current, v1.0 at release candidate, announced Dec 2025 with CopilotKit/Flutter/Gemini Enterprise and adopted since by Oracle's Agent Spec, Lynx, Svelte/Vue/Swift renderers) is the only mainstream generative-UI system that meets all four of our constraints at once. It has a **published JSON Schema** for the whole wire format (`catalog.json` 46 KB, `common_types.json` 9 KB, `server_to_client.json` 6 KB, draft 2020-12). Its IR is a **flat adjacency list** — every component is `{ "id", "component", …props }` and refers to children by id — so the schema is non-recursive, which is what makes it approximable by a regular language for constrained decoding (§1.4) and what keeps a 26B model's output shallow. It has a **Python SDK** (`a2ui-core` for schema and topology validation; `a2ui-agent-sdk` with a `payload_fixer` for smart quotes and trailing commas, prompt generators and experimental compact formats). And it has a **plain-page web renderer**: `@a2ui/lit` (Lit 3 web components, CSS-variable theming, no Tailwind/React/Material dependency), which drops into the Chromium `--app` HUD as-is. The event model is exactly what a tutor needs: `Button.action = {event: {name, context}}`, and with `sendDataModel: true` every click carries the surface's whole data model (all the quiz answers) back over the socket, so the agent never tracks UI state.

**What it lacks, and the `edu` catalog that fixes it.** The basic catalog has 18 components (Text with simple Markdown, Image, Icon, Video, AudioPlayer, Row, Column, List, Card, Tabs, Modal, Divider, Button, TextField, CheckBox, ChoicePicker, Slider, DateTimeInput) and no table, chart, maths, progress, timer or annotation. Catalogs are first-class and are themselves JSON Schema files of the same shape, so we add one custom catalog of eight non-recursive components, each with fixed keys and scalar or `{path}` values: `Math` (LaTeX → KaTeX), `Markdown` (GFM + inline maths), `Table` (`columns`, `rows`, `highlightRow`), `Chart` (`kind`, `series`; rendered by GPT-Vis or Chart.js), `Timer`/`Progress` (`seconds`, emits `timer_done`), `Flashcard` (`front`, `back`, local flip, emits `graded`), `AnnotatedImage` (`url`, `marks[{x, y, label}]`), `Steps` (children revealed one at a time by a renderer-side function — the hint ladder as a widget). MCQ (`ChoicePicker mutuallyExclusive`), checklists, forms, comparison layouts and buttons are already covered. Pin v0.9.1 and version the catalog file: the 0.8 → 0.9 renames (`distribution → justify`, `usageHint → variant`, `userAction → action`) show the spec still moves.

**Alternatives and why not.** Vercel `json-render` (Apache-2.0, flat map + JSON Patch, shadcn catalog with Table/Tabs/Progress/charts) is the fallback if we want finished built-ins fast, but it is React 19 + Tailwind 4 + Zod 4, TypeScript-only, and its `catalog.jsonSchema()` emits untyped props (we would derive a strict schema from the Zod definitions ourselves). Thesys OpenUI Lang has the best token economy (a line DSL, ~4.8k tokens where JSON needs ~10k) but no grammar, React-only, and a telemetry postinstall. Microsoft Adaptive Cards is mature and vanilla-JS but recursive (100 KB schema, depth 9) and looks like Teams. `assistant-ui`'s generative UI is 0.0.x with a deliberately loose schema. MCP Apps / MCP-UI / OpenAI Apps SDK render arbitrary HTML in sandboxed iframes — nothing to constrain, safety by sandbox rather than catalog — kept only as an escape hatch for one prebuilt widget. Gradio/Streamlit/Mesop/NiceGUI define UI in code, not in a document the model emits.

### 1.1 How DiffusionGemma produces it

The two output channels (D12) become: spoken text, and an A2UI `updateComponents` payload between `<a2ui>…</a2ui>` sentinels (the SDK's parser convention), both in the same generation. A single MCQ or a small table is 300–500 tokens (two canvases, ~0.8 s); a five-question quiz plus a flashcard deck is ~1.3k tokens (five to six canvases, ~2 s at 700 tok/s) — visible, and the whole surface lands at once. The Conductor runs the validate-and-repair pipeline on commit (James's suggestion to lean on JSON-repair libraries, adopted 2026-09-12): extract the payload between the sentinels (tolerating a missing closing sentinel at a canvas boundary) → `json_repair.loads(payload, schema=UpdateComponents, schema_repair_mode="salvage")` (mangiucugna's `json_repair`, MIT, v0.39.x: missing quotes/commas/brackets, unquoted keys, truncated structures, Python literals, comments, prose and fences; its beta schema-guided mode coerces or drops toward the schema, which is what A2UI's `unevaluatedProperties: false` otherwise rejects outright; every change it makes is logged for X11) → JSON Schema (Draft 2020-12, bundled schemas, `referencing` registry) → topology (one `root`, no dangling ids) → **per-component resample**: because A2UI is a flat list of independent objects, valid components are kept and only the failing ones are regenerated ("regenerate `q3_c`, `deck_nav`"), not the whole surface. A2UI's own `payload_fixer` (smart quotes, trailing commas) is subsumed. `fast-json-repair` (Rust port, 10–30× faster, no streaming, no schema mode) is not needed at ≤ 10 KB payloads against a 400 ms canvas; it is the swap if profiling ever puts the fixer on the hot path. **Progressive rendering:** with `stream_stable=True` (or Pydantic's `from_json(allow_partial=True)`), after *each* canvas commit the gate parses the prefix, extracts the component objects that are already complete, validates them individually and pushes them as incremental `updateComponents` — A2UI is incremental by design — so a five-canvas quiz builds up at ~0.4 s intervals instead of appearing at 2 s (X11 checks how `@a2ui/lit` treats a child id referenced before its component arrives). Repair rate, salvage rate, resample rate and the error taxonomy (expected: balanced within a canvas thanks to bidirectional attention, truncation at canvas boundaries) are the Q11 metrics. Valid surfaces are pushed to the HUD as `astra.ui.surface`; user actions come back as `astra.ui.action` and become a user turn (`[ui] check_quiz answers=…`), to which the model replies with a small `updateDataModel` canvas (feedback, score). Interaction with the tutoring state: the `TutorState` records the surface id and the answers, so the hint ladder can address "question 3" without re-reading the UI.

**Delta (2026-10-16, T-0108):** the expectation "balanced within a canvas thanks to bidirectional attention" is retired. Re-gating the stored T-0103 run (6720e56, Q12 positives, a fresh gate per trial, CPU) found structural damage inside canvases: of 376 A0 calls, 126 failed and only 103 of 153 turns ended on a valid last call. The damage is a duplicated opener `{"{"id":`, a missing separator `"From:" "{"id"`, a wrong closer and a stray `"` after a closer. The gate now runs a structural stage, `local_astra/ui/bracket_repair.py`, when strict parsing fails and before json_repair. It is one linear, string-aware pass that only inserts or deletes `{ } [ ] , "` outside strings, and grounding stays against the original canvas. On the same data, 149/153 last calls are now OK (C3: 80 → 114/128).

**Delta (2026-10-17, T-0108b):** the gate gains a component stage, `local_astra/ui/component_repair.py`. It runs on both fixer paths (after the strict parse, and before salvage on the unguided path) and repairs a schema-invalid component only when the model wrote everything the component needs in the wrong shape: BC (a Button's single child under `children`), LI (inline children lifted), TF (`placeholder`/`text` → `label`), DT (`value: ""`), CPO (string options), CPV (`value` → list) and RB (a text-only Button). It is all-or-nothing per component, and valid components stay identical. The rule "a repair never invents content" is re-scoped (H-T108b (b), (d)): every string value is the model's own; added keys are only catalog properties of that kind; added non-strings are only `""` and `[]`; no id is created. The one exception is the reserved namespace RB uses: the Text id `__gate_<button id>_label` and the event `__gate.clicked`, whose click sends the label back to the model (cards are illustrations, not applications). The stage also fixes a stale-stub defect: a re-started fence cut mid-component no longer overwrites an accepted component's as-written copy. On the stored Q12 positives (CPU re-score, fresh gate per trial), complete cards went from 54 → 132/160 (e6c3a81 A0), 64 → 132 (K1), 66 → 108 (K2), 63 → 136 (6720e56 A0) and 32 → 101 (C3).

**Delta (2026-10-20, T-0127):** the component stage gains CC, a Card written with `children`. With one distinct id, `child` becomes that id. With several (H-T127-1), `child` becomes `__gate_<card id>_body`, and a gate-made Column with that id and the ids in first-occurrence order follows the Card, which is the wrapping the catalog prescribes. Inline children are lifted LI-style first. An id-less inline object, the Card's own id, a reserved id, or a cycle refuses the repair. The reserved namespace is extended by exactly that id and, on that one Column, the kind `Column`; both are exempt from grounding for that Card only. Independently of repair, the gate no longer calls an incomplete card clean. When a surface is emitted, `problems` names every component written on the canvas (or dropped by salvage) that the gate did not emit, with its kind, and every reference to an id never defined ("reference pruned", which is not a loss). `GateResult` gains `lost` and `complete`: a surface was emitted, the accumulated tree holds `root`, `root` reaches every component in it, and nothing was lost. `ok` keeps its meaning (safe to render). The turn line gains `ui_complete_final`, and an incomplete final surface is still re-sent but writes one session-log note, ids only. List `items` and out-of-enum Text variants are not repaired (H-T127-2/3 declined), so such a card is reported incomplete. `scripts/replay_ui_gate.py <session.jsonl>` replays a session's `ui` commits on CPU as the pre-desk check.

### 1.2 Interaction with pixel-first perception

None: the UI is an output. Pixel-first (§3) governs what the model *sees*; A2UI governs what it *shows*.

### 1.3 Token economy

Token count is canvas count is latency. Three levers, in order: prune the prompt's schema to the 15–20 components we use and give two few-shot surfaces; prefer data-bound templates (`List.children` as a `{componentId, path}` template plus an `updateDataModel`) over repeated components; evaluate A2UI's experimental compact "Express" format (compiled to JSON by the host) once its parser is stable (X12).

### 1.4 Constrained decoding, honestly

A2UI's catalog is finite-automaton friendly in shape — fixed keys, enums, strings, arrays of strings, small fixed-shape objects, with `event.context` restricted in our catalog to scalars or `{path}` — but a 20-component catalog with free-text string fields compiles to thousands of states, far beyond the ≤ 128-state live budget in `07`. So constrained decoding is *not* how UI validity is achieved in v1: validate-and-repair is. Where the decoder helps later is at the envelope level (the sentinels, the `component` enum per object, the `root` requirement) and, if `07` ships its plugin, as commit-time validation with re-denoise. The S³ "schema scaffolding" idea — pre-filling the invariant skeleton so the model fills slots — is worth one experiment on the diffusion sampler, because it is exactly the kind of structure the paper says converges in 2–3 steps.

## 2. The denoising view: showing the diffusion process, truthfully

**Data source.** vLLM does not expose intermediate canvases; the plugin from `07` does. Its first milestone is therefore *passive*: after delegating to the stock sampler step, it reads `states.canvas[slot]` (the current denoised canvas including still-random positions), `states.argmax_canvas[slot]`, `states.step[slot]` and, where accessible, the acceptance mask and per-position entropy, copies them non-blocking into a pinned host ring, and a publisher thread emits `astra.canvas.step` events at ≤ 30 Hz. Per event: `request_id`, `canvas_idx`, `step`, 256 token ids, 256-bit accepted mask, 256-bit stable mask, mean entropy, segment (`thought | answer | ui`). The HUD decodes ids with a vocabulary table shipped once at page load, so an event is ~1 KB. Commits are `astra.canvas.commit` with the text. Overhead target < 3 % of step time (B16). Before the plugin exists, the transformers path (`TextDiffusionStreamer.put_draft`) gives the same data for offline demos, and a *synthesised* animation from the final text (random tokens resolving over ~12 frames) is available as a clearly labelled "illustrative" fallback — never shown as the real trajectory.

**Widget.** A 16 × 16 grid of token tiles per canvas. Tiles show the current token text; colour encodes state: dim and flickering while a position is still noise (uniform-state diffusion refills it with random tokens every step — that flicker *is* the model), lit when accepted this step, solid when stable across steps, and a brief flash when a previously accepted token is revised (the signature of renoising that masked models cannot show). Around it: a step ring (k of 48), a mean-entropy sparkline that drops as the canvas converges, and tokens-committed-per-second. On commit the tiles settle and morph into the flowing text of the answer pane; thought canvases render dimmed under a "thinking" label and are never spoken or stored; tier-B thinks show a filmstrip of canvases; UI canvases morph into the A2UI surface. A reduced-motion toggle exists. Beyond the demo value, this is the debugging view for the two failure modes the report names — stuttering loops ("the the the") and unclosed thoughts — both visible at a glance.

## 3. Pixel-first perception (revises D12a)

James's requirement: showcase raw visual understanding; DOM, OCR and text layers are optional and behind checkboxes. So the default input is pixels only — the screenshot(s) at the maximum visual-token budget (1120 per image) and camera frames — and every text assist is an explicit, visible toggle in the HUD: *Assist: page text* (DOM selection/visible text from the browser-tab source), *Assist: PDF text layer*, *Assist: spreadsheet cells*, *Assist: accessibility tree* (AT-SPI2). All off by default; a badge shows which are on so a recording is honest about what the model saw. The model's weakest published number (OmniDocBench 0.319) is then a risk we carry deliberately, mitigated only by pixel means: maximum visual tokens for documents; **focus crops** — the whole screen plus a high-resolution crop of the active window or the region around the pointer, sent as two images; a model-requested **zoom** (a normalised bounding box the model asks for, served as a third crop) if Gemma 4's grounding proves reliable (X13); and the read-back confirmation for handwriting, which is itself pixel-only. The desk-work eval (Q9) runs with assists on and off so the cost of pixel-first is a number, and the demo runs with them off.

## 4. Changes to other documents

Design: D12 (two channels → spoken + A2UI surface), D12a (text-first → pixel-first with optional assists), new D15 (denoising view). Architecture: the HUD renders A2UI via `@a2ui/lit` plus the `edu` catalog; the plugin's first milestone is the passive canvas tap; new events `astra.ui.surface`, `astra.ui.action`, `astra.canvas.step`, `astra.canvas.commit`, `astra.assist.toggle`.
