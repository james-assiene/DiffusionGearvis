# Literature review — building software with multiple AI coding agents

**Purpose:** ground the Claude Code setup for local_astra in what Anthropic, Andrew Ng and credible practitioners have actually published, rather than folklore. Prepared 2026-09-11. Quotes are verbatim from the cited pages.

## 1. Why a single agent that writes everything fails

The failure mode James hit — one long session producing a large volume of buggy code — is the one every serious source describes, and the explanations converge on three mechanisms.

The first is context. Anthropic's maintained best-practices doc opens with the governing constraint: "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills." Their context-engineering post names the effect "context rot" and recommends finding "the smallest possible set of high-signal tokens". Thariq Shihipar (Claude Code team, Apr 2026) reports that even with a 1M window, quality degrades around 300–400k tokens and advises: "When you start a new task, you should also start a new session."

The second is self-grading. Anthropic's harness-design post (Mar 2026) is blunt: "when asked to evaluate work they've produced, agents tend to respond by confidently praising the work — even when, to a human observer, the quality is obviously mediocre." The academic result matches: a 2024 study of self-verification found "ChatGPT often erroneously predicts its generated incorrect code as correct" (arXiv 2405.12641). The best-practices doc draws the design conclusion: a verification subagent "has a fresh model try to refute the result, so the agent doing the work isn't the one grading it."

The third is scope. The long-running-agents harness post found "the agent's tendency to do too much at once" and fixed it by forcing one feature per session against a feature list; Steve Yegge's warning is the same in plainer words: "If you give one a task that's too big … it will hurl itself at the problem and get almost nowhere." GitHub's Copilot coding-agent guidance says to avoid "complex and broadly scoped tasks" and to supply "complete acceptance criteria".

## 2. Anthropic's guidance

The best-practices doc recommends an Explore → Plan → Implement → Commit rhythm using plan mode, with the caveat "If you could describe the diff in one sentence, skip the plan." It recommends writer/reviewer separation in two forms: "A fresh context improves code review since Claude won't be biased toward code it just wrote", and "have one Claude write tests, then another write code to pass them." The adversarial reviewer "sees only the diff and the criteria you give it, not the reasoning that produced the change", with a calibration warning worth keeping: "A reviewer prompted to find gaps will usually report some, even when the work is sound … Tell the reviewer to flag only gaps that affect correctness." Verification is the centrepiece: "Give Claude a check it can run: tests, a build, a screenshot to compare", "Have Claude show evidence rather than asserting success", and "If you can't verify it, don't ship it."

On CLAUDE.md the guidance is to keep it small: "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" The memory doc gives a number — "target under 200 lines per CLAUDE.md file" — and offers `.claude/rules/*.md` with `paths:` globs for module-scoped rules. Hooks are the enforcement layer — the best-practices page puts it as "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens", and the hooks reference adds that exit code 2 is a blocking error that "even a JSON `permissionDecision` of \"allow\" can't override". Skills load on demand, which is the progressive-disclosure mechanism for anything that would otherwise bloat CLAUDE.md.

Subagents (`.claude/agents/*.md`, with `tools`, `disallowedTools`, `model`, `permissionMode`, `memory`, `maxTurns`, `isolation: worktree`, and per-agent `hooks`) start "with a fresh, isolated context" that "does NOT include your conversation history" — which is exactly the property a reviewer needs. Three documented details shaped our setup: settings-level hooks also run inside subagents and receive `agent_type`; `$CLAUDE_PROJECT_DIR` stays at the main checkout for worktree-isolated subagents while the hook input's `cwd` follows the worktree; and subagent worktrees branch from the default branch with tracked files only unless `worktree.baseRef` is set. Worktrees (`claude --worktree name`) give each session its own checkout and Claude "blocks an Edit, Write, or NotebookEdit that targets a path in the main checkout." The experimental agent-teams feature (lead plus teammates with a shared task list) comes with its own caution: "Agent teams add coordination overhead and use significantly more tokens than a single session … For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective", and "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files."

The multi-agent research-system post supplies the cost number everyone quotes: "multi-agent systems use about 15× more tokens than chats", and the domain caveat: "most coding tasks involve fewer truly parallelizable tasks than research." The long-running harness post contributes the pattern of an initializer session that writes a progress file and a feature list, a coding session that picks one failing feature per run, and the rule "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." The evals post says to start with "20–50 simple tasks drawn from real failures" and to read transcripts, because "the transcript tells you whether the agent made a genuine mistake or whether your graders rejected a valid solution." Boris Cherny's tips add practical details: plan first, then have "another Claude review as a 'staff engineer'"; keep a team CLAUDE.md of Claude's common mistakes; PostToolUse hooks for formatting; Stop hooks for background verification; and the claim that feedback loops multiply "result quality 2–3×".

## 3. Andrew Ng

Ng's agentic design patterns (2024) are reflection, tool use, planning and multi-agent collaboration, and he ranks them by reliability: reflection and tool use are dependable, while "I find the output quality of multi-agent collaboration hard to predict, especially when allowing agents to interact freely." His 2025–2026 letters shift the emphasis to specs and evals. "Make All Your Tokens Count" (Jul 2026): "AI tokens are cheap; human tokens are gold", and "Coming up with the spec, the evals, or test set is one of the hardest tasks … and a key place to inject human knowledge." His prescription when a defect is found is the one we adopt verbatim: "tell the agent not only to fix it but also to update the spec (and perhaps the test plan), so the agent's stopping criteria in the future require checking that this problem does not occur again." "Three Key Loops" (Jun 2026) describes the agentic coding loop as "given a product specification and optionally a set of evals … write code, test its work, and keep iterating", nested inside a developer feedback loop and an external feedback loop. The Skills Map series (Aug–Sep 2026) repeats that "developers who deeply understand how software works vastly outperform those who vibe code without understanding", puts spec-writing ("requirements, technical design, and architecture") before building, and warns that "social media often gives oversimplified descriptions of how to use coding agents", especially long autonomous runs.

## 4. Other practitioners and evidence

Simon Willison: "Code that started from your own specification is a lot less effort to review", and "I can only focus on reviewing and landing one significant change at a time." Addy Osmani: "Delegate the tasks, not the judgment"; commit after each small task; worktrees; hierarchical leads so "the lead only talks to two agents, keeping its context clean"; "The bottleneck is no longer generation. It's verification." His reviewer-diversity data point is striking: of 617 locations flagged by four AI reviewers, "93.4% were caught by exactly one of the four tools", which argues for more than one reviewer on high-blast-radius changes. Harper Reed's loop is spec (one question at a time) → plan → todo → small TDD chunks. Kent Beck: "In augmented coding you care about the code, its complexity, the tests, & their coverage", and the red flag is "any indication that the genie was cheating, for example by disabling or deleting tests." Armin Ronacher: tools must be fast, "Crashes are tolerable; hangs are problematic", log to files so agents can self-diagnose, and manage shared state so several instances can run. Mitchell Hashimoto gives agents an end goal "but using this shape" and notes they "struggle with architectural decisions". Geoffrey Huntley's "Ralph loop" — a fresh context per iteration, one item per loop, reading the plan and specs from disk — is the minimalist version of the harness pattern.

Birgitta Böckeler (Thoughtworks/martinfowler.com) is the most useful sceptic. Her harness memo notes that OpenAI's internal harness relies on "deterministic custom linters" and "enforced boundaries". Her Aug 2026 TDD-in-the-agent-loop study found "no clearly discernable difference based on TDD workflow versus no TDD workflow", observed agents that "skip confirming the red step", and concluded she had "stopped telling my coding agents to write tests first" in favour of monitoring outcomes with mutation testing and static analysis.

On productivity evidence, METR's randomized trial (Jul 2025, 16 experienced open-source developers, 246 issues) found developers were 19% slower with AI while believing they were 20% faster. METR's Feb 2026 update showed −18% for the original cohort and −4% for new recruits, while noting that selection effects (heavy adopters declining to participate) likely bias the estimate downward, so the figures are a lower bound on the true effect. The practical reading is that throughput claims are unreliable in both directions and the setup should optimise for correctness first.

## 5. Consolidated principles

1. Spec before code, plan mode before edits (Anthropic; Ng; Reed; Osmani; Codex "Done when").
2. Small tasks with explicit acceptance criteria, one per session or iteration (Anthropic harness; Huntley; Yegge; GitHub).
3. The agent must have a runnable check and must show evidence (Anthropic; Ng; Cherny).
4. Writer and reviewer are different agents with fresh context; self-grading is unreliable (Anthropic ×3; AgentCoder; SWE-Gym; Osmani).
5. Context hygiene: CLAUDE.md under 200 lines, skills for on-demand knowledge, subagents to absorb exploration, new session per task (Anthropic docs; Thariq; Böckeler).
6. Deterministic guardrails beat prompt pleading: hooks, linters, type checkers, CI (Anthropic; Böckeler; Cherny).
7. Isolate parallel work: worktrees, one task per branch, disjoint file ownership (Anthropic; Osmani; Ronacher).
8. Externalise state: progress file, feature/task list, commits as save points (Anthropic; Huntley; Osmani).
9. Evals from real failures; read transcripts; every escaped bug becomes a test, an eval case and — if systemic — a rule or hook (Anthropic; Ng).
10. Human review scaled to blast radius; never let an agent approve its own PR (Willison; Osmani; Ng; Anthropic Code Review).
11. Simplest architecture that works; add agents only for parallel or adversarial work (Anthropic; Ng).
12. Never: mega-prompts, editing tests to pass, unbounded autonomy, stacking corrections in a polluted context, treating one reviewer's approval as proof.

## 6. Where the sources disagree

Tests-first as ceremony versus tests as protected artefacts: Beck and Anthropic endorse TDD; Böckeler found the ordering did not matter and agents fake the red step. Our reconciliation: tests are written by a *different agent* from the implementer, protected by a hook, and required to be run with output shown; the ordering is enforced by workflow (test-author runs first) rather than by asking the implementer to be disciplined. Multi-agent cost: Anthropic's 15× and "few parallel tasks in coding" versus Osmani's orchestras and Yegge's "Gas Town" (which he calls "expensive as hell" and where "some work gets lost"). Our reconciliation: parallelism is by worktree and disjoint ownership, capped at two or three implementers, and multi-agent is used mainly where it is clearly justified — review and verification with fresh context. Review depth: Willison no longer reviews everything, Hashimoto reads every line; we scale by blast radius, with the Conductor's turn machine and anything touching audio/GPU services counted as high.

## 7. What this means for the local_astra repository

CLAUDE.md under 100 lines carrying only what an agent cannot derive: commands, the non-negotiable rules, pointers to the docs, and the role protocol. Roles as `.claude/agents/`: `planner` (read-only, produces a task plan with acceptance criteria and files touched), `test-author` (may edit `tests/` only), `implementer` (worktree-isolated, may not edit `tests/`), `reviewer` (read-only, sees diff + acceptance criteria, reports only correctness gaps), `verifier` (runs the suites, refutes claims), `explorer` (read-only research), `bench-runner` (GPU box only). Hooks: formatter and type-checker on edit; deny edits to `tests/` from the implementer role and to `src/` from the test-author; block destructive git; Stop hook that runs the fast suite; SubagentStop that demands test output in the report. Skills for `/spec`, `/plan`, `/implement`, `/review`, `/verify`, `/triage`. Worktree per task. `PROGRESS.md` and `docs/tasks/` as external state. PR flow with mandatory reviewer and verifier reports and a human merge. These are implemented in `CLAUDE.md`, `.claude/`, and `docs/agent-workflow.md`.
