# Constrained decoding for DiffusionGemma — what works, what doesn't, what to build

**Status:** 2026-09-11. Motivation from James: constrained decoding for tool calls and syntax, plus the idea of bounding spoken answers to a short length despite the 256-token canvas, with a possible speed benefit. His own implementation, `diffgemma-fa` (audited below from the zip at commit `bf14e76`, 2026-08-13), is a working JAX port of Dang & Ermon against the real 26B checkpoint — which changes this document from "what could work" to "what is measured to work, and what it takes to move it into our stack".

## 0. Audit of `diffgemma-fa`

**What it is.** A JAX implementation of arXiv 2607.07026 against `google-deepmind/gemma`'s `gemma/diffusion/` sampler and the Orbax checkpoint, inference-only; at bf14e76 the package is 9,561 lines (+2,577 in `scripts/`) with 27 test files / 19,450 lines (~600 test functions, 167 parametrised; the README's counts are stale). Layout: `compile/` (JSON Schema → regex via `outlines-core` → token DFA with a class-table representation, Valmari minimisation, a build gate), `infer/` (Blelloch tree forward–backward in log space, constrained marginals, eq. 8 token draw, a float64 numpy reference oracle), `model/` (a fork of `DiffusionSampler` with a widened state, constrained emission, and a budget-aware terminal factor `b_L = 1[d(s) ≤ R]`), `eval/` (BFCL, Countdown, Sudoku runners with Wilson/McNemar statistics). The method consumes only the `[B, 256, V]` logits at each denoising step and draws the *entire canvas jointly* from the constrained posterior, so the guarantee is exact by construction, not by rejection.

**What is measured to work.** On BFCL-Live `simple` (n = 130, one seed): schema validity 0.631 → **1.000**, constraint satisfaction 0 → 1.000, argument accuracy 0.639 → 0.663 and exact call 0.500 → 0.531 — the README correctly insists the accuracy claim is *parity, not gain* (restricted to commonly answered records the argument accuracy reverses; the exact-call McNemar p = 0.55). All 4,549 BFCL-Live schemas compile.

**What is *not* measured, corrected after verification.** An earlier draft of this document claimed constrained decoding was 25–27 % *faster* end to end. That was a misread of `RESULTS.md`: the −27.5 % arm (`eval_bfcl_live_simple_j0_map`) ran the *stock-whitespace* grammar with argument accuracy 0.327 — a broken grammar — while the accuracy-parity headline arm (`exp_e5_grammar130_map`) took 49.0 s/record against 37.4 s unconstrained, i.e. **+31 % slower**, on the same commit and box; whitespace-tolerant arms ranged from −8.6 % to +29 %. More importantly, every arm ran `--max-new-tokens 256` (one canvas) with `NoEarlyStop` (48 fixed steps), so the campaign contains **no measurement about steps per canvas** — the only lever that matters for a one-canvas spoken answer — and the "deliberate stop token → shorter generations" mechanism could not have operated. The repo's own `RESULTS.md` sentence to that effect is unsupported by its data. The speed question is therefore open, not answered; §4 and the experiment in §5 are how it gets answered.

**What is measured *not* to work, and matters for us.**
- Per-position masking is wrong for non-product constraints (SPEC §2.8, the paper's `"1."`/`".1"` → `".."` example); the repo's `mask` variant was slower (+18.7 %) and, on BFCL, produced schema-valid output only 30 % of the time with zero constraint satisfaction (the Sudoku collapse is not evidence about masking — every constrained variant collapsed there). A plain `TokenSetMask` is therefore not a substitute for the automaton path; it remains valid only for product-shaped constraints (forbidden token classes, a pad-only tail).
- The tree's cost is a function of automaton size: 0.5 ms per step at |S| = 64, 2.2 ms at 128, 18.1 ms at 256, 173 ms at 512 (float64 sum-product tree only, L = 256; the MAP tree was never benchmarked and the headline arm's per-step cost was dominated by a dense `[C, L, V]` class-max and an fp64 softmax that need redesigning). The repo measured these against a 0.21 s JAX model forward, where they look free. **Against vLLM's ~15–25 ms step on the 5090 they are not free**: |S| = 64 is ~3 %, 128 is ~10 %, 256 is ~100 %. Live-path automata must stay ≤ 128 states. Sizes from the compiler's construction: a 3-key JSON schema is 59 states without the 11-state channel header (~72 with it, bucket 128); a Gemma-4 tool call with 3 tools × 2 args ≈ 70–85 states, 5 × 4 ≈ 200–250 (too expensive live; needs key-order fixing or a two-stage grammar); `length_bounded(N)` is **3 states** with per-position edge masks, not N + 2. Note also that the shipped J0-map variant only *uses* the constrained draw at emission, so on that path the tree runs once per commit, not per step — the per-step cost applies to the J1/constrained-SC variants.
- Constraints fix format, not reasoning: the guarantee "is free when the grammar encodes the task's correctness condition, and can be catastrophic when it only encodes the output's shape" (Sudoku). Do not expect gains on open-ended screen Q&A; expect them on tool calls, JSON, and termination.
- Numerics are the real engineering risk: two numerically wrong `log_matmul` kernels plus one that exhausted host memory before the shipped pairwise-max kernel, fp32 upstream softmax/class sums driving spurious `Z == 0` on 42–54 % of records at L = 256, an XLA hang at |S| ≥ 128 in fp32, a complement-cancellation defect that triggers when the model is confident on a token inside a negated class's stored set, and a float64 reference oracle with an unaudited hole from 69 nats (pinned as `xfail(strict)`). The shipped sum-product path requires float64; the RTX 5090 executes fp64 at 1/64 rate, so the PyTorch port ships the max-plus MAP path (fp32-safe) first. Every optimised path is differential-tested against the oracle and a `Fraction` enumeration; that test stack is the most valuable asset in the repo.
- Model facts the repo established, with their scope: in the *JAX gemma sampler* the emitted canvas is the sample and can contain uniform random tokens even on the early-stop step (1/31 blocks) — **vLLM and transformers commit the per-position argmax instead**, so this does not transfer; `forbidden_tokens` and `sampling` are inert on the JAX diffusion path; the header grammar `<|channel>·name{1,8}·\n·<channel|>` (ids 100, …, 107, 101) is the **empty thought block of non-thinking mode** — a thinking-mode thought with content is outside that language, which matters because tool calling "works best in thinking mode"; a mask that should reach self-conditioning must sit upstream of the sampler (SPEC §3.7 — the variant was never built; in vLLM the SC state is computed from the step's probabilities, so a pre-step logits edit gives constrained SC for free); sentinels must be finite and must survive division by the temperature (`-1e30 / 1e-10` overflows to `-inf`; use ≤ −1e20); all `end_tokens` (EOS, END_OF_TURN, BEGIN_OF_TOOL_RESPONSE, stop tokens — and `<turn|>` may close a tool call instead of `<tool_call|>`) must be handled or the state set empties at a block boundary.

**Not implemented / open in the repo** (from `docs/HANDOFF.md`): constrained self-conditioning (§3.7, "the actual research question"), renoising variants R1/R2, the `entropy_threshold` sweep (structurally inert — `early_stop_fn` is never passed at production call sites), the refusal-branch union for irrelevance records, five of six evaluation datasets, the MAP tree benchmark (materialises 68 GB at |S| = 512), and a Countdown degeneracy with three refuted hypotheses. Eleven artifacts are archived with no current version; the committed `RESULTS.md` text is the record and must not be regenerated.

**Port implications for local_astra.** Our serving stack is vLLM/PyTorch and SPEC §5.8 rules out a JAX/PyTorch hybrid (a framework boundary forces a sync per denoising step), so the inference core is re-implemented in PyTorch behind the plugin hook in §5. Size of the job, measured: ~470 executable JAX lines in `infer/` + `model/constrained.py` (no `associative_scan`, no `donate_argnums` — those are only rejected in docstrings; loops are Python-unrolled) → ~700–900 lines of torch including a chunked max-plus/log matmul (the broadcast `[L/2, S, S, S]` is 1 GB at S = 128); `reference.py` (503 numpy lines) ports for free; `model/sampler.py` + `state.py` (401 lines of flax/while_loop) are rewritten against vLLM; 14 test files (8.2k lines) are JAX-free, 13 (11.3k lines) need `jnp → torch`. Three things transfer unchanged: `compile/` (swap its `gemma` tokenizer import for HF/sentencepiece), the oracle and the exactness/guarantee tests, and the model facts above. The JAX code stays as a second oracle on CPU. The budget-aware terminal factor needs `R = min(max_tokens − emitted, max_model_len headroom) − canvas_length` per block; vLLM exposes `max_tokens` in `add_request` and the committed count via `num_computed_tokens − prompt_len`, and delivers `max_model_len` truncation as `valid_canvas_len` (pad `M_i` with identities there). Design points that differ from the repo: emission is the joint constrained draw written coherently into vLLM's `argmax_canvas`/`canvas`/`draft_tokens` (never voice a canvas that is not accepted); the MAP path first; constrained self-conditioning tested early because a pre-step logits edit reaches vLLM's SC for free.

## 1. Why it is harder for this model than for an AR model

An AR grammar engine (Outlines, xgrammar, llguidance) keeps one automaton state for the known prefix and emits one token bitmask for the next position. In a diffusion LM the 256 canvas positions are predicted jointly and accepted out of order, so most positions have no known prefix and hence no single automaton state. DiffusionGemma makes it strictly harder than the masked-diffusion models in the literature: it is uniform-state ("renoising") diffusion, so non-accepted positions are refilled with random vocabulary tokens every step and previously accepted tokens can be re-noised if their entropy rises (vLLM's sampler literally does `torch.where(eb_mask, new_tokens, random_tokens)`). Nothing is fixed until the whole canvas converges and is committed. Any method that assumes "unmasked means final" only holds at commit time here.

## 2. What the literature offers

Four families, in order of relevance to us.

Automaton marginals over positions. DINGO (Suresh et al., NeurIPS 2025) runs a Viterbi-style dynamic programme over DFA states across all positions each step, treating unknown positions as "any transition", and picks the highest-probability regex-valid full sequence; the model's normal acceptance rule then commits a subset. Overhead is marginal (23.92 s vs 23.78 s on GSM-Symbolic) with up to +68 points on JSON tasks. Dang & Ermon (2026, arXiv 2607.07026) generalise this with forward–backward over an (N)FA as a chain graphical model, giving exact per-position marginals of the constrained mean-field posterior, supporting sampling, and — the property that matters for us — "compatible with parallel and block-wise decoding under arbitrary remasking schedules", at under 5 % wall-clock overhead (Dream-7B BFCL-Live 63.9 → 71.5). Because it re-derives everything from the *current* per-position distributions at every step and assumes nothing about monotone unmasking, it is the only family that is a principled fit for a renoising sampler.

CFG completability with rejection (Mündler, Dekoninck, Vechev, ETH; arXiv 2508.10111, code `eth-sri/constrained-diffusion`): checks whether a partially filled canvas can still complete to a string in the grammar and resamples violating proposals. Near-perfect syntax, but median +30 % time and no finite-budget guarantee, and it assumes accepted tokens stay. EPIC (arXiv 2606.00722) makes CFG constraints cheaper by committing jointly-compatible subsets.

Projection / Lagrangian methods (Cardei et al., NeurIPS 2025; CDC 2605.16829) handle soft or semantic constraints (toxicity, counting, static-analysis-checked code) by projecting per-step distributions — not what we need for tool calls, possibly useful later for "must mention the on-screen entity" style constraints.

Schema scaffolding (S³, arXiv 2507.04504) pre-fills the invariant JSON skeleton into the canvas and lets the model fill value slots; it reached target quality in 8 steps instead of 16 — the clearest published evidence that fixing structure a priori makes the sampler converge faster. DiffusionGemma's own report says JSON extraction and code debugging "converge in merely two to three steps", which is the same phenomenon.

Commercially, Inception's Mercury exposes `response_format: json_schema` (mechanism undisclosed); no structured-output support is documented for Gemini Diffusion.

## 3. What serving stacks support today

vLLM: structured outputs are rejected with HTTP 400 for diffusion models (PR #45468) after issue #45436 showed why — the scheduler hands a whole committed canvas to xgrammar, which finishes at the closing brace and rejects the tail; denoising steps are never constrained. Issue #45572 tracks canvas-aware support; the DiffusionGemma author calls it "an open problem". Tool calling works, but only by regex post-parsing (`--enable-auto-tool-choice --tool-call-parser gemma4`) and "works best in thinking mode". `logit_bias` is not applied in the diffusion sampler; penalties are ignored. The good news is in the code: `DiffusionSampler.__call__` receives raw logits of shape `[num_seqs × canvas, vocab]` at every denoising step and applies top-k/top-p before the compiled sampling step, and the runner already has the per-request bitmask plumbing (`StructuredOutputsWorker` with `mask_stride = canvas length`, `apply_grammar_bitmask` before the sampler). What is missing is a backend that computes a *position-wise* mask instead of a *prefix-wise* one.

SGLang: `json_schema`, `regex`, `ebnf`, `structural_tag`, `logit_bias` and penalties all return 400 for `Gemma4Renoise`. Streaming is block-level.

transformers (`DiffusionGemmaForBlockDiffusion`): `generate(..., logits_processor=...)` calls the processor at every denoising step on the full `[batch, canvas, vocab]` tensor with `cur_step`, before sampling, acceptance and the stopping criterion; `decoder_input_ids` can seed the initial canvas (scaffolding); `TextDiffusionStreamer` exposes `put_draft` per step and `put` at commit. This is the prototyping surface.

Native tokens: Gemma 4 tool calls are `<|tool_call>call:name{key:<|"|>value<|"|>}<tool_call|>`, results after `<|tool_response>`, thinking in `<|channel>thought…`; these are single vocabulary entries, ideal anchors for per-position masks. Note that Gemma 4 uses `<|"|>` as string delimiters, so any regex must be built on token IDs, not characters.

## 4. Length bounding — the specific idea

What happens after EOS today (verified in vLLM and transformers source): once a canvas commits, everything after the first EOS is dropped (vLLM trims in the scheduler; transformers pads); the full 256-position canvas has already been denoised, so `max_tokens` has no latency effect; pad is not special in the sampler; `valid_canvas_len` shrinks only near `max_model_len`. The stopping rule averages entropy over **all 256 positions** and checks argmax stability over all positions, in both implementations.

Consequences. A length constraint cannot cut per-step cost (fixed by canvas length); it can only cut the *number* of steps by making the criterion satisfied sooner, and a deterministic tail does lower the criterion. But three things temper the hypothesis: stock short answers already stop in 3–5 steps (repo Phase 0: ~70–120-character answers), so the tail is not what delays them — the lever exists only when the model intends a long answer and the constraint fights its plan, and the repo's own trace shows a constrained emission flipping for 48 steps at entropy 1e-6 in that regime; under the J0 design nothing about the trajectory changes, so nothing changes the step count — the mask must sit upstream, on the logits before `_compiled_sample_step` (or the transformers processor); and a two-token `{EOS, pad}` tail is not deterministic — it carries up to 0.69 nats per position against a total budget of 0.005 × 256 = 1.28 nats, so it would *prevent* convergence. The tail must be pad-only (or handled by the joint automaton), with EOS allowed only at the boundary. James's "≤ 64 human characters" maps onto a 3-state automaton with per-position edge masks; character limits become token limits through the tokenizer's byte lengths.

Alternatives, ranked by cost: (1) a smaller server-global canvas (linear reduction of per-step FLOPs and sampler buffers; quality away from the 256 training length unknown — B1 sweeps 128 vs 256); (2) the pad-only tail as a ~20-line logits hook; (3) system prompt; (4) `max_tokens`, output-only.

Verdict: **depends — decide by experiment, not argument.** The decisive test (transformers, one afternoon): 50 prompts whose unconstrained answers are long; arm A unconstrained, arm B pad-only tail beyond N = 48 via the logits hook, arm C `{EOS, pad}` tail (predicted to run to 48 steps), arm D brevity prompt only; log per-step per-position entropy, steps-to-stop, wall time, EOS ≤ N rate and answer quality. B approaching A's short-answer 3–5 steps with EOS ≤ N ≥ 95 % confirms the lever; B running to 48 or truncating mid-sentence refutes it.

## 5. Plan (revised after the audit)

0. **Plugin milestone 0 — the passive tap (no constraints).** Ship the out-of-tree plugin first as pure observability: wrap the stock sampler, and after each step copy `states.canvas[slot]`, `states.argmax_canvas[slot]`, `states.step[slot]` (plus the acceptance mask and per-position entropy where reachable) non-blocking into a pinned host ring; a publisher thread emits `astra.canvas.step` events for the HUD's denoising view (`12` §2). Zero risk to generation, it validates the whole registration path (entry point, `get_model_state_cls`, `custom_sampler`, `add_request`, slot reset), and it produces the demo's most distinctive visual. Overhead budget < 3 % of step time (B16).

1. **Package the compiler.** Extract `diffgemma_fa.compile` as a standalone, framework-free package (`dgfa-compile`) with its existing tests; add two grammars we need: `length_bounded(N, end_tokens)` and `gemma4_tool_call(tools)` built on token IDs with the `<|"|>` delimiters. Both must land in the |S| ≤ 128 bucket; the build gate reports |S| and refuses larger automata on the live path.
2. **PyTorch inference core.** Port `infer/` (tree forward–backward in log space, constrained marginals, eq. 8 draw, budget-aware terminal factor) to PyTorch with the repo's numerics lessons baked in: log-space throughout, normalise every tree node, finite sentinel `-1e30`, `log(max(q, 1e-30))`, edge-multiplicity weighting on NFAs, `is_dfa` fast path. Port the float64 reference oracle and the exactness and guarantee tests *first*; fix the oracle's complement-cancellation hole while porting (use the kernel's non-subtractive form). Ship the max-plus MAP path first (fp32-safe); the sum-product path needs an end-to-end log-space design (log-softmax → per-class logsumexp → log tree) because the 5090's fp64 rate is 1/64. Target: |S| = 128 MAP tree ≤ 2 ms per step in fp32 on the 5090.
3. **Prototype in transformers** through the `logits_processor(input_ids, scores, cur_step)` hook (verified: it runs before sampling, acceptance and stopping, and the step's self-conditioning logits are taken from the *processed* logits, so the constraint reaches SC). Reproduce the BFCL-Live simple result on a 50-record slice as the port's acceptance test, then measure the two things we care about: steps-to-convergence and wall time with `length_bounded(N)` for N ∈ {32, 64, 96} at canvas 256 and 128, and Screen-QA accuracy under the length grammar plus a brevity system prompt.
4. **vLLM integration as an out-of-tree plugin, not a fork** (verified against vLLM `main` and v0.29.0). The extension point is two levels deep: the model class exposes `get_model_state_cls()`, and it is the **ModelState** (`DiffusionGemmaModelState.custom_sampler(sampler)`) that returns `(DiffusionSampler(...), None)`. The plugin is a pip package registered under the `vllm.general_plugins` entry point (loaded in every process) that calls `ModelRegistry.register_model("ConstrainedDiffusionGemma", "pkg.mod:Class")` under a **new** architecture name selected with `--hf-overrides '{"architectures": ["ConstrainedDiffusionGemma"]}'` (multimodal processor registration and the other class-level registrations are inherited by the subclass; the lazy string form keeps the registry's inspection subprocess from importing worker code). The subclass overrides `get_model_state_cls()` → a ModelState subclass whose `custom_sampler` wraps `super().custom_sampler(sampler)`'s sampler in `ConstrainedDiffusionSampler`. The runner calls `sampler(logits, input_batch)` (two positional arguments) and expects a `SamplerOutput`; `__call__` is eager Python, and only `_softcap_logits`, `_compute_num_rejected` and `_compiled_sample_step` are compiled, so a host-side branch plus a contiguous fp32 tensor op before the compiled step is safe. Per-request options arrive in `sampler.add_request(req_index, prompt_len, sampling_params)` (`SamplingParams.extra_args`, set by the OpenAI server from `extra_body={"vllm_xargs": {"dgfa_mode": "none|mask|joint", "dgfa_grammar": "<id>"}}`; scalars/lists only) — not in `input_batch` — and per-slot state is reset in `ModelState.remove_request` (slots are LIFO-reused). With no constrained slots in the batch the sampler delegates untouched (host-side check on `np.any(mode_np[decode_slots])`), so unconstrained and constrained requests share one server. Rows are decode requests only, position-major (`row = decode_idx·CL + pos`); `mask` mode edits logits before the step (finite sentinel ≤ −1e20 — `-inf` makes the entropy NaN and the request runs all 48 steps, and −1e30 overflows after `÷ temp`); `joint` mode overwrites `argmax_canvas`, `canvas` and `draft_tokens[slot, :CL]` coherently after the step, gated on `is_committing`; constrain only `valid_canvas_len` rows; allocate plugin buffers in the constructor because the decode path never runs during `profile_run`. Coupling surface: `get_model_state_cls`, `ModelState.custom_sampler`, `DiffusionSampler.__call__`/`add_request`, `_compiled_sample_step` parameter names, `DiffusionGemmaRequestStates` fields, `InputBatch` fields used — pinned to v0.29.0 in `services/versions.lock` with a contract test that fails loudly on drift. Two environmental traps: `VLLM_PLUGINS=""` disables plugins silently (add a startup probe), and any installed package exposing a `vllm.logits_processors` entry point forces the V1 runner, which rejects diffusion models. Structured-output backends are a closed enum invoked prefix-wise in the scheduler (never seeing logits), and SGLang's `--dllm-algorithm` is in-package discovery — neither is an alternative. Upstreaming on issue #45572 is optional. The dual-branch AR path (`08`) remains parked because it needs the scheduler; note that vLLM also rejects `structured_outputs` for any diffusion model at validation, so an AR branch inside the diffusion engine would need that bypassed too.
5. **Safety net that works today**: commit-time validation of the canvas with xgrammar `validate_tokens()` and a re-denoise retry; the `gemma4` regex parser as the tool-call fallback.
6. **Research branch** (after the above ships): constrained self-conditioning, which `diffgemma-fa` identifies as the untried lever that lets the model re-plan under the constraint.

## 6. Tests to write first

From the repo, ported: brute-force exactness on tiny alphabets (V = 4, L ≤ 8, Bonferroni-corrected χ²), the two-part guarantee (viable prefix per block within budget; acceptance of the concatenation at the end), reference-vs-optimised differential tests across the regimes that bit the JAX port (L = 256, narrow negated classes, T = 0.1, spans to 250 nats), NFA as well as DFA fixtures, kernel-shape tests. New: |S| budget gate on the live path; `length_bounded(N)` yields ≤ N content tokens 100 % of the time and never masks a position < N; tool-call grammar yields parseable Gemma-4 tool calls 100 % of the time on a 50-prompt set versus the unconstrained parse rate; steps-to-convergence ratio and wall time recorded (B13); Screen-QA within 2 points of baseline under the length grammar; determinism at temperature 0 with and without the constraint. Process rules imported from the repo's CLAUDE.md into ours: a reviewer reads every GPU- or artifact-writing command before it runs; never measure a tree an agent is editing; state the whole regime beside every number.
