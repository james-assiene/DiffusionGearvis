# Dual-branch decoding: AR opener + diffusion thinker from one prefill

**Status:** parked, 2026-09-12 — superseded for the demo by the `talker` profile (Gemma 4 E2B as a front-of-house model that never asserts content; design D14, `11` §8), which delivers the low-latency spoken opener without a vLLM scheduler patch. The AR-mode go/no-go experiment (X6) still runs in Phase 0 because it informs a possible "deep think in AR mode for maximum quality" route later. Original proposal follows (2026-09-11).

## 1. The fact that makes it possible

DiffusionGemma is not a different network from Gemma 4. It is "an encoder-decoder transformer with shared weights θ": the same parameters act as a causal encoder over the history and as a bidirectional decoder over the noisy canvas, with a 7.8M-parameter self-conditioning MLP as the only addition. Section 3.5 of the report: "Because DiffusionGemma shares the exact same transformer architecture as Gemma 4, the final DiffusionGemma weights can be seamlessly loaded back into the original architecture to perform standard AR generation using causal attention, exactly as the base model does." Table 3 (thinking on; columns TD → DG-in-AR-mode → Gemma 4 served with MTP) gives: AIME 2026 69.1 → 84.2 → 88.3; GPQA Diamond 73.2 → 79.8 → 82.3; LiveCodeBench 69.1 → 71.4 → 77.1; MMLU-Pro 77.6 → 78.8 → 82.6; IFEval 97.4 → 97.2 → 98.7. The no-think columns are the relevant ones for a spoken opener: DG-AR 57.5 / 67.2 / 58.3 / 79.1 / 95.7 vs TD 50.8 / 64.6 / 60.6 / 77.9 / 94.5 — near parity. Throughput on one H100 FP8 at batch 1: TD 1479 tok/s (19.7 tokens per forward) vs DG-AR 204 tok/s (1.0 per forward; the checkpoint ships no MTP heads). The introduction says this "opens up the possibility to route requests dynamically based on latency constraints and task complexity, as well as to employ hybrid decoding approaches", but the paper ran no hybrid experiments.

So from the same weights we have a slower, better mode and a faster, slightly worse mode, and the causal encoder KV cache built over the prompt is the same object in both.

## 2. The proposal

For each user turn, after one (prefix-cached) prefill, run two decoding branches concurrently in the same engine:

Branch A — AR: a short spoken answer, streamed token by token into the TTS. Its time-to-first-token is the transcript prefill plus one step (~30–50 ms after the cached prefix), and it decodes at roughly one token per diffusion step (~35 tok/s at the design's 25–30 ms step), far above speech rate.

Branch B — diffusion: the full reasoning and complete answer, where diffusion's throughput advantage is real (thinking tokens are never spoken, so burstiness does not matter).

**A constraint discovered in verification: the two branches cannot differ on thinking.** The chat template emits `<|think|>` as the first token of the system turn, so an A without thinking and a B with thinking diverge at token ~3 and share no cacheable prefix. Either both carry `<|think|>` and A is sent as a raw prompt that appends the template's own empty thought channel (`<|channel>thought\n<channel|>`) after `<|turn>model\n` — to be validated for quality — or both run without thinking, in which case Table 3's no-think columns say A and B are near-equal in quality and B's only justification is speed.

The Conductor speaks A immediately. When B commits its answer, a cheap comparison (entailment via a small CPU model, or B's own one-line self-check appended to its prompt) decides whether B's conclusion is consistent with what A said; if not, the assistant self-corrects ("actually, looking closer, …"), which is also what people do. If A is still speaking when B arrives, B's continuation replaces A's remaining text at the next sentence boundary.

## 3. Cost analysis on a 32 GB RTX 5090

Memory: persistent per-slot diffusion state is small (< 10 MB; self-conditioning is stored as `[CL, hidden]`), and the prompt KV is shared through prefix caching, so an **AR** branch costs almost nothing beyond its KV blocks. A second *diffusion* branch is different: the vocab-sized sampler transient (~2.5–2.7 GB per concurrently denoising request, tiled when memory is short) is paid per branch. A second *instance* would need its own 17.5 GiB of NVFP4 weights, KV pool and CUDA graphs and does not fit next to the diffusion server. Conclusion: one engine, two request modes, and the opener must be the AR branch, not a second canvas. James's intuition that the weights leave room is right for the request-level version.

Compute: the diffusion step processes a 256-token canvas that activates about 84 unique experts per MoE layer (versus 8 for one AR token), which makes the MoE kernel 4.3× slower than an AR step and the whole step 3.2× slower — i.e. the step is still dominated by expert *loading* (weight bandwidth), not by arithmetic on the canvas (report §6, Fig. 11). Batching one extra AR token into that step therefore adds little, and the AR token advances once per diffusion step (~35 tok/s on the 5090 at the design's step time), still far above speech rate. This is a hypothesis to measure, not a fact: the diffusion path captures full CUDA graphs with persistent buffers, and an extra token changes the batch shape and may push steps to eager mode.

## 4. The obstacle: vLLM has no per-request AR mode

`DiffusionConfig` is engine-global (`canvas_length` becomes `num_speculative_tokens`, `max_denoising_steps`); the scheduler sets `num_sampled_tokens_per_step = 0` for every diffusion request. `canvas_length = 1` is not AR mode — each token would cost at least two forwards (converge, then commit), use the temperature schedule and entropy-bound Gumbel sampler, and predict position *i* from a noise token rather than from the position *i−1* state. The actual AR computation already exists inside the DiffusionGemma model in vLLM: the prefill/commit pass runs the causal encoder, and the runner has a per-sequence causal flag so causal and bidirectional sequences share one batch (report §6; on sm_120 only the Triton attention backend implements it). What is missing is a request-level `decode_mode: "ar"` that (a) marks the sequence causal, (b) schedules one token per step instead of a canvas, (c) bypasses the diffusion sampler for that sequence, and (d) keeps the self-conditioning MLP off it — `prepare_inputs` currently applies SC to every request with draft tokens, so an AR slot must be excluded in `prepare_inputs`, the sampler split and the scheduler. It must also bypass `_validate_diffusion`, which rejects `structured_outputs`, `temperature ≠ 1`, `min_tokens`, `logit_bias` and `seed` for any diffusion model. Conceptually clean; in practice a scheduler + model-runner + sampler patch, complicated by the canvas riding the spec-decode path ("num_sampled = 0 and num_rejected = query_len … only a commit advances" the KV position).

SGLang has the same global-config limitation; no evidence it is easier there.

## 5. Recommended path

Phase 0 (no patch, ~1 day of GPU time): the bf16 checkpoint (~52 GB) cannot be loaded in transformers on the 5090, and the tensors live under `model.encoder.language_model.*` / `model.decoder.*` with `architectures = ["DiffusionGemmaForBlockDiffusion"]`, so the go/no-go is: remap the **NVFP4** checkpoint to Gemma 4 layout (text config is identical: 30 layers, kv 8/2, head_dim 256/512) and serve it in vLLM as a plain AR model; run a 30-item MMLU-Pro/GPQA slice thinking-on (expect ≈ 79–80 per Table 3) and the Screen-QA set thinking-off; then serve DiffusionGemma normally and measure first-canvas latency for spoken-length answers plus the LLM-judged contradiction rate between the AR opener and the TD answer. Go if contradictions ≤ 3–5 % and AR-NVFP4 quality is within noise of Table 3; add one probe for whether `<|think|>` plus a forced empty thought channel keeps no-think quality (this decides whether the shared prefix exists at all). If the first canvas is already ≤ 300 ms for spoken-length answers, the AR branch's TTFT gain is small and its value is quality and token-level streaming; if it is 600 ms+, it is the main latency fix.

Interim (no patch): an acknowledgement clip keyed to the first-canvas EMA. Gemma 4 E4B as an independent opener is **not** coherent as first written — a different 4B model without the screen speaking a "first-order answer" that a 26B model then completes. It becomes coherent only as "A conditions B": A's first sentence is appended to the shared prefix and B *continues* it. That same idea simplifies the dual-branch design itself — start B ~0.4 s after A with A's first sentence in the prompt — and removes the consistency classifier; it may remove the need for the `decode_mode` patch altogether if the AR-remapped checkpoint can run as a second small request on the same engine (it cannot: same weights, different architecture class — so this variant still needs either the patch or a separate small model).

Target (patch): implement `decode_mode` in a vLLM fork as a contained subproject with its own tests (see §7), run it as the default engine, and propose it upstream — the tech report's own "hybrid decoding" framing makes this a natural contribution.

## 6. Interactions with the rest of the design

Constrained decoding (`07-constrained-decoding.md`): on an AR branch, standard prefix-FSM engines (xgrammar/llguidance) would work — but only once the `decode_mode` patch also bypasses vLLM's diffusion validation, which rejects `structured_outputs` for the whole model; `max_tokens` genuinely reduces latency on A. Turn machine: a new sub-state `SPEAKING_A_AWAITING_B` with events `b.committed(consistent | inconsistent)`, plus the cases the first draft missed — A finishing before B (dead air: filler or hold), swap on inconsistency (the gate must feed TTS at most one sentence ahead), check latency, history shape. History: store A's spoken text and B's final answer, never B's thoughts. VRAM: `max-num-seqs` is 3 (A, B, anticipatory prefill); the idle captioner yields.

## 7. Tests

Contract (transformers, GPU): AR-mode load succeeds and matches Table 3 within noise on a 30-item MMLU-Pro/GPQA slice; AR tok/s and TD first-canvas latency recorded (B14). Fork tests: an `ar` request and a diffusion request in one batch produce the same outputs as when run alone (determinism at temperature 0); AR TTFT ≤ 2 step latencies after a cached prefix; step latency with the extra AR sequence within 10 % of the diffusion-only step; prefix-cache hit for both branches ≥ 0.9. Integration: consistency classifier precision/recall on a labelled set of (A, B) pairs; correction utterance timing; no double-speaking. Eval: user-perceived answer quality with A+B versus B-only on the Screen-QA set (LLM-judge), and latency distribution B3 with the dual branch on.
