# Second pass on the identified risks — what we missed, and the resulting design changes

**Status:** 2026-09-11. This pass was triggered by James catching that Kyutai Pocket TTS runs on the CPU, which the first draft had not considered. The question asked of every risk was: "what CPU, smaller-model or architectural alternative did we not look for?" Each section ends with the change made (or explicitly not made) to `01-design.md` / `02-architecture.md`.

## R1 VRAM tightness

The real finding is that DiffusionGemma is the only component that *needs* the GPU. STT has a credible CPU path: NVIDIA's `nemotron-speech-streaming-en-0.6b` (and the newer `nemotron-3.5-asr-streaming-0.6b`, 40 locales) runs through NeMo-Speech.cpp (Apache-2.0, ggml-style, CPU/Vulkan/CUDA backends, WebSocket server with `endpointing_ms`; Q8_0 1.06 GB, Q4_K 0.56 GB). Caution from verification: the widely quoted int4 0.67 GB / 8.2 % WER / 0.56 s / "comfortably faster than real-time on CPU" numbers come from an **ONNX Runtime** study (arXiv 2604.14493), not from NeMo-Speech.cpp, which publishes no CPU RTF — measure. `parakeet_realtime_eou_120m-v1` (120M, emits `<EOU>`, p50 160 ms) is the lightest option with built-in endpointing. Moonshine v2 and sherpa-onnx streaming Zipformer are further CPU options. Kyutai STT on CPU has no evidence of realtime operation and is not worth pursuing. Relevant to the choice: Kyutai's Rust STT server has a reported idle CPU-spin bug (500–1200 % CPU while idle, moshi issue #390). OCR and embeddings also run fine on CPU for a 1–2 Hz change-detection loop (PP-OCR on OpenVINO at 2–4× native; SigLIP-2 ONNX CPU servers exist).

On the LLM side we had not listed: vLLM sleep mode (`--enable-sleep-mode`, level 1 parks weights in host RAM) for handing the GPU to a batch job; FP8 KV cache, which on Blackwell goes through FlashInfer without Hopper's workarounds, with the recommendation to skip sliding-window layers (`--kv-cache-dtype-skip-layers sliding_window`) and the caveat of a ~1.6× prefill penalty for head-dim-256 models — measure before enabling; and the confirmation that `--max-num-seqs ≤ 4` is mandatory (sampler transient scales seqs × canvas × 262K vocab). MoE expert offload to CPU does not exist for this model in vLLM; llama.cpp's `-ncmoe` works for Gemma 4 but DiffusionGemma there is CLI-only. Gemma 4 E4B int4 on a 16–32-core CPU should manage ~10–20 tok/s — enough for a ten-token acknowledgement, not for content.

**CORRECTION 2026-09-13 (measured on the box).** The arithmetic below is stale by 2 GiB and its conclusion no longer holds. T-0014 raised the KV pool from 2 to 4 GiB because 2 GiB of **bf16** KV tops out at 8,720 tokens — not enough for the 4-image prompt this design allows — and bf16 is mandatory (docs/01 R2; the checkpoint's own `kv_cache_scheme` silently selects fp8 otherwise). Measured footprint of the running engine: **26.9 GiB**, leaving 4.8 GiB free, so GPU STT at ~2.5 GiB would breach the ≥ 3 GiB reserve. **The `lean` profile as specified does not fit.** We are therefore already running the `cpu-stt` shape this section anticipated, arrived at by measurement rather than by decision — with Kyutai on CPU rather than Nemotron, a third option not costed here. X9 should now decide it deliberately. Original text follows.

Change: with Pocket TTS on CPU the default (`lean`) profile is ≈ 17.5 (weights) + 2 (KV) + 2–3 (activations/graphs) + 2.5 (sampler transient, unprofiled) + 2.5 (Kyutai STT) + 1 (contexts) + 1 (desktop) ≈ 28–30 GiB — it fits, without CUDA MPS, but only with Pocket TTS on the CPU; GPU TTS-1.6b returns only if STT also moves to the CPU. Kyutai STT stays on the GPU by default for pragmatic reasons (Unmute wires it; streaming words with timestamps), not because of its semantic VAD — TurnBench shows smart-turn v3 matches it on end-of-turn. The `cpu-stt` profile is compared in a one-evening experiment (X2). FP8 KV is dropped (≈5 % saving with the hybrid KV manager); sleep mode stays as an operator convenience.

## R2 First-canvas latency

Confirmed against source: vLLM's `DiffusionConfig` has exactly two engine-level fields (`canvas_length`, `max_denoising_steps`); the sampler constants come from `generation_config.json` and are overridden with a custom `--generation-config` directory (the recipe's `--hf-overrides` keys do not exist in current vLLM). SGLang exposes more (steps, entropy bound, temperature schedule, thresholds) but via a global YAML. There is no per-request canvas or step control in either. The "small first canvas per request" idea in the first draft is therefore not implementable as stated. Adaptive early exit is on by default (mean entropy < 0.005 and argmax stable for two steps), so short answers already converge in ~9–17 steps; the tech report gives per-step latency of 13.56 ms on an H100 FP8 and average effective steps of ~12. Prefix caching works on the encoder, hashes multimodal inputs by content, and requires text-before-image ordering for hits; there are open reports of encoder-cache crashes under concurrency. Thinking roughly doubles tokens before the answer.

Change: D3 is rewritten. Canvas length becomes a deploy-time constant chosen by benchmark B1 (128 vs 256). Perceived latency comes from three other levers instead: the CPU reflex/filler path, the dual-branch AR opener (`08-dual-branch-decoding.md`), and constraint-driven convergence (`07-constrained-decoding.md`). Prompt layout is fixed as stable text prefix first, current frame last, and an unchanged frame is never re-sent.

## R3 Echo cancellation and double-talk *(revised after verification — see the last paragraph)*

PipeWire's `module-echo-cancel` supports only the WebRTC APM backend and documents no double-talk tuning. Two better options were missed. First, do AEC in-app: because we synthesise the TTS audio ourselves we hold a perfect far-end reference, so WebRTC APM AEC3 via `webrtc-audio-processing` bindings (Rust crate from tonarino; older Python bindings) with our own TTS stream as the reference removes PipeWire routing latency variability and lets us gate STT during our own speech. Second, a "self-echo" filter at the transcript level: if STT output fuzzy-matches the text currently being spoken by TTS, drop it. Hardware AEC in USB speakerphones (Jabra Speak, Anker PowerConf, Poly) is the cheap robust fix for open speakers; they present as UAC devices with DSP-side AEC. RNNoise (PipeWire filter-chain) and DeepFilterNet3 (LADSPA) are the CPU noise-suppression options.

Change (revised): the frontend no longer owns audio at all. The verification pass found that an AEC3 whose reference is "the PCM we sent to the browser" cannot work — the browser drains an app-level queue, so the reference-to-echo delay grows and jumps per utterance, and AEC3 tolerates a fixed unknown delay with slow drift, not that; APM also runs at 16/32/48 kHz, not 24. So the Conductor owns capture and playback on PipeWire (48 kHz, 10 ms blocks), which gives exact `played_ms` for barge-in truncation and a stable reference; AEC then runs in-process via `livekit-rtc`'s `AudioProcessingModule` (the only maintained Python AEC3 binding — PyPI `webrtc-audio-processing` is 2019-era AEC2) or via PipeWire `module-echo-cancel` with a dedicated TTS sink. The transcript-vs-TTS filter stays; the first demo is headset + VAD gating with no AEC.

## R4 Multi-turn drift

The Gemma 4 chat template re-injected prior assistant *thinking* into multi-turn prompts, causing 33–37 % repetition-loop failures in agentic loops until Google's July 2026 template fix, and 26B still shows "rumination loops" in the thinking channel; DiffusionGemma shares the template lineage. Unsloth's guidance is explicit: do not include previous hidden thoughts in history. For a diffusion model, truncation on barge-in must be of the *committed and spoken* text, not the canvas.

Change: history stores (user text, assistant *spoken* text) only; thoughts are never replayed; images older than two turns are replaced by a one-line caption/OCR summary (which also frees KV); rolling summaries run on the CPU helper. A unit test replays the July-2026 template loop case. The template revision is pinned.

## R5 Blackwell software churn

vLLM ≥ 0.24 uses native CUTLASS SM120 kernels for W4A4 NVFP4 layers; W4A16 layers in "mixed" ModelOpt checkpoints fall back to Marlin with a misleading "no FP4 support" warning. The NVFP4 DiffusionGemma checkpoint was being tested on SM120 with torch 2.11 + cu130 in June 2026. Known landmines: NVFP4 KV corrupts V scales on the FlashInfer XQA route (open bug); some SM120 backends need piecewise CUDA graphs. Lna-Lab still ships twelve out-of-tree SM120 patches as a Docker image, which says the bare-metal path is rough. No evidence that SGLang is more stable on SM120.

Change: vLLM is deployed from the pinned `vllm/vllm-openai:v0.29.0` container (cu130) on driver ≥ 580 with `--attention-backend TRITON_ATTN` (mandatory: only Triton implements the per-sequence causal flag on sm_120), W4A4 layers only, no FP8/NVFP4 KV, SGLang kept as a tested fallback image. A "known-good versions" file is part of the repo; the boot-time VRAM assertion is joined by a kernel-backend assertion (the `NvFp4 MoE backend` log line — NVIDIA's checkpoint has no W4A16 layers, so a Marlin check would be the wrong test) and by an `entry_points(group="vllm.logits_processors")` emptiness check.

## R6 Wayland window metadata

Nothing standard has landed for GNOME: focused-window title and geometry still require a Shell extension over D-Bus. KDE Plasma exposes window titles/app IDs/focus by default through scriptable D-Bus (`kdotool`) and the `kde-plasma-window-management` protocol; wlroots compositors expose `wlr-foreign-toplevel-management`; `ext-foreign-toplevel-list-v1` is the cross-compositor answer and is implemented by KDE and wlroots but not GNOME. Portal screencast restore tokens make the one-time picker a solved problem everywhere.

Change: KDE Plasma becomes the reference desktop for the target box; GNOME is supported with a small bundled Shell extension as a hard dependency. Correction from verification: KWin does **not** implement `ext-foreign-toplevel-list-v1` (wlroots compositors do); KDE's mechanism is `org_kde_plasma_window_management` or a resident KWin script over D-Bus, and `zkde_screencast_unstable_v1` offers dialog-free capture. Capture uses portal restore tokens (opt-in on wlroots) and the daemon carries a portal app-id.

## R7 Things that were simply missing

A CPU front-end chain so the GPU is never touched until the owner is addressing the assistant: a global hotkey via the `GlobalShortcuts` portal or openWakeWord (code Apache-2.0, but the **bundled models are CC-BY-NC-SA** — train our own with its pipeline) with a session window so follow-ups need no re-wake → Silero VAD → STT, with an owner-voice check (WeSpeaker/3D-Speaker via sherpa-onnx) as a **veto** at end-of-turn rather than a gate: reliable embeddings need ≥ 1.5–2 s of speech (17 % EER at 0.5 s), so it cannot sit before STT or inside a 300 ms barge-in decision. It still answers the "talking to someone else" case that Full-Duplex-Bench v1.5 says cascades handle badly, one step later. Power: 5090 Linux idle draw is a recurring complaint; `nvidia-smi -pl` costs little at batch-1 MoE inference, and moving the display to the iGPU lets the card reach deeper idle states. Operational hygiene: a warm-up request with an image at boot (JIT kernels), a systemd watchdog on `/health`, audio ducking of other streams during TTS via PipeWire per-stream volume, per-app privacy exclusions matched on app-id before capture, and an audible/visible cue when the mic goes hot.

Change: all of the above are added to the architecture (reflex lane, perception, services) and to the test plan (owner-check false accept/reject rates, wake-word FRR/FAR, warm-up and watchdog tests).

## Summary of design deltas

| Item | First draft | After second pass |
|---|---|---|
| TTS | Kyutai 1.6b GPU; Kokoro fallback | **Pocket TTS on CPU default** (sentence-in; weights CC-BY-4.0); Kyutai 1.6b only with CPU STT |
| STT | Kyutai 1b GPU | Kyutai 1b GPU default (semantic VAD); **`cpu-stt` profile** with Nemotron via NeMo-Speech.cpp compared in Phase 0 |
| Canvas | small first canvas per request | **server-global**; benchmark 128 vs 256; latency from filler path, AR branch, constraints |
| Audio | frontend owns mic/playback; PipeWire AEC | **Conductor owns audio I/O on PipeWire**; AEC in-process (`livekit-rtc` APM) or PipeWire echo-cancel with a TTS sink; transcript self-echo filter; headset first |
| History | summarise past 6 turns | **spoken text only, no thoughts, images aged out to captions**, template pinned |
| vLLM deploy | pip wheels | **pinned v0.29.0 cu130 container**, `TRITON_ATTN`, `--kv-cache-memory-bytes`, NvFp4-backend assertion, no FP8 KV |
| Desktop | GNOME Wayland | **KDE Plasma reference** (`plasma_window_management`, `zkde_screencast`), GNOME via bundled extension |
| Activation | always listening | **hotkey / self-trained wake word (session window) → VAD → STT**, owner-voice **veto** at end-of-turn |
| Ops | — | warm-up, watchdog, ducking, per-app exclusions, power cap |
