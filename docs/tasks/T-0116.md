## Goal

T-0108b changed what "complete card" means in practice. The gate now repairs what K1 was written to make the model emit itself:
- placeholder TextFields;
- missing DateTimeInput and ChoicePicker values;
- string options;
- inline children;
- text-only Buttons (RB).

Under a rule fixed before any run, this task asks one question: with the merged gate scoring both arms, does K1's UI block still give more complete cards than the live block A0, without regressing anything else?

If the human rules (0) "no run", the task shrinks to a write-up of the CPU re-score below, labelled post hoc. That is a docs-only append, re-derived by one reviewer.

## Power (inference)

**Uncertainty in the stored data:**
- The SD of K1 − A0 complete over 160 per arm is about 6.4 cards.
- The stored estimate is 0 ± 12.5 at 95 %.
- A0 is at 132–136/160, so K1 has at most 24–28 cards of headroom.

**Chance of passing a bar of Q1 = A0 + 12**, by true effect:

| true effect | P(pass) |
|---|---|
| 0 | ≈ 4 % |
| +8 | ≈ 29 % |
| +12 | ≈ 50 % |
| +17 | 80 % (the effect needed for 80 % power) |

**With the stored data as the prior:**
- P(Q1 passes) ≈ 10 %;
- P(Q2 holds on flight_booking_with_memory) ≈ 46 %;
- **P(K1 selected) ≈ 5 %**.

**Why the cheaper or bigger options don't help:**
- Fixing the lone-quote Row (T-0108f) would not reach +12.
- A0's shortfall is mostly surfaces it never drew, which no field wording addresses.
- A positives-only run saves only about 2.3 min.
- Doubling n moves the 80 % power point only to about +12.
