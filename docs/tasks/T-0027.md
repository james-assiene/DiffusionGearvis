# T-0027 — The inbound message limit counts bytes, and `bucket_for` accepts the wire string

**Status:** merged 2026-09-14 (6b69cc7; implementation 1cb9921, review APPROVE with seven mutations red) · **Blast radius:** low (two pure functions; no turn machine, no audio, no GPU, no hook) · **Depends on:** T-0002 (owns `local_astra/contracts/**`; **not** in progress — see Owned files for the carve-out), T-0008 (merged 1ad0421; rulings R7 and R11 are where both defects were recorded)

## Goal
Two one-line defects that merged reviews recorded as "not this task" get a home. (a) `local_astra/contracts/codec.py:61` bounds an inbound **`str`** message by `len(raw)` — code points — while `hud/src/protocol.js` (ruling R11) counts **UTF-8 bytes** against the same `MAX_MESSAGE_BYTES`. Measured on main today: `decode('{"type":"astra.transcript","turn_id":"t","text":"' + "€"*3_000_000 + '"}')` — 9,000,051 bytes on the wire, 8,388,608 allowed — returns a valid `AstraTranscript`, and the same message is `malformed` on the page. It is a consistency defect, not a hole: the socket is loopback-only and `websockets`' `max_size` still bounds the process. (b) `local_astra/perception/policy.py::bucket_for` tests `source is Source.CAMERA`; `Source` is a `StrEnum`, so the raw wire value `"camera"` silently gets `screen_max` (1120 visual tokens for a webcam frame) instead of the camera bucket. Harmless behind a validated `AstraFrame`, wrong for any raw caller — T-0008's test-author found it incidentally and filed it here. After this task the server and the page refuse and accept exactly the same payloads at the same boundary, and `bucket_for` agrees with itself whether it is handed the enum or the string that enum is made of. The value of this task is in the shared fixture rows, not in the diff: the production change is two edits of a few lines each.

## Rulings (decided at plan time; the implementer does not re-open them)

**R1 — the page is right and does not change.** `hud/src/protocol.js::overTheLimit` was fixed under T-0008 R11 and is correct, including its short-circuit. Python follows it; `hud/**` is not touched by this task (criterion 7).

**R2 — the cheap short-circuit is `× 4` in Python, not `× 3`.** The page may skip the encode when `raw.length * 3 <= MAX` because a UTF-8 byte count is at most 3 bytes per *UTF-16 unit* (an astral character is 2 units and 4 bytes = 2 bytes/unit). Python's `len(str)` counts *code points*, where the bound is 4 bytes. Copying the page's constant is the single most likely way to get this wrong, and criterion 2 exists to kill it: the astral payload has `len(raw) * 3 == 7_500_153 <= 8_388_608` yet occupies 10,000,051 bytes. A short-circuit is optional; a wrong one is not.

**R3 — an unencodable `str` is `Malformed`, not an exception and not an acceptance.** A `str` carrying a lone surrogate cannot be UTF-8 encoded, so a byte-length guard can raise `UnicodeEncodeError` where the old character count could not. `decode` is documented as total ("never raises", module docstring, docs/03 §3 "Protocol codecs"); the outcome is `Malformed` with the bytes branch's wording (`"not utf-8: …"`). Messages small enough to skip the encode keep exactly today's outcome (criterion 6) — the fix must not make `decode` eager on every message.

**R4 — `bucket_for` stays a policy function, not a validator.** The comparison becomes value-based so `"camera"` reaches `CAMERA_BUCKET`; an *unrecognised* string keeps today's behaviour (screen buckets, no exception). Introducing `Source(source)` — which raises `ValueError` on unknown input — would give every caller a new failure mode for a bug that is only about one branch. Validation is `contracts/perception.py`'s job.

**R5 — the `source` parameter is not widened to `Source | str`.** Internal callers should pass the enum and `mypy --strict` should keep saying so. The runtime tolerance is for wire-derived values that have not been through a model yet; it is documented in the docstring, pinned by tests, and not advertised in the signature.

**R6 — the boundary is `>`, at both ends.** Exactly `MAX_MESSAGE_BYTES` bytes is accepted; `MAX_MESSAGE_BYTES + 1` is refused. Both sides already agree on this for ASCII and must keep agreeing (criterion 4); the existing `f"message exceeds {MAX_MESSAGE_BYTES} bytes"` error string is reused verbatim so existing `"exceeds" in out.error` assertions keep their meaning.

**R7 — the new payloads live in the shared corpus, built at read time on both sides.** `tests/fixtures/hud/decode_corpus.jsonl` already carries an `oversized` flag built in Python and in JS rather than stored (an 8 MiB fixture does not belong in git). This task generalises that to a `build` object; the existing `oversized` case is left exactly as it is (no churn in merged rows). Corpus rows that are red until the fix lands carry `"pending": "T-0027"`, which the Python loader turns into `pytest.mark.pending(task="T-0027")` (strict xfail, `tests/conftest.py`); the JS side ignores the key — the page is already correct, so those rows must be *green* there from the first commit. The test-author removes the `"pending"` keys at the start of `/implement`, per CLAUDE.md.

## Acceptance criteria

1. **Multibyte oversize is refused (R11).** The corpus row `multibyte_oversized_euro` — `'{"type":"astra.transcript","turn_id":"t","text":"' + "€" * 3_000_000 + '"}'`, 3,000,051 code points, **9,000,051 UTF-8 bytes** — makes `local_astra.contracts.codec.decode` return `Malformed` with `"exceeds"` in `.error`. On main @ `e85965c` it returns `AstraTranscript` (measured, see Regime). Satisfies T-0008 ruling R11 and the T-0008 merge note's carried follow-up; docs/03 §3 "Protocol codecs".
2. **The astral row kills a `× 3` short-circuit (R2).** `'…"text":"' + "😀" * 2_500_000 + '"}'` — 2,500,051 code points, 5,000,051 UTF-16 units, **10,000,051 bytes**, and `len(raw) * 3 = 7_500_153 <= MAX_MESSAGE_BYTES` — returns `Malformed`. A Python port of the page's `× 3` test passes criterion 1 and fails this one.
3. **The size check precedes parsing.** For the payloads of criteria 1, 2 and 4b, `json.loads` is never called with a string longer than `MAX_MESSAGE_BYTES` (spy/monkeypatch), mirroring the page's already-tested "the size check comes before `JSON.parse`" (T-0008 criterion 2, `tests/hud/protocol.test.mjs`).
4. **Both sides land on the same boundary (R6).** With `prefix = '{"type":"astra.transcript","turn_id":"t","text":"'` (49 bytes) and `suffix = '"}'` (2 bytes): (a) `"x" * 8_388_557` → total exactly 8,388,608 bytes → `astra` / `astra.transcript` in Python **and** `{kind:"astra"}` in `hud/src/protocol.js`; (b) `"x" * 8_388_558` → 8,388,609 bytes → `malformed` on both. Rows 4a and 4b are corpus rows, so one fixture drives both test modules.
5. **`decode` is still total (R3).** `decode(prefix + "\ud800" * 3_000_000 + suffix)` returns `Malformed` (`"not utf-8"` in `.error`) and does **not** raise; the existing Hypothesis properties `test_decode_never_raises_on_arbitrary_bytes` and its `st.text` sibling in `tests/contract/test_protocol_codec.py` still pass unchanged. docs/03 §3; `codec.py` module docstring ("the Conductor answers with `astra.error` and never a crash").
6. **Negative — nothing under the limit changes.** Every pre-existing row of `decode_corpus.jsonl` and every case in `tests/contract/test_protocol_codec.py` keeps its outcome and its `.type`; in particular a *short* `str` containing a lone surrogate (`'{"type":"astra.transcript","turn_id":"t","text":"\ud800"}'`) still decodes to the same typed message it does today and must **not** become `Malformed` (a fix that encodes eagerly on every message fails here); `encode()` is unchanged; `MAX_MESSAGE_BYTES` keeps the value `8 * 1024 * 1024` (`tests/unit/test_hud_constants_parity.py` compares it with the page).
