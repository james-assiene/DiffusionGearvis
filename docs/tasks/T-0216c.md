## Goal

A typed `astra.text` of `"a\ud800 hi"` (a lone UTF-16 surrogate; a browser's `JSON.stringify` emits such escapes for broken text, e.g. a pasted half emoji) decodes fine, but everything downstream that encodes it to UTF-8 breaks:
- the echo `astra.transcript`: `codec.encode` raises in `HudServer.publish` (`hud_server.py:~1125`), the `hud-writer` task dies (`_write`, `~1075`), and that page receives nothing for the rest of the session; a reloaded page stalls too, because the journal replays the transcript;
- likely also the LLM request body (`httpx` JSON) and the memory store (`sqlite3`), which both raise `UnicodeEncodeError` on such text.

Fix it at the one entry point: after `json.loads` in `contracts/codec.py` `decode`, every lone surrogate (U+D800–U+DFFF not part of a valid pair; after `json.loads` any surrogate code point in a Python `str` is lone) in any string of the decoded value, keys included, is replaced with U+FFFD. Nothing downstream ever sees one.

## Acceptance criteria

1. `decode` of a frame containing a lone surrogate (as a JSON `\ud800` escape) in any string, at any position or nesting depth, in a value or a key, returns the same message type it would for the text with U+FFFD in its place. Valid surrogate pairs (`😀` → 😀) are untouched.
2. End to end on a real loopback socket (the rig `served` + `HudClient`): a typed `astra.text` `"a\ud800 hi"` gets its `astra.transcript` echo (with U+FFFD), the turn runs, a second turn's messages still arrive, and a reloaded page gets its full hello reply.
3. The fake LLM request for that turn and any memory write carry the replaced text, and nothing raises.
4. Negative: any frame without a lone surrogate decodes byte-for-byte as today (same objects; the existing codec contract tests and T-0216 rows stay green). Encode is unchanged. The replacement adds no measurable cost to a normal frame (no second walk when the raw text has no surrogate escape: check the raw string first, case-insensitively, for `\ud8`–`\udf`).
