# T-0049 — `astra up` tells the truth about what it started

**Status:** done (merged at 005d4fe; status corrected 2026-10-23 from 'in progress', T-0147 audit: no implementation in flight) · earlier: in progress 2026-09-16 — **group A merged**; **group B** tests activated at this commit (`cli.py` freed when T-0045 merged), implementer next; group C is a `/launch` run the human invokes · three groups, ordered (A → B → C) · **Blast radius:** group A MEDIUM (one reviewer), group B **HIGH** (two reviewers: the verb that can stop a running engine), group C is a `/launch` run, not code · **Origin:** the live finding of 2026-09-16 (PROGRESS, "Live finding 2026-09-16"), reproduced and extended by the planner against the box at 3e34937 · **Depends on:** T-0033 (built `up`/`down`/`status`; its criteria 10–15 and rulings A11/A14–A16 are preserved, not replaced), T-0041 (budgets + log tail) · **Blocks:** T-0048 group B (the KV-pool bench) · **Ownership:** group B needs `local_astra/cli.py`, which T-0043 group A and T-0045 both claim — see *Ordering and ownership*.

## Goal

`astra up --profile lean` run against a box that was already serving printed `started` for all three services and then `ok` for all three, while two of the three starts had failed: the recorded pids were vllm 3574540 (dead), stt 3574545 (dead), tts 3574555 (alive); `logs/stt.log` carries `Conflict. The container name "/astra-stt" is already in use by container 61f0d405…`; and `docker ps` shows the containers actually answering the health probe are the originals, up two hours. Three separate defects compose into that lie: `cli.up` (cli.py:139-152) runs every command in the start plan unconditionally with no pre-check and no idempotence; the launcher's non-zero exit is never read although the CLI is still its parent (`supervisor.Handle` keeps the pid and drops the `Popen`, so the `isinstance(handle, int)` guard at cli.py:148 cannot fire); and the health probe answers for *any* instance on the port, so a stale one certifies a start that never happened — after which the pid files are overwritten with dead launcher pids, which is also why `astra status` calls a healthy containerised service "not running (stale pid file)". After this task a start reports success only when *this* invocation produced a *new*, healthy instance whose identity it can name; a service that is already running is skipped out loud with its identity and age rather than started over it; a service that is running from a configuration different from the one on disk is a refusal, not a skip; and `--restart` is how you deliberately reboot one. This is a prerequisite for T-0048 group B: that task's whole purpose is to reboot the engine at a 2.5 GiB KV pool and measure it, and today's `up` would silently no-op against the 4 GiB engine while the bench reported the new number — an unattributable number that looks like a success, which is the failure CLAUDE.md exists to prevent.

This is not a one-sentence diff and the protocol is not skipped: it changes what a start *means*, touches the verb that controls GPU services, and adds a flag that can stop a live engine.

## Design rulings (the four questions, answered with the trade-off)

**D1 — what `up` does about an already-healthy service: skip it loudly, and refuse when the configuration has drifted.** Three outcomes per service, decided *before* anything is spawned: not healthy → START; healthy **and** provenance matches (this CLI's state record names the live instance, and the service script's content digest is unchanged since that record was written) → **SKIP**, printed as `already running` with pid/container id and the age, exit 0; healthy but provenance is missing, stale, or the script digest differs → **CONFLICT**, nothing is started, exit non-zero, with the remedy in the row. Rejected alternatives and why: *refuse the whole command* makes `up` useless in its most common case (the human's arrival, where one or two services survived) and trains people to `--force` everything; *restart by default* turns an idle `astra up` into a 130 s cold engine start and would drop the engine under a live session. The brief's worry — "a caller who has just changed a service's configuration wants the opposite of a skip" — is answered by the CONFLICT branch rather than by a flag the caller must remember: T-0048 group B edits `services/vllm.sh`, the digest changes, the skip refuses itself. `--restart vllm` (or `--restart all`) is the deliberate form and exists because T-0048 needs to reboot exactly one service without stopping STT and TTS.

**D2 — how a start failure becomes visible: the launcher's own exit status first, then liveness, then newness; the log only ever explains.** Ranked by what can be fooled. (i) The launcher's exit code cannot be fooled by a stale healthy service and needs no new machinery — the CLI is the parent; `Handle` must carry the `Popen` (or a `returncode()` callable) and `up` must poll it. Every `services/*.sh` ends in `exec` on a foreground server, so *any* exit inside the settle window is a failure, whatever the code. (ii) Liveness at the end of a short settle window catches a launcher that hangs and dies without a status we waited for. (iii) Newness (D4) catches the case where the launcher exits 0 but nothing new is serving. (iv) `supervisor.log_tail` (T-0041 criterion 3) is quoted in the FAILED row as the explanation and is **never** the detector: matching known failure strings is a blacklist that fails open on the next failure mode — the docker Conflict line would have been caught, "address already in use" from the engine would not. A launch-script-level duplicate refusal is also rejected as the mechanism: `services/stt.sh` and `services/vllm.sh` belong to T-0048, a shell-level refusal cannot be exercised in the fast suite, and it would still leave `up` reporting success for the service it skipped.

**D3 — tracking a containerised service: the state file names the handle, the right authority answers for its liveness.** The pid file becomes an identity record — `kind` (process | container), pid, `/proc` start time, argv, the service script's digest, and for containers the `container_name` and the `container_id` resolved immediately after the start. That is not a second source of truth about what is running: the record only says *what this CLI started*; whether it still runs is asked of `/proc` for a host process and of `docker inspect` for a container. A container whose name is unknown (the engine today: `services/vllm.sh` passes no `--name`, so docker generated `exciting_maxwell`) degrades to `kind=process` with the limitation printed in the row — never a crash, never a guess by image ancestry, which would claim containers this CLI did not start. Adding `--name astra-vllm` is T-0048's edit to make; this task's code must already use it the day it lands.

**D4 — a start must be verifiably new, and the cheap honest handle is a start time.** Take a reference point before spawning (wall clock, plus the pre-existing container id when the name is known); after the service reports healthy, read the instance's own start time — `/proc/<pid>/stat` field 22 for a host process (`supervisor.start_time_of` already does exactly this for `down`) and `docker inspect -f '{{.State.StartedAt}}'` / a changed `.Id` for a named container. An instance whose start time precedes the attempt is NOT-NEW: a failure, never an `ok`. An engine boot identifier was considered and rejected: vLLM exposes no stable boot id on a free endpoint, so it would mean scraping the log or an inference-path call, and `astra doctor`/`up` must stay body-free status polls to keep costing nothing (`.claude/rules/gpu-services.md`). Honesty limit, stated in the row rather than papered over: newness is asserted **only for services this invocation started**; a SKIP row claims `already running since <t>`, which is all it knows.

## Acceptance criteria

Each is checkable in the fast suite with no GPU and no route off the box, except criterion 15 (`/launch`, group C) and criterion 16 (orchestrator).

### Group A — the decision and the supervisor primitives

1. **The live failure cannot report success (the reproduction row).** Given a probe that reports the service healthy both before and after, and a launcher that exits non-zero within the settle window having written the docker `Conflict. The container name "/astra-stt" is already in use…` line to its log, `supervisor.start_service("stt", …)` returns a FAILED outcome whose message names the exit status and quotes that log line, and the pre-existing state record for `stt` is **byte-identical** afterwards. *Negative, and the whole point:* no branch of that outcome is `ok`/`started`, and the healthy probe result does not appear anywhere in the decision to call it started. Satisfies the live finding; docs/02 §6 ("startup order is enforced by health checks") is strengthened here to *health plus identity*.
2. **The three-way decision is pure.** `service_state.decide(observation) -> Decision` with `action ∈ {START, SKIP, CONFLICT}` and a reason string, where `observation` carries the health result, the state record (or its absence), the live identity, and the current script digest. No I/O, no clock, no subprocess: a test monkeypatches `subprocess.run`, `socket.socket` and `time.time` to raise. Same input twice → identical `Decision` (T-0033 criterion 1's purity discipline, applied to the start half).
3. **A start is verified new.** A START whose service becomes healthy but whose instance start time is **not** strictly after the attempt reference is reported NOT-NEW and is a failure. *Adversarial:* a stub that is healthy before and after with an unchanged `/proc` start time (the stale-instance case that today's probe certifies) must produce a non-`ok` outcome; mutating the newness comparison to `>=`-on-equal or deleting it must turn this row red.
4. **The launcher's exit status is observed.** `Handle` exposes the child's return code; a launcher that has exited by the end of the settle window is FAILED with its code, *whatever* the code — the scripts all `exec` a foreground server, so exiting at all is the failure. *Negative:* a launcher still alive at the end of the window is never called failed on that ground alone, and the settle wait never blocks past its window (criterion in *Regime*).
5. **The state record replaces the bare pid file, without breaking the files already on disk.** A versioned record: `{version, name, kind, pid, start_time, argv, script_digest, container_name, container_id, started_at}`. Written **only after** the start is verified (criteria 3 and 4), so a failed start leaves the previous record intact (criterion 1). *Negative, concrete:* the three T-0033-shape files currently in `.git/local_astra/run/` (`{"pid", "argv", "start_time"}`) are still read by `supervisor.read_pid_file`/`stop`/`pid_files` with their T-0033 behaviour unchanged — a test feeds exactly that JSON shape and asserts the T-0033 rows (stale pid, reused pid, exec'd argv) still pass.
6. **Containerised liveness is asked of the right authority.** For `kind=container`, liveness and start time come from `docker inspect` of the recorded **id** (not the image, never `docker ps | grep`), with the `sg docker -c` retry on a permission-denied socket (the same fallback `services/stt.sh` documents and `preflight._docker` implements). An unresolvable container name — the engine today — degrades to `kind=process` with `container=unknown (services/vllm.sh passes no --name)` in the row. *Negative:* no code path stops, removes or renames a container it did not record.
7. **Configuration drift is a refusal, not a skip.** A healthy service whose recorded `script_digest` differs from the digest of the service script as it is on disk now yields CONFLICT with both digests named and `--restart <name>` as the remedy. This is T-0048 group B's case in the fast suite: a test edits a copy of a service script between the recorded start and the new `up` and asserts the service is not skipped and not silently restarted.
8. **Unknown provenance is a refusal.** Healthy, but no state record names the live instance (record missing, or its pid/container id is gone while the port still answers) → CONFLICT naming what is answering the port and saying plainly that `astra down` will not stop it. *Adversarial:* this is the shape the box was in when the human ran the command; the row must not be a PASS and must not attempt a start.
9. **Nothing here spends GPU time or leaves loopback.** The pre-check reuses `supervisor.check_service`; no new endpoint, no request body, no inference path (a static test over the module source, as T-0033 criterion 3 does). `astra up` therefore stays a *routine service start* under `.claude/rules/gpu-services.md` — clean tree, no `/launch` token — and nothing in this task may change that classification or touch `.claude/hooks/`.

### Group B — the verbs

10. **`up` reports per service what actually happened.** One row per service drawn from the decision: `started` (only when verified new and healthy, carrying pid, start time and container id when known), `already running` (with identity and age), `CONFLICT`, `FAILED`. Exit non-zero iff any row is CONFLICT, FAILED or NOT-NEW; all-SKIP exits 0. The final health table stays the shared renderer `status` uses (T-0033 criterion 14, ruling A14's printed budget unchanged).
11. **`--restart` is the deliberate reboot, and it is the only way `up` signals anything.** `--restart all` or `--restart vllm,stt` stops the named services through the existing `supervisor.stop` identity rules (T-0033 ruling A11, A16's no-SIGKILL) and then starts and verifies them per criteria 3–4. A restart whose stop reports `still_running` does **not** proceed to start and does not report success. *Negative, the mutation the reviewer must run:* without `--restart`, `up` sends no signal to anything and removes no state file — flip SKIP to stop-then-start and the row goes red. (Rationale: an `astra up` that reboots a live engine mid-session is a worse bug than the one being fixed.)
12. **`status` stops lying about containerised services.** A service whose record is `kind=container` and whose container is running is reported running, naming the handle it checked; a record whose handle is gone while the endpoint answers is reported as such ("healthy, but not the instance this CLI started"). *Negative:* `status` still starts nothing, signals nothing and writes nothing.
13. **Regression fence.** `astra up --dry-run` output is **byte-identical** to today's (plan lines then `then probe …`); no probe targets a non-loopback URL; `up` still downloads nothing; nothing is written under `artifacts/`; `astra session`, `astra config`, `astra doctor` and `astra down` behave exactly as they do today (T-0033 criteria 13, 15 and T-0041 criterion 3 re-asserted by their existing tests passing unchanged).
14. **`services/README.md` is true again.** Documents: skip-when-healthy, the CONFLICT cases and their remedies, what "verified new" means and what it does *not* claim for a skipped service, `--restart`, and the engine's missing `--name` limitation with the pointer to T-0048. *Negative:* the paragraph T-0033 ruling A17 added about `down` (start time decides; exec'd scripts are stopped; a reused pid is never signalled) is unchanged, byte for byte.

### Group C — the live proof (`/launch`, human present)

Then, after the originals are stopped by hand (`docker stop astra-stt`, the engine container by id — these are the human's commands; `astra down` cannot stop them because their records were clobbered on 2026-09-16), `astra up` starts all three with identity in each row; an immediate second `astra up` prints three `already running` rows and exits 0; `astra up --restart vllm` shows a different container id / later start time for the engine and leaves the STT and TTS pids untouched. ## Implementation notes

- Shape: *observe → decide → act → verify → record*. `service_state.decide` is the pure middle and must stay free of I/O (criterion 2 is aimed there); `supervisor` does the observing, acting and recording; `cli` only renders and turns rows into an exit code. Resist putting any of the decision in `cli.py`: that is where today's bug lives.
- `start_new_session=True` does **not** sever parenthood — keep it (T-0033 criterion 10's Ctrl-C property depends on it) and additionally retain the `Popen` in `Handle` so `poll()` is available. Do not reach for `os.waitpid` on a pid you did not father; `_await_exit` already handles both cases and is the model to follow.
- The settle window must be a poll loop (≈50 ms granularity) against the window, never a flat `sleep`: a launcher that dies in 40 ms should be reported in 40 ms, and T-0033 criterion 10's "up returns fast" bound still applies to the happy path.
- `script_digest`: a sha256 over the service script's bytes is enough and is cheap. Do **not** try to reconstruct the engine's intended argv by running `services/vllm.sh` under `ASTRA_DRY_RUN=1` from the CLI — it is T-0048's file, and an agent running it from a Bash call trips `guard_bash.sh`'s engine-start path trigger. Note the digest's honest limit in the code: it catches a changed *script*, not a changed environment variable (`ASTRA_PLUGIN`, `ASTRA_STT_CPU`); record the relevant env overrides in the state record alongside it if that is cheap, and say so in the row when it is not.
- `preflight._docker` is private and `preflight.py` is T-0045's: write the `sg docker -c` fallback locally in `supervisor.py` (≈8 lines) and say in the docstring that the duplication is deliberate and that consolidation is a later task. The unit row for criterion 6 pins the fallback shape so the two copies cannot drift silently.
- `astra up` must remain a *routine service start* under `.claude/rules/gpu-services.md` (clean tree, no token, no Runs entry). Nothing added here may make it match the engine-start or measurement patterns, and `.claude/hooks/guard_bash.sh` is not touched.
- Every probe stays a body-free `GET` on a loopback URL derived from `config.Services` (T-0033 criterion 3); `docker inspect` of a recorded id is a local socket call, not network egress — the zero-non-loopback-sockets test must still pass untouched (docs/02 §9, docs/03 E8).
- mypy `--strict` on `local_astra/`; the record types are frozen dataclasses, not `contracts/` Pydantic models (T-0033's precedent — this is not a wire format). No new dependency.
- Keep the FAILED-row renderer shared between `up` and `status` (T-0033 criterion 14); a second wording is a second truth.
- Landmine from the live finding, worth repeating in a comment: the pid file must be written *after* verification. A record written on spawn is exactly what destroyed the provenance of the still-serving containers on 2026-09-16 and is what made `astra down` unable to stop them.

## Regime

No GPU, no network, no PipeWire for anything in groups A and B. Numbers are bounds, not performance claims.

- **Settle window.** `SETTLE_S` = 1.0 s default; a launcher exiting at ~40 ms is reported in < 250 ms wall (`time.monotonic`), n = 5 in one test, no seed. Fast suite, `make fast-parallel` (`-n 8 --dist loadfile`, 60 s budget), profile `lean`, `astra.toml` defaults, probe stubbed.
- **Happy path — amended by ruling B4, do not read the original bound.** One settle window per **started** service, serially: `up` over
  a three-service plan returns in < 1.0 s + (services actually started) x `SETTLE_S`. The windows are deliberately **not** overlapped:
  overlapping means spawning the speech services before the engine answers, and docs/02 section 6 makes startup order a health-check
  ordering rather than a timer, so it would trade a correctness property for about two seconds. The half that protects the human is
  pinned separately and is the one that matters: **a skip pays no window at all**, so `up` against an already-running box still
  returns in < 1.0 s (n = 3, the shipped default window). Both rows use the default, which closes ruling A17's second half — no happy
  path had ever exercised it. T-0033 criterion 10's bound inherits this amendment.
- **Group C (criterion 15).** Box `gpu-box`, profile `lean`, versions from `services/versions.lock` at the run's SHA (KV pool as committed — if T-0048's 2.5 GiB edit has landed, say so), STT device read from the container argv, n = 1, seed n/a, clean tree, loopback only. No latency figure is produced and none may be quoted from it.

## Ambiguities for the human

1. **Flag surface.** `--restart [all|names]` as specified, or only `astra down && astra up`? Recommendation: the flag, because T-0048 group B must reboot the engine alone while STT and TTS stay up. A `--force` alias is deliberately *not* proposed: the CONFLICT rows each name their own remedy.
2. **Skip-by-default vs refuse-by-default** (D1). Recommendation: skip, with CONFLICT on drift or unknown provenance. Say so if you would rather `up` refuse outright whenever anything is already running.
3. **`--name astra-vllm` in `services/vllm.sh`.** Needed to close criterion 6 for the engine; the file is T-0048's. - **A2 (ordering, decided).** Group A is startable now — `service_state.py` is new and `supervisor.py` is unclaimed. Group B needs

- **A18 (minor, folds into A13's fix).** Container start times are compared as **strings**, and Go trims trailing zeros from its timestamp
  format, so lexicographic order is not time order when the fractional digits differ. Only reachable when the id is unchanged, which is
  what `--restart` will produce. Parsing to a datetime for the wall-clock arm removes it.
- **A19 (correcting my own A13: the clock is the primary arm, not the fallback).** The test-author asked the right question and my wording
  ("so the stale case is double-guarded") was ambiguous enough to be read either way. Settling it against **D4 as written**, which the code
  must follow: *"Take a reference point before spawning (**wall clock**, plus the pre-existing container id when the name is known) … An
  instance whose start time precedes the attempt is NOT-NEW."* So:
  **the comparison of the instance's own start time against `attempt_at` is the primary and always-required arm**, and the changed
  container id is *supplementary evidence*, not the thing being compared. Both come from the same host clock — the daemon's `StartedAt` is
  stamped by the same machine — so there is no skew argument for preferring the id.
  Two consequences. **(a)** A13's hole closes on the clock arm alone: when the pre-spawn read fails, the two-hour-old container is still
  older than `attempt_at`, so it is NOT-NEW without needing the snapshot at all. That is simpler and stronger than making the clock a
  fallback. **(b)** The fixture must move **again**: a container this invocation started necessarily has `StartedAt` **after**
  `attempt_at`, so anchoring the new container 30 s in the *past* models something that cannot happen on the happy path and forces the
  weaker snapshot-primary design. Anchor it after the attempt instead, computed at spawn time.
  What still catches the mistake A10 found? Not the happy-path row — the snapshot-only implementation and the clock implementation agree
  there. It is **A13's new row**: a snapshot-only implementation has nothing to compare when the read fails, and stays red. That is the
  honest discriminator, and it does not expire.
  **Honesty limit, unchanged and already documented:** a container somebody *else* started inside the window passes both arms. Neither the
  id nor the clock can tell "started after my reference" from "started by me".
- **A20 (A19 accepted by the test-author, with a parsing landmine the implementer must not walk into).** The daemon's `StartedAt` carries
  **nine** fractional digits and `datetime.fromisoformat` takes at most six on 3.11, so the parse must truncate — and truncating to
  **seconds** would call a container started in the same second as the attempt NOT-NEW, a false failure on a *fast* start. Parse to
  microseconds. The happy-path row was deliberately built not to depend on that choice (a 1.2 s pre-spawn delay puts a clear second
  between the attempt and the stamp), so a wrong precision shows up as a real defect rather than as a flaky row. A19 also retires A18: the
  string comparison disappears once the primary arm parses to a datetime.
