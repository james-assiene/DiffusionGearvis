# T-0057 — the audio writer thread dies with the test that made it, and the suite says so out loud

**Status:** merged 2026-09-17 (verified on a13d0fe: 2380 passed, zero leaked threads, switch fence 0.665 subset / 0.784 suite; ruling A21) — earlier: in progress 2026-09-17 — tests written red at ce6734e; implementer dispatched. Planned 2026-09-16 · **Blast radius:** high (audio path — two reviewers per CLAUDE.md) ·
**Origin:** T-0049 ruling B14, sharpened by B18; queued follow-up 7 in `PROGRESS.md`; second independent
sighting by T-0051's implementer (`PytestUnhandledThreadExceptionWarning: Exception in thread

## Goal

`PipeWireAudioIO` starts a daemon thread called `astra-audio-writer` on the first `play()` and has no way
to stop it: the thread's only exit is `WRITER_IDLE_EXIT_S = 2.0` seconds of idleness, and nothing joins it.
Every unit test that plays a single tone therefore hands the *next* test a live thread that keeps reading
the device and the clock for two more seconds. Measured on this tree (details in §Regime): the thread
outlives its test by **2.00 s** and makes **7 981** reads of one device method in that window — roughly
**eight times** the ~1000 clock reads T-0049 ruling B18 estimated, because the run is never cleared so the
loop stays on the 0.2 ms *active* poll rather than the 2 ms idle poll. **48 of 66 rows** in four audio
modules leak one, and one Hypothesis row leaks **29 at once**. Today that is a warning in one run out of
three; the moment any row patches a clock globally, or a fake clock counts or advances on read, it becomes
a wrong **pass**. This task gives the module an explicit stop seam, gives the suite a teardown guard that
**fails the test that leaked**, by name, instead of warning, and records a before/after measurement so the
next person can tell whether it worked.

**What this task deliberately does not claim, now measured rather than argued.** I was asked to find out
whether the leaked thread and the 94 seconds of the serial suite that are neither user nor system time are
the same fact. **They are not, and the counterfactual was run over the whole suite in both arms.** Removing
the thread's lifetime **halves the suite's voluntary context switches** (1 577 775 → 798 218, −49.4 %) and
**recovers no wall time at all** (the matched four-module comparison gives 3.0 s of 34; the full-suite arms
give none). So the thread owns the context-switch signature the orchestrator spotted, and it owns
essentially none of the 94 seconds. A third measurement, taken on the way, reframes where those seconds
are: `/usr/bin/time` counts **child** CPU as user time, and the pytest process's own CPU during the rows is
only **26.3 s of 211.4 s of row wall** — so roughly **91 s of the 118 s of reported CPU belongs to
subprocesses the suite launches**, not to pytest. The gap is named, with a per-module ranking, in
§Implementation notes. Nothing here raises the serial ceiling; that stays T-0050's question and is a
negative criterion below.

## Acceptance criteria

Every criterion is checkable by a test or by a stated command. Criteria 1-4 are the durable half and stand
whatever the timing turns out to be; 5-8 are the negatives.

1. **A thread that outlives its test fails that test, loudly and by name.** An autouse teardown in
   `tests/conftest.py` compares the live thread set after each test against the set before it and fails
   with an `AssertionError` naming (a) the nodeid of the test that created the thread and (b) the thread's
   name, for any surviving thread whose name begins `astra-`. It is a failed row, not a warning, not a
   `PytestUnhandledThreadExceptionWarning`, not a summary line. *(Queued follow-up 7; T-0049 rulings
   B14/B18; `.claude/rules/tests.md` "no asserting current behaviour" — a warning nobody reads is the
   current behaviour.)*

2. **The guard is not too wide** — the other half of the `.claude/rules/tests.md` rule that a guard needs a
   row for being too wide as well as one for being absent. Threads alive *before* the test starts are never
   attributed to it; the guard tolerates the interpreter's own threads (`MainThread`, `asyncio_0`-style
   default-executor threads, `pytest-xdist` workers, `ThreadPoolExecutor-*`), so `make fast-parallel`
   produces zero new failures from this criterion. A row proves both directions: one leaking thread is
   caught, one pre-existing `astra-`named thread created by an earlier test is *not* re-reported.

3. **`PipeWireAudioIO` can be stopped, and stopping it is bounded and idempotent.** The playback half gains
   an explicit stop seam (name is the implementer's; `close()` is the house precedent — `HudStaticServer.close()`,
   T-0040) that (a) causes `_writer_loop` to return and joins the thread within **100 ms** measured on the
   fake device, (b) cancels or awaits the `_feed_loop` feeder task so no asyncio task is left pending
   (`FEEDER_IDLE_EXIT_S = 5.0` today, and my probe found **3** live tasks at the end of a one-tone test),
   and (c) is safe to call twice, and safe to call on a module that never played. Architecture §4: nothing
   about `played_ms`, drain or underrun semantics may change to achieve this — see criterion 6.

4. **Zero leaked `astra-audio-writer` threads across the whole fast suite, measured.** With criteria 1 and
   3 in place, `uv run pytest tests/unit tests/contract -q -m "not gpu"` reports **0** failures from the
   criterion-1 guard across all 2315 rows, and the before/after of the two numbers below is recorded in the
   task file and in `PROGRESS.md` with its full regime:
   - *voluntary context switches for the serial run* — **before: 1 577 775 / 1 566 825** (two runs of mine)
     and **1 556 842** (the orchestrator's third run), all of them context and none of them a
     threshold. The fence (ruling A12): the after value is at most **0.85 × before** on the
     four-module subset and at most **0.90 × before** suite-wide, with the before **re-measured in
     the same session** as the after and the **load average** recorded beside both. Never an
     absolute count: the counter is rate × writer-alive time, so the same fix on the same tree
     measured 0.74, 0.62 and 0.65 at load averages 6 to 13. This is a regression fence, not a
     target; the gate the task is judged on is the load-independent one above, **zero leaked**
     `astra-` threads.
   - *wall clock for the serial run* — **before: 212.47 s / 214.02 s** (mine) / **212.37 s** (the

## Implementation notes

Constraints and landmines. The implementer designs the seam; none of this is a solution.

**Where the thread comes from.** `local_astra/conductor/audio_io.py`: `_ensure_writer()` (line ~495) starts
`threading.Thread(target=self._writer_loop, name="astra-audio-writer", daemon=True)` and is called from
`play()`, `resume()`, `mark_drain()` and twice inside `_feed()`. `_writer_loop()` (line ~504) is an
unconditional `while True` whose **only** exit is `time.monotonic() - idle_since > WRITER_IDLE_EXIT_S`
(`= 2.0`, line 72), and it sleeps `POLL_ACTIVE_S` (`0.0002`) when `self._run is not None`, otherwise
`POLL_IDLE_S` (`0.002`). There is no `close()`, no `stop()`, no `Event`, nothing joins it, and the class
has no lifecycle end at all for the playback half — `close_capture()` exists and closes only the capture
half. That absence is the defect; the 2 s constant is a symptom of it.

**Why B18's estimate of ~1000 reads was 8× low, and why it matters.** `_run` is cleared only by
`_end_run()` (a flush or a drain). A test that plays a tone and stops asserting never flushes, so after the
row ends `self._run is not None` is still true and the loop stays on the **0.2 ms** poll for the entire 2 s,
not the 2 ms one. Measured: **7 981** reads of one device method in 2.00 s. The wrong-pass window is
therefore eight times wider than the queued item claims, and the queued item should be corrected when this
lands.

**The second leak, which the thread guard will not catch.** `_ensure_feeder()` creates an asyncio task
running `_feed_loop()`, which exits only after `FEEDER_IDLE_EXIT_S = 5.0` seconds with an empty queue. My
probe found **3** live asyncio tasks at the end of a one-tone test. Criterion 3(b) covers it; criterion 1's
guard cannot, because a pending task is not a thread. Do not let a green thread guard stand in for it.

**A trap the probe walked into, recorded because the implementer will meet it.** When the feeder task's
coroutine raises after the test's event loop has moved on, the traceback surfaces as
`Task exception was never retrieved` at garbage-collection time — attached to *whatever* is running then.
That is very likely the mechanism behind the sighting T-0051's implementer named
(`PytestUnhandledThreadExceptionWarning: Exception in thread astra-audio-writer` appearing in one run and
not the next with identical code): an exception raised in a leaked worker is reported against an arbitrary
later point in the session. **I did not reproduce that exact warning**, so this is a hypothesis with a
mechanism, not a finding. Naming it here so the implementer does not chase it as a separate bug, and so
the reviewer knows it is unproven.

### The honest split: what the thread explains, and what it does not

I was asked not to assume the leaked thread and the 94 seconds are the same fact. **They are not.** The
counterfactual is in §Regime; the conclusion:

- **Proved, and this task fixes it.** The thread outlives its test by 2.00 s, makes ~4 000 device reads a
  second while doing so, and is left behind by **48 of 66** rows in four audio modules (65 threads; one
  Hypothesis row leaves 29). It is **85 %** of the voluntary context switches and **45 %** of the CPU in
  those modules. Those four modules alone produce **986 449** of the whole suite's **1 566 825** voluntary
  switches — **63 % of the suite's blocking, from 66 of 2 315 rows.** That is what the orchestrator's
  context-switch arithmetic was pointing at, and it is real.
- **Proved, and this task does not fix it.** Removing the thread's lifetime from those same four modules
  moves the wall from **34.05 s to 31.06 s** — 3.0 s, 8.8 %. Over the **whole suite** the same probe moves
  the wall from 212.47 s to 231.87 s, i.e. **no win at all** (that arm had 7 failures and a higher load
  average, so read it as "no measurable improvement", not as a regression). The whole-suite leak census
  explains why the subset number does not scale: only **54 rows of 2 393 leak a writer**, and 48 of them
  are in those four modules. So the thread explains **about 3 seconds of the 94, and plausibly none**, and
  **~91 seconds is somewhere else.** If this task lands and the serial suite still runs at ~212 s, that is
  the expected result, not a failed fix — which is precisely why criterion 4 gates the switch count and
  only *reports* the wall.
- **A third measurement that reframes the question, and that nobody has stated yet.** `/usr/bin/time`
  reports **child** CPU inside "User time" (verified directly: a parent whose own `time.process_time()`
  delta is 0.00 while a child burns 0.84 s is reported by GNU time as `user 0.84`). Measuring the pytest
  process's *own* CPU per row with `time.process_time()` gives **26.3 s across 211.4 s of row wall**. So
  the suite's reported 107.75 s of user time is roughly **27 s of pytest and ~91 s of subprocesses**, and
  the pytest process itself is idle about **88 %** of the run. "94 s is neither user nor system" is
  arithmetically right and slightly misleading: the honest statement is that **pytest computes for ~27 s
  of a 212 s run**, and everything else is either a child process or a wait.

### Contracts to respect

- **Architecture §4 and the T-0006 spec deltas.** `playback.drained` requires `mark_drain()` *and* the last
  sample; `played_ms` is the device's rendered position, never the write cursor; `played_text` comes from
  the committed `TtsSpeak.source`. A stop seam that ends a run, emits an event, or lets `_end_run` fire is a
  behaviour change, not a lifecycle change. Stopping the writer is **not** `flush()` and must emit no
  `PlaybackStopped`.
- **`.claude/rules/conductor.md`:** nothing on the event loop may block for more than 20 ms. Note the
  comment at `_writer_loop` (ruling A14): opening the stream takes tens of ms of PortAudio/ALSA and is
  deliberately done **inside** the thread. A stop seam that joins the thread *while holding `self._lock`*
  recreates exactly the stall that comment exists to prevent — the writer takes the same lock every pass.
  This is the most likely way to get a deadlock out of a two-line change.
- **`.claude/rules/tests.md`:** a guard needs a row for being too wide as well as one for being absent
  (criterion 2 is that row); do not mutate a blunt version of the ruling when checking coverage; a test
  double closes by delegation, not enumeration — the criterion-2 tolerance list is an enumeration and is
  the one place where that is unavoidable, so make it a *prefix* rule (`astra-`) plus an explicit
  before-set, not a list of allowed names.
- **Loopback rule:** nothing here opens a socket. The zero-non-loopback test must stay green.
- The thread stays `daemon=True`. Making it non-daemon to force a join at interpreter exit would hang
  `astra session` on Ctrl-C and collides with T-0040.

- **A8 (one edit outside the writer's lifecycle, justified by measurement).** `_feed_loop` now waits under `asyncio.timeout` rather than

  `wait_for` needs **four** scheduling hops to leave `all_tasks()`, under `asyncio.timeout` it needs **one**. Same idle-exit semantics — both

- **A9 (ruling A7 re-derived by measurement: it holds, and the gate cannot stand).** The conversion factor nobody had measured: a 0.2 ms
  `time.sleep` or `Event.wait` costs **exactly one voluntary context switch per iteration** with a real period of 250 µs (n = 20 000 per arm),
  so a live writer on the active poll costs about 4 000 switches a second. The afterlife ceiling a lifecycle-only seam can remove is therefore

- **A10 (BLOCKER, implementer: ruling A8's "identical semantics" was wrong, and the difference is an architecture §4 hang).** `asyncio.timeout`
  and `wait_for` agree on an empty queue and **differ at the deadline boundary**: an item enqueued in the same loop iteration as the idle
  deadline is recovered by `wait_for`, which re-checks the future after cancelling, and **left in the queue** by `asyncio.timeout`, which
  converts the cancellation at context exit. In situ on the real module, three of three: the feeder exits with one item still queued, the
  utterance is already in the run with `complete=False`, `_all_complete` is false for ever, and `mark_drain()` never produces
  `PlaybackDrained` — the turn machine stays in SPEAKING. A later `play()` in the same run heals it; the last or only utterance of a turn does
  not. Probability is one loop iteration in a five-second window, deterministic when hit, and **new**: `wait_for` did not have it. **Fix: on
  `TimeoutError`, if the queue is not empty, continue; else return.** Do not revert to `wait_for`: the one-hop claim is true (measured 1 versus
  4 on this interpreter) and reverting reddens the pending-task row.
