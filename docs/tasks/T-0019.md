# T-0019 — The Stop hook and the activate-then-implement window contradict each other

**Status:** merged 2026-09-14 (three reviews; third APPROVE on the implementation with 13/14 mutations red, the fourteenth pinned in aeab053; 25 tests)· **Blast radius:** low (a hook and one line of docs/09) · **Depends on:** none

## Goal
`.claude/hooks/stop_fast_suite.sh` stops demanding a green fast suite in the one state the
protocol itself prescribes as red: between a test-author removing `pending` markers and the
implementer landing the code. After this task the hook tolerates failures that are **confined to
modules whose task is `in progress`**, and fails on anything else — so it still catches a
regression in merged code, which is what it exists for.

## Why (observed 2026-09-13, eight times in one session)
CLAUDE.md: acceptance tests are written before the implementation and held green as strict xfail
by `pending(task=…)`; "the test-author removes the marker when `/implement T-NNNN` starts". That
window — markers removed, code not yet landed — is legitimate, can last hours, and is exactly
when the orchestrator most needs to end turns to dispatch the next agent. The hook fires on every
one of those turns with `Fix or report before finishing`. Re-adding markers is forbidden ("never
add `pending` to make a red test green"), so the only compliant response is to report the same
thing again. Tonight that was: 89 failures, all in `test_speech_gate.py` (43), `test_llm_client_segments.py`
(18), `test_ui_gate.py` (16), `test_prompt_builder.py` (12) — four tasks, four implementers in
flight, zero regressions — reported eight times.

A gate that fires on the prescribed state trains its audience to skim it. That is the same
failure T-0016 documents for `guard_bash.sh`: a check that cries wolf loses the one time it is
right.

## Acceptance criteria
1. The hook classifies each failing test by module and looks the module up in
   `docs/tasks/*.md` "Tests to write" / `tests/` ownership: a failure in a module named by a task
   whose `**Status:**` is `in progress` is **expected**; any other failure is a **regression**.
2. With only expected failures, the hook exits 0 and prints one line per in-progress task:
   `expected: T-0004 (43 failing in tests/unit/test_speech_gate.py, implementer pending)` — so the
   red is visible and attributed, not hidden.
3. With any regression, the hook fails exactly as today, and the regression is listed **first**,
   separated from the expected block, so it is not buried under 43 lines of expected noise.
4. A test module with failures that no in-progress task claims is a regression (the safe default).
   A module claimed by a task whose status is `planned` (markers still on) and yet failing is also
   a regression — that means someone removed markers without moving the status, and the hook
   should say so in those words.
5. The status transition is enforced the other way too: `scripts/check_pending.py` warns when a
   task is `in progress` and still has `pending` markers, or `planned` and has none — the two
   halves of the mechanism must agree.
6. `docs/09-agent-workflow.md` gains one paragraph naming the window and the rule, so the next
   person reading a red suite mid-task knows it is prescribed and where to look.
7. **Negative:** the hook never reads `pending` markers to decide tolerance — that would let
   "mark it pending" become a way to silence a real failure, which CLAUDE.md forbids. Tolerance
   comes only from the task file's declared status and ownership.

## Rulings after tests (2026-09-13)
**A1 — ownership is a whole-file scan of `docs/tasks/*.md`:** a test module is claimed by a task
if the task file names it anywhere (Tests to write, Evidence required, prose); `tests/` never
appears under Owned files by convention (`docs/tasks/README.md`), so a section-scoped reading
would leave merged tasks' modules unclaimed.
**A2 — the regression listing contains the word "regression"**, the expected block the literal
`expected: T-NNNN (N failing in <module>, implementer pending)`, both in the same stream; `-x`
goes (the counts are real). **A3 —** `check_pending.py` warns (exit 0) on the two mismatch
directions; a `planned` task whose modules do not exist yet is silent. **A4 —** the docs/09
paragraph (criterion 6) is prose; no test. **A5 — the seam:** the hook keeps invoking the suite via
`uv run pytest tests/unit tests/contract …` from the git toplevel; any helper lives under
`.claude/hooks/` or `scripts/`.

## Rulings after review (2026-09-13, verdict REVISE both)
**A6 —** a pytest collection abort (`ERROR <path>` with no `::`, or an `Interrupted:` banner) is a
regression whatever the module's owner: nothing ran, so no status can excuse it. The pre-T-0019
hook blocked on it; the classifier must too. **A7 —** the precedence rule (done > other > in
progress > planned) is load-bearing and gets its own test: an in-progress task that merely
mentions a merged module cannot excuse that module's failure (T-0019.md itself names
`test_speech_gate.py`). **A8 —** `check_pending`'s planned-without-markers warning considers only
`test_*.py` modules (fakes/conftests named in ownership prose carry no tests). **A9 —** criterion 2
reads "one line per (in-progress task, module)"; the mandated format string already says so.
**Tests to write (this task's own modules):** `tests/unit/test_stop_hook.py`,
`tests/unit/test_check_pending.py`.
**A10 (after the re-review) — module granularity, resolved by claim strength.** A module amended
by an in-progress task (T-0026 → `test_guard_bash_hook.py`, T-0025 → `test_hud_constants_parity.py`)
is red by design, but "done > in progress" handed it to the merged creator and the hook blocked the
prescribed window on the live tree. Ruling: an in-progress task that names the module under
`## Owned files` or `## Tests to write` (a *structured* claim) outranks a merged task's claim; a
mention in prose never outranks anything. So A7's motivating case (T-0019.md mentioning
`test_speech_gate.py` in prose) still resolves to T-0004, and the precedence test must use a
prose-only mention for its in-progress task, with a second case where the structured claim wins.
**A11 —** the `Interrupted:` banner is matched at line start (captured test output cannot fake a
collection abort). **A12 —** the tolerated report stays on stdout (transcript-visible); the
blocking report on stderr. Owned files gain `.claude/hooks/classify_failures.py` (A5 helper).

- **A13 (2026-09-14, after the A11 pin).** The second alternative of the collection-abort pattern was a fixed-width prefix window (`^.{0,40}errors? during collection`), so a failing test that *quoted* the banner in its assertion message faked an abort depending on the column the phrase landed on. Both alternatives are now line-anchored (`^[!\s]*Interrupted:` and `^=+ .*errors? during collection`). Residual, accepted: a test that `print()`s the banner at line start puts it at line start in the captured-stdout section and still fakes an abort; A11 stands as written (line start is the signal), and the cost is one spurious block on a test nobody should write.
- **A14 (2026-09-14, third review; implementation approved, one test owed).** Two of the reviewer's non-blocking notes applied: the hook treats the classifier's report as meaningful only when it contains an `expected:`/`regression:` line (stderr chatter exiting 0 no longer lets a red turn finish), and `FAILED`/`ERROR` lines are matched at line start only (no `.strip()`), so quoted summary lines in captured output cannot inject phantom entries. The owed test pins A3's `exists()` filter, which survived deletion at 22/22.
