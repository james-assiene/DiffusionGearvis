## Goal
`.claude/hooks/guard_bash.sh` stops losing track of the program it is looking for the moment a
wrapper or an interpreter is given a flag that takes its argument as a separate token. Today
`nice -n 10 bash <harness>`, `sudo -u user bash <harness>`, `timeout -s KILL 600 bash <harness>`,
`env -u FOO bash <harness>`, `ionice -c 2 -n 7 bash <harness>`, `stdbuf -o 0 bash <harness>`,
`bash -euo pipefail <harness>` and `bash -o pipefail <harness>` all run a `scripts/gpu/` harness
with **no launch token and no dirty-tree check** — the T-0016 defect-A hole, reopened by an
ordinary spelling nobody thinks of as an evasion (`nice`, `timeout` and `set -euo pipefail` are
how a person bounds a long run). Alongside that: the over-block twin of ruling I10 gets a
regression pin (quoting a harness *path* in a commit message or a search pattern is still prose),
and the engine-start refusal stops demanding an obligation the rules file does not impose. All
verified on `main` @ aad95b0 with the sandbox from `tests/unit/test_guard_bash_hook.py`;
"ALLOWED"/"BLOCKED" below are measured, not predicted.

## Why (measured on main @ aad95b0, 2026-09-13)
`runs_gated()` peels wrappers by consuming tokens that start with `-`, taking two tokens only for
members of `VALUED` (`-m --module --with --python -p --project -C --directory --chdir --cwd`).
Every other flag consumes one token, so its *argument* becomes the candidate program: after
`nice -n`, the peel inspects `10`; after `bash -euo`, it inspects `pipefail`. Neither is a gated
path, so the verdict is "not gated" and the harness runs unreviewed. Probe output:

```
ALLOWED  nice -n 10 bash scripts/gpu/x3_prefix_cache.sh
ALLOWED  nice -n 10 scripts/gpu/x3_prefix_cache.sh
ALLOWED  sudo -u user bash scripts/gpu/x3_prefix_cache.sh
ALLOWED  timeout -s KILL 600 bash scripts/gpu/x3_prefix_cache.sh
ALLOWED  env -u FOO bash scripts/gpu/x3_prefix_cache.sh
ALLOWED  ionice -c 2 -n 7 bash scripts/gpu/x3_prefix_cache.sh
ALLOWED  stdbuf -o 0 bash scripts/gpu/x3_prefix_cache.sh
ALLOWED  bash -euo pipefail scripts/gpu/x3_prefix_cache.sh
ALLOWED  bash -o pipefail scripts/gpu/x3_prefix_cache.sh
ALLOWED  bash -o pipefail -e scripts/gpu/x3_prefix_cache.sh
BLOCKED  timeout -k 30 600 bash scripts/gpu/x3_prefix_cache.sh   (blocked by accident: -k eats
         nothing, then 30 and 600 are both swallowed as durations — must stay blocked)
```

The follow-up line in T-0016 proposed "add `-n -u -s -k -o` to `VALUED`, one line + four rows".
**That prescription is wrong as written and must not be implemented literally**, for two measured
reasons:

1. `VALUED` is consulted by *both* the wrapper peel and the interpreter flag loop, and the same
   letter means different things there. `-u` and `-s` take no argument in a shell (`nounset`,
   read-stdin). `bash -u <harness>` and `bash -s <harness>` are **BLOCKED today**; a global
   `VALUED` containing `-u`/`-s` makes both ALLOWED — the fix would open a second hole while
   closing the first. Same for `sudo -n` (non-interactive, no argument) versus `nice -n 10`.
2. The clustered form is the common one and exact membership never matches it: `-euo` is not
   `-o`, so `bash -euo pipefail <harness>` stays ALLOWED after the prescribed edit. The rows below
   pin the cluster, so a literal implementation fails this task.

The design question the implementer answers is therefore "which flags take a separate argument,
**for this program**", not "which flags take a separate argument".

## Acceptance criteria
Throughout, `<harness>` is a file under `scripts/gpu/` or `scripts/locked/`; "blocked" means exit
non-zero with no launch token in the sandbox, "allowed" means exit 0.

1. **A wrapper flag with a separate argument does not end the peel.** Each of these is blocked
   (T-0016 defect A; rules file "Where GPU-spending commands live", trigger class *Measurement*):
   `nice -n 10 bash <harness>`, `nice -n 10 <harness>`, `sudo -u user bash <harness>`,
   `timeout -s KILL 600 bash <harness>`, `env -u FOO bash <harness>`,
   `ionice -c 2 -n 7 bash <harness>`, `stdbuf -o 0 bash <harness>`.
2. **An interpreter flag with a separate argument does not end the peel**, including the clustered
   short-option form: `bash -euo pipefail <harness>`, `bash -o pipefail <harness>`,
   `bash -o pipefail -e <harness>` are blocked (same citation as 1; this is the half the T-0016
   follow-up prescription misses).
3. **Negative — a flag that takes no argument still must not swallow the program.**
   `bash -u <harness>`, `bash -s <harness>` and `sudo -n bash <harness>` are blocked today and
   stay blocked. Deleting the per-program distinction and using one flag set turns at least one of
   these green, so this criterion is the mutation guard on criteria 1–2.
4. **Negative — ruling I9 survives.** `bash -n <harness>`, `bash -en <harness>`,
   `nice -n 10 bash -n <harness>`, `nice -n 10 python3 -m py_compile <gpu-py-harness>`,
   `uv run ruff check <gpu-py-harness>`, `cat/sed/wc/git add` on a harness are all allowed
   (T-0016 I9, R4). The shell `-n` early return keeps precedence over any new flag handling.
5. **Negative — ruling D5 survives under a wrapper.** `nice -n 10 uv run python scripts/demo/ask.py
   'hi'` and `uv run --with mss python scripts/demo/ask.py --screen` stay allowed: the fix widens
   *where the program is found*, never *which directories are gated* (T-0016 D5).
6. **The over-block twin of I10 is pinned.** Naming a harness path inside prose is allowed with no
   token: `git commit -q -m "…bash <harness>…"`, `git log --oneline --grep 'bash <harness>'`,
   `rg -n '<harness>' docs/`, `echo "see <harness>" >> notes.md`, and the existing commit-message
   heredoc row. These pass on main today; the criterion is that they still pass after the change
   (T-0016 I10 says a quoted gated *path in a program position* is gated — this is the other
   direction, unpinned at merge, so nothing stops a future widening from re-blocking commit
   messages, which is defect B and the habit CLAUDE.md's "Observed mistakes" warns about).
7. **The engine-start refusal names only obligations the rules impose.** With no token,
   `vllm serve …` is blocked and the message names a `/launch` review and a clean tree but does
   **not** claim a `PROGRESS.md` *Runs* entry (`.claude/rules/gpu-services.md` attributes the
   *Runs* entry to the *Measurement* class; the *Engine starts* class needs "the same token and
   clean tree"). Ruling below: the **message** changes, not the spec — the rules file is owned by
   two open tasks (see Owned files) and inventing an obligation in a refusal is how a gate starts
   to look arbitrary.
8. **Negative — the D2/I12 split stays visible in the wording.** A routine start
   (`uv run astra up --profile lean`, `systemctl --user start astra-*`) on a dirty tree is refused
   with a message that names the dirty paths and mentions neither `/launch` nor a token; on a clean
   tree it is allowed with no token (T-0016 I12). Criterion 7 must not be satisfied by collapsing
   the two refusals into one sentence.
9. **Negative — nothing else regresses.** All 70 existing rows in
   `tests/unit/test_guard_bash_hook.py` stay green, `bash scripts/bootstrap.sh` still prints
   `hooks run and block an unapproved GPU command` (T-0016 criterion 4), and the non-GPU guards
   (destructive git, test silencing, implementer-push) are untouched.
10. **Negative — per-call cost unchanged.** `guard_bash.sh` still starts exactly **one** `python3`
    process of its own (the normaliser; `_lib.sh`'s `jf` accounts for the rest) and no new
    subprocess, network call or git invocation is added on the untriggered path. Median wall time
    over n=25 is within **2 ms** of the `main` baseline measured in the Regime section below
    (T-0016 criterion 6: the hook runs on every Bash call).

## Implementation notes
- **Read `docs/tasks/T-0016.md` end to end first.** The vocabulary (`WRAP`, `INTERP`, `SUB`,
  `VALUED`, `CHDIR`, `bare()`, `resolve_cd`, the `-c` payload exception, the `gated`/`scan`
  two-line protocol between the python normaliser and bash) is that task's, and every ruling
  D1–D5, I1–I12, R1–R4 is still binding. This task changes one thing: how the peel finds the
  program.
- **The contract to respect:** `VALUED` is read in two places with different semantics — the
  wrapper peel (`runs_gated`, first loop) and the interpreter flag loop. The fix belongs in that
  split, not in the shared list. A per-program mapping (`nice`/`ionice` → `-n`, `-c`; `sudo` →
  `-u -g -U -C -p -r -t`; `timeout` → `-s -k`; `env` → `-u -S`; `stdbuf` → `-i -o -e`; shells →
  `-o -O` including the clustered `-euo` form; `python` → `-m -c -X -W`) is one shape that
  satisfies criteria 1–4; the implementer picks the shape and states it in a comment. Whatever the
  shape, the unknown-flag default must stay "consumes one token" (fails closed — an unrecognised
  flag leaves the program where it is).
- **Order matters in the interpreter loop.** The `-c`/`-m` re-target and the shell `-n` early
  return currently run *before* the `VALUED` lookup. Keep that order: moving the `-n` return after
  a new cluster rule turns `bash -en <harness>` into a token demand and breaks I9.
- **Clustered short options** are the part the T-0016 follow-up line missed. `-euo` must be read as
  a group whose *last* letter decides whether the next token is an argument. `-en` must still hit
  the `-n` early return first.
- Optional, implementer's call, and if declined say so in this file rather than deleting anything:
  `bash -ec 'bash <harness>'` is ALLOWED today because the re-target test is exact membership in
  `("-m", "--module", "-c")` and `-ec` is not a member. Once cluster handling exists, a cluster
  ending in `c` re-targeting is nearly free. No test row is prescribed for it; if you take it,
  ask the test-author for one.
- **`ROLE=implementer` cannot edit `.claude/**` at all** — `.claude/hooks/protect_paths.sh` denies
  it before the owned-files check ever runs, so listing the hook under Owned files is necessary
  but not sufficient. Do this work from the main session (`ROLE=none`), or from a role that is
  permitted. **Do not "fix" this by loosening `protect_paths.sh`**: that file is out of scope and
  the restriction is deliberate.
- The hook must keep failing closed: if `python3` cannot normalise the command, the fallback is
  `gated=0` plus the raw command, i.e. the pre-T-0016 behaviour. Do not add a second fallback path.
- Probing beats reasoning here, and T-0016 says so from experience ("caught by probing the
  normaliser, not by the suite"). Drive the normaliser directly with a scratch script before
  running the suite; the rows above were produced that way.
- `.claude/rules/gpu-services.md` is **not** owned by this task. Anything you want to say about the
  residuals goes in the hook's comment header and in the *Deferred* section above.

## Rulings after the two reviews (2026-09-13)

(reviewer B found the branch had opened them). **A2 —** the `-n` early return runs before the

**A4 —** `sudo -n` is pinned *without* an interpreter (`sudo -n <h>`) — the interpreter form
cannot discriminate because the harness becomes `toks[0]` either way. **A5 —** the mandatory
"unknown wrapper flag consumes one token" default gets rows (`nice -5 <h>`, `nice --verbose
<h>`, `env --ignore-environment <h>`, `timeout --foreground <h>` BLOCKED). **A6 —** `xargs -I {}
bash <h>` / `xargs -n 1 bash <h>` now BLOCKED (tightening of a documented residual; noted for the
rules file when T-0014/T-0015 release it).
