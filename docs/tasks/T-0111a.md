# T-0111a — The tool-result loop: results go back to the model, which continues until it answers

**Status:** ruled 2026-10-17 (H-T111a-1…10 defaults approved) · **Blast radius:** high (turn machine, audio path, GPU probe); two reviewers on a1, a3 and a4 · **Umbrella:** T-0111 (H-T111a: loop first) · **Branches:** `T-0111a1-loop-machine`, `T-0111a2-loop-render`, `T-0111a3-loop-session`, `T-0111a4-loop-probe`

## Goal

Today a tool turn ends at its one call. The call is dry-run after the spoken prefix drains, and the turn closes (docs/02 §4 P1, P3; T-0080d settled default 6).

With `tool_loop = on`:
- The executed call's result goes back to the model as a native `<|tool_response>` block, and the model continues. It makes another call or gives a final answer, up to `max_tool_steps` executed calls per turn.
- Speech follows D16:
  - **step 1** is unchanged, and its committed spoken prefix is the start sentence;
  - **steps 2 and later** voice nothing unless the step ends without a call: an end report, a confirmation or a "stuck" question.
- Tool results never reach TTS or history. History holds only what was played, joined across every playback run of the turn.

Every new behaviour sits behind `tool_loop`, default `off`. With it off, every machine step, request body, prompt and HUD message is byte-identical to `main`.

`google_search` results come from an injected `SearchBackend`; in this task that is only a test fake, and ddgs is T-0111b. Click, type, scroll and key results are the dry run's "would …" text, with `screen_changed: false`.

## Design answers (planner, with evidence)

### 1. Shape: a new request that continues the final assistant message

Each step is a **new request**: the step-1 prompt as sent, plus one final `assistant` message continued with `continue_final_message: true`. Its text is:

`spoken_prefix_1 + render_call(c1) + render_response(c1, r1) + text_2 + render_call(c2) + render_response(c2, r2) …`

It is rendered on the host exactly as the pinned template does it: `format_tool_response_block` at template lines 160–173 and `format_argument` at lines 118–147.

**Why not structured `role: tool` messages.**
- The template's OpenAI path (lines 270–313) renders an assistant message's `content` *after* the tool responses, and closes the turn with `<turn|>` when content is present (lines 348–352). So the spoken prefix cannot ride in that message.
- Form A (no content) renders `…<|tool_response>response:google_search{value:<|"|>1. Paris 14C<|"|>}<tool_response|>`. No `<|turn>model` header follows a tool response (lines 356–362), so the model continues the same model turn.
- Our continuation form (G) renders the identical structure with the prefix kept in the model's own order.
- vLLM cuts the template output after the final message's content. T-0087 q9 proved this for `spoken_prefix + "<|tool_call>"` (`docs/cd/toolcall-live-probe.md` q9).
- `Message` has no `tool_calls` or `tool_call_id` (`contracts/llm.py:120–127`). The continuation shape is already allowed (`contracts/llm.py:186–200`) and sent as a plain string (`llm_client.py:220–223, 240–242`).
- The id reader starts in the normal state, because the text does not end in the call tag (`llm_client.py:471`).

**Prefix cache.** `tools`, `chat_template_kwargs` and the step-1 messages are unchanged, so every step's prompt has the step-1 prompt as a byte-prefix. The anticipatory prefill is not used for steps. The hit rate at steps 2 and later is report-only, measured in a4.

**Thinking.** It stays session-wide. Step thoughts are not replayed into later steps (`.claude/rules/conductor.md`; H-T111a-5).

**History.** Calls, responses and withheld step text never enter history (H8).

**Special-token injection.** Special-token literals in assistant text are tokenized as special ids (q9). So every string in a response passes `drop_special_literals`, and so does step text before it is re-embedded.

**Repair.** It applies at step 1 only. `live.repair_prompt` cannot continue a step prompt (`live.py:481–500`). At steps 2 and later the session downgrades `repairable` to `refused` with reason `"repair: step 1 only"`.

### 2. Turn machine (a1)

**No new `TurnState`.** The wait for a result is THINKING with `awaiting_result` set (H-T111a-4).

**Policy** (`TurnPolicy`):
- `tool_loop: bool = False`;
- `max_tool_steps: int = 8` (counts executed calls);
- `tool_result_timeout_ms: int = 15_000`.

**`MachineState`** (all per-turn, in `_PER_TURN_RESET`):
- `tool_step: int = 1`;
- `tool_steps_executed: int = 0`;
- `awaiting_result: str | None`;
- `step_text: str = ""`;
- `played_prior: str = ""`.

**New event:** `ToolResult(t_ms, call_id, status: Literal["dry_run","executed","refused","failed","timeout"])`. It carries no text, so the machine never sees result content.

**Other additions:**
- command `LlmContinue(request_id, step, call_id)`;
- timer `tool_result`;
- `ToolCancelReason` gains `"step_budget"`.

**Ids.**
- Step 1 keeps `{turn}-gen` and `{turn}-call`.
- Step k ≥ 2 uses `{turn}-gen-s{k}` and `{turn}-call-s{k}`.
- The repair keeps `{turn}-repair`.

**Rows** (loop on only):

| Row | Trigger | Effect |
|---|---|---|
| **R11** execute and continue | Today's R1/R3 completing condition holds (`turn_machine.py:697–714`, `:651–655`), with a valid pending call and `tool_steps_executed < max_tool_steps` | `tool.execute` and arm `tool_result`, with no `commit_history` and no `schedule_summary`. State becomes THINKING with `awaiting_result = call_id`. `played_prior += played_text`. Per-step fields reset. `committed_answer`/`spoken_text` stay cumulative. `llm_start_ms` and `first_canvas_measured` are not reset. |
| **R12** | THINKING, `ToolResult(call_id == awaiting_result)` | Cancel `tool_result`. Emit `LlmContinue({turn}-gen-s{k+1}, k+1, call_id)`. Set `active_generate`, arm `llm_timeout`, `tool_step = k+1`, `awaiting_result = None`. |
| **R13** | Any non-matching `ToolResult` | Nothing. |
| **R14** | Step ≥ 2, `llm.commit(answer, not thought_open)` | Append to `step_text`; nothing is spoken. |
| **R15** | Step ≥ 2, `llm.done` | **No tool, or a refused/repairable call:** `step_text` becomes committed and held, then `_speak(final=True)`. Non-empty: SPEAKING, completing on drain. Empty: IDLE with `commit_history`. A non-valid call also emits `tool.cancel(refused)`. **Valid call with budget left:** `step_text` is withheld (logged), then R11. |
| **R16** report step | The step after the `max_tool_steps`-th execute | A valid call emits `tool.cancel(step_budget)`; its `step_text` is voiced. |
| **R17** takeover after action | THINKING (awaiting, or step ≥ 2) and `user_takeover` with `tool_steps_executed > 0` | Close like an interrupt: `llm.abort` if live, `tool.cancel(takeover)` if pending, history `(user, joined played + " [interrupted]", interrupted=True)`. Open the new turn **without** `keep_words`, so executed actions are not re-run. |
| **R18** | THINKING awaiting, `Tick ≥ tool_result` | `_fail_turn("tool timeout")` with played history. |

**History.** `_commit_played` and `_relisten` write `" ".join(nonempty(played_prior, played_text))`. Today `_on_playback_drained` overwrites `played_text` (`turn_machine.py:733`).

**Invariants** (Hypothesis, `tests/unit/test_turn_invariants.py`). None weakens "never voice uncommitted text", H4 or P6.
- **P1′.** Loop off: P1 as written. Loop on: at most `max_tool_steps` `tool.execute` per turn, at most one per step, with distinct call ids, each from a valid draft of that step.
- **P3′.**
  - (a) No tuple holding `tool.execute` holds a `tts.speak`.
  - (b) The drain rule is unchanged.
  - (c) Loop off: the result is IDLE with `commit_history`.
  - (d) Loop on, R11: the result is THINKING awaiting, with no `commit_history`, `llm.start`, `LlmContinue` or `schedule_summary` in the tuple.
- **L1 budget.** At most `max_tool_steps + 1` generates per turn, plus at most one repair.
- **L2 one in flight.** No `tool.execute` while a generate is live or a result is awaited, and no `LlmContinue` while a generate is live.
- **L3 causality.** The k-th `LlmContinue` follows exactly one accepted `ToolResult` for the (k−1)-th executed call. An unmatched result emits nothing.
- **L4 cancellation.** After an interrupt, takeover, error, `tts.error` or disconnect, the turn emits no further `tool.execute` or `LlmContinue`. (Amended by T-0114, the T-0112 carry-over: `tts.error` is a cut only in SPEAKING/PAUSED/INTERRUPTED; elsewhere it only degrades.)
- **L5 D16 speech.** A `tts.speak` at step ≥ 2 sources only a step that ended without an executed call.
- **P6′.** No `TtsSpeak.source` holds text from a `tool` commit, a repair commit, or withheld step text.
- **L6 history.** Assistant history is a subsequence of the played texts in run order.
- **L7 liveness.** Every loop turn reaches IDLE.
- **L8 differential.** With `tool_loop=False`, `step` equals a frozen post-T-0089 machine on every sequence, including `ToolResult`s.
- **P5′.** A repair happens only at `tool_step == 1`.
- **P8′.** Every pending call ends in exactly one `tool.execute` or `tool.cancel`.

### 3. Speech across steps (D16)

- **Start:** step 1's committed prefix, as today.
- **Routine steps** (step ≥ 2 with a call): nothing; the text is withheld and logged.
- **Confirm / stuck:** a step that ends without a call. T-0107 still gates irreversible calls.
- **End report:** the final answer, or the report step after the budget.

**Session changes.**
- `_drain_marked` resets at R11. It is per-turn today (`session.py:1165, 2701–2709`), so the end report's drain would never be marked.
- The speech gate becomes one per (turn, step); today it is per turn (`session.py:1302–1305, 1329`).

### 4. Tool results

Results use the mapping form, with keys sorted as the template sorts them.
- **`google_search` with a backend:** `response:google_search{query:…,results:[{snippet:…,title:…,url:…}…]}`. At most 5 results, each snippet ≤ 300 chars, the whole response ≤ 1500 chars.
- **`google_search` without a backend:** `{note:"search is not connected in this session",results:[],status:"dry_run"}`.
- **Dry-run actions:** `{action:"would click at (412, 300)",screen_changed:false,status:"dry_run"}`.
- **Refused:** `{reason:…,status:"refused"}`.
- **Failed or timed out:** `{reason:…,status:"failed"|"timeout"}`.
- **Calls:** rendered from the validated name and arguments, never from the raw draft.

**New frames are not attached after step 1.** A live screenshot after an action is T-0111c's. a4 Q5 asks whether vLLM accepts an image part in a continued assistant message.

### 5. Logging and HUD

- **Session log, per step:** `tool.call` with distinct call ids; `tool.result {call_id, step, status, response}`; `note {what:"step text withheld", step, chars}`; one `llm.request` per step, with `step`.
- **Turn line:**
  - `tool` stays the step-1 record;
  - extras gain `tool_steps`, `tool_steps_executed` and `tool_loop_end`.
- **HUD:** `AstraToolCall` gains optional `step` (absent with the loop off), and `hud/src/panels/tool_call.js` labels the cards "step k".

### 6. Measurement

- **Fake LLM:**
  - one stream per step continuation, consumed in order;
  - step continuations are told apart from repairs structurally: a step's final assistant text ends in `<tool_response|>`, a repair's in `<|tool_call>`;
  - step prompts are recorded.
- **Fake search:** canned results, a query log and an injection fixture.
- **GPU probe (a4):** required. No live run has ever sent a `<|tool_response>` continuation.

## Acceptance criteria

### a1 (machine)

1. **Loop off is unchanged (negative).** With `tool_loop=False`, L8 holds against the frozen post-T-0089 machine (300 Hypothesis sequences of ≤ 60 events, `ToolResult` included), and P1–P9 pass unchanged.
2. **Loop-on invariants.** With `tool_loop=True`, P1′, P3′, L1–L7, P5′, P6′ and P8′ hold (300 examples, ≤ 80 events).
3. **R11.**
   - A valid step-1 call after a drained prefix emits `tool.execute` and `arm_timer(tool_result)` in one tuple, with no `commit_history`, `tts.speak` or `llm.start`.
   - *Adversarial:* a speak after the last drain withholds the execute until the next drain.
4. **R12 and R13.**
   - A matching `ToolResult` emits exactly one `LlmContinue(step=2)`.
   - *Adversarial:* a duplicate result, a stale one, one before execute, and one after an interrupt each emit no command.
5. **R14 and R15.**
   - No speak happens before the step-2 `llm.done`.
   - A valid step-2 call drops its text.
   - A toolless step-2 `llm.done` voices exactly `step_text`.
   - *Adversarial:* a step-2 canvas with `thought_open=True` contributes nothing.
6. **R16.**
   - With `max_tool_steps=2`, the third generate's valid call is cancelled with `step_budget` and its text is voiced.
   - *Adversarial:* a model that calls a tool on every step ends IDLE after exactly 3 generates.
7. **R17.**
   - A takeover after an executed call opens a new turn holding only the post-takeover words; the previous history entry ends in `[interrupted]`.
   - *Adversarial:* the new `llm.start` transcript lacks the first request's words.
8. **History across playback runs.**
   - Played "A." and then "B." store `"A. B."`.
   - *Adversarial:* the second run's drain does not erase the first.
   - Withheld text is never stored.
9. **R18 and P5′.** A tool-result timeout ends IDLE with `hud.error`. A repairable step-2 draft never starts a repair.

### a2 (render)

10. **Template parity.** `render_call` and `render_response` equal the pinned template's rendering (`tests/cd/oracle/gemma4_template.py`) for every v1 tool, both response forms, nested lists, booleans and ints. `step_prompt` for two steps equals the oracle's form D, apart from the step-1 prefix.
11. **Injection (adversarial).**
    - A result holding each of the 24 `SPECIAL_TOKENS` literals, including spliced cases such as `<tu<turn|>rn|>`, renders with zero special literals other than the renderer's own `<|"|>` delimiters.
    - Re-parsing yields the sanitised values.
    - `router.template_content(text) == text`.
12. **Bounds.**
    - At most 5 results; snippets ≤ 300 chars; a response ≤ 1500 chars; an 8-step continuation ≤ 14 000 chars.
    - *Negative:* `router.py`, `native.py`, `score.py`, `tools.py`, `tools_v1.json`, `live.py` and `tool_executor.py` are unchanged.
13. **Imports.** `loop.py` imports only stdlib, `contracts` and `toolcall.special_tokens`/`router`.

### a3 (session)

14. **Loop off is unchanged (negative).** With `tool_loop` off, the tools-off golden and the single-call tool rows are unchanged, and no `step` key appears on the wire.
15. **A scripted two-step search turn** (FakeLlm plus the fake search):
    - the prefix is voiced and the search executes;
    - the step-2 prompt is `continue_final_message` and ends with `<tool_response|>`, with the same `tools` and `chat_template_kwargs`, and the step-1 prompt as its message-wise prefix;
    - the end report is voiced and history is "prefix report";
    - `tool_steps_executed=1`, `tool_loop_end="final"`.
16. **Canary (adversarial).** A snippet carrying `ZQX-CANARY` never reaches `TtsSpeak`, `astra.spoken`, history or memory. It does appear in the session log.
17. **Drain (adversarial).** In a three-step turn with speech at step 1 and at the final step, the final drain is marked and the turn reaches IDLE.
18. **Per-step judging.**
    - Withheld text is logged.
    - Step 2 is judged with `{turn}-call-s2`.
    - A repairable step-2 draft is refused with `"repair: step 1 only"`, and no repair request is sent.
19. **Failures.**
    - A 413 at step 2 is not retried; the turn ends with `hud.error`.
    - A hanging executor is cut by the session timeout, and `ToolResult(status="timeout")` follows.
20. **Negative.** No non-loopback socket is opened. `tools = live` is still refused.

### a4 (probe, `/launch`)

21. The pre-registered rows Q1–Q6 are reported with every number and its regime. There are no gates: the reading decides whether the human turns the loop on (H-T111a-1).

## Implementation notes

- **Machine purity.** `turn_machine.py` stays pure, and it never receives result text.
- **Clocks.** Do not reset `llm_start_ms` or `first_canvas_measured` per step. Add `step_start_ms` if it is needed.
- **Answer bookkeeping.** `committed_answer` stays cumulative. Withheld text joins it only when voiced.
- **Step prompts.** Build them from the step-1 prompt *as sent*, after any over-long retry. Never change thinking or tools per step.
- **`execute_tool`.** It runs mid-turn in the loop. It must submit `ToolResult` on every path, behind a session timeout below `tool_result_timeout_ms`.
- **Per-step state.** `_TurnLog.tool_commit`, `repair_id` and `tool` become per-step, keeping step 1's fields where the turn line reads them.
- **Repair.** Step 1 only; `live.py` is not edited.
- **Self-disabling.** If the loop turns itself off, it publishes that: a note plus `tool_loop_end`.
- **Durations.** Never computed from two clocks.

## Notes for T-0114 (session) from the T-0113 review (2026-10-17)

- **Thoughts in step text.** `drop_special_literals` deletes the `<|channel>`/`<channel|>` markers but keeps the words between them. So T-0114 must pass only post-router, thought-stripped step text, never raw text, or the thought is replayed as plain assistant text (H-T111a-5). Add a test with a step text that contains `<|channel>thought…<channel|>`.
- **Lengths.** `render_call` arguments (for example a long `type_at` text) and step texts are not bounded by T-0113. T-0114 must bound them, or test the real worst case against `max_model_len`.
- **Keys that collide after sanitising** merge, and the last one wins. That is harmless for the fixed v1 keys; note it for any free-form payload.
