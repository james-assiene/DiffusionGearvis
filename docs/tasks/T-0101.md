## Goal
On a fresh engine boot the first H-T84-2 repair that uses a given tool's automaton takes 1.5–2.5 s; later repairs on the same automaton take
213–346 ms. The cause is the plugin's Triton `log_matmul` kernel, JIT-compiled once per kernel variant per engine process; the variant depends
on the automaton's live state count S, and the engine runs in a `--rm` container with no Triton cache mount, so every boot compiles again.
Under the 3000 ms deadline (`turn_machine.py:52`) the first press_key repair spent 2545 ms (85 %) compiling. After this task the composition
root (`cli.run_session`) sends one warm-up repair request per payload automaton before the session starts — through the real client and CD
path, out of the denoising view, output discarded — only when tools and repair are on. The cold cost moves from the first user turn into
session start (~8 s right after a boot, ~1.1 s on a warm engine). The deadline, the repair and every other measured number stay as they are; a
pre-registered GPU re-run of the T-0099 harness with the warm-up on confirms the fix.

## Acceptance criteria
1. **One request per payload automaton.** `local_astra/toolcall/warmup.py` exposes `async def warm_repair(llm, kit, *, total_budget_s=30.0)
   -> WarmReport` (names may vary). One generate per payload in `kit.payloads.tools`, sequentially, sorted by tool name; every
   `automaton_sha256` exactly once; tools sharing a bucket or kernel variant are **not** merged. Each request's `cd` equals
   `live.repair_request(name, ids, 50, tag, kit.payloads, kit.calibration)` in every field except `draft` and `record_tag`; options are
   `live.REPAIR_OPTIONS`; the prompt carries the session's `tools` field and is built by `live.repair_prompt` on a fixed minimal pass-1 prompt
   (no screen, memory or user data); the draft is the engine's ids (`llm.tokenize`) of a fixed, valid native call for that tool.
2. **Invisible.** Every warm-up request carries `xargs` `{"astra_tap": "off"}`, a request id starting `warmup-` and a `record_tag` starting
   `warmup:` (≤ 64 chars, `[A-Za-z0-9_.:-]`). Its commits are consumed and discarded; nothing reaches TTS, the HUD, history, memory or a session
   log.
3. **Never stops the session or turns repair off.** A request that raises, ends 4xx/5xx or exceeds its share of the cap is recorded as failed
   (aborted if running) and the next tool is still tried; when the 30 s cap is spent the rest are `skipped`; `warm_repair` never raises except
   `CancelledError`; the kit object is unchanged (same object, `repair_off` unchanged).
4. **Wiring and order (H-T101a).** `cli.run_session` awaits `warm_repair(graph.session.llm, kit)` **before** `graph.session.start()`, only when
   `kit` is not `None`, `kit.repair_off is None` and `kit.payloads` is not `None`, then prints one stdout line
   `astra session: repair warm-up: <tool> <ms> ms <status>, …, total <ms> ms`. Tools off, repair off, or a duck-typed graph without `tool_kit`:
   zero requests, no line.
5. **Report, never gate, in the session.** `WarmReport` per tool: status (`ok` | `failed: <reason>` | `skipped`), wall ms, commits delivered,
   and the `live.repair_verdict` status of the output (reported only); plus total wall ms. An invalid output is not a failure.
6. **Harness flag.** `scripts/gpu/t0099_repair_live.py` gains `--warm-repair` (default off). On: `main` runs `warm_repair` once with the
   harness's real `VllmClient` after the idle and loopback checks and before case 0, and writes `regime.repair_warmup = {"on": true, "per_tool":
   {…}, "total_ms": …, "ended_wall": …}`; off: `{"on": false}`. A warm-up leaving any tool not `ok` voids the run (`integrity: repair warm-up
   incomplete (<tool>: <status>)`).
7. **First-use report rows.** `build_report` adds `first_use_repair` (for every payload sha, the first `tool_repair` request in manifest session
   order, either arm: tool, arm, case, repetition, `tool.repair` span ms) and `first_use_repair_max_ms`; `render_markdown` adds one table. A
   pre-T-0101 run dir (no key) reports `repair_warmup: {"on": false}` and still gets the rows.
8. **Pre-registered confirmation (H-T101b; read only if G1–G8 and criterion 6 hold).** Fresh boot at the T-0101 merge commit with
   `--warm-repair`: **C1** every payload tool appears in `first_use_repair` and every first-use span ≤ **600 ms**; **C2** arm-S `tool.repair` p90
   (nearest rank) ≤ **1500 ms** when arm S fires ≥ 1 repair (else "unread (n = 0)", C1 decides); **C3** arm-F `tool.repair` p50 in **[203, 248]
   ms** (±10 % of a794a98's 225); **C4** (reported) the slowest warm-up request ≥ 1000 ms. Readings: **R1** C1–C3 hold → the H-T99b trigger is
   closed by fixing the cause, the deadline stays 3000 ms; **R2** C1 fails for a tool whose warm-up was `ok` → cold state is not process-wide,
   re-plan, no deadline change; **R3** C1 holds, C4 does not → fix holds, attribution unconfirmed on this boot, inspect for a persisted cache;
   **R4** C1 holds, C2 fails → slow repairs are not first-use; open the budget/deadline task H-T99b named, the human decides; **R5** C3 fails →
   the warm-up changed a steady-state number, the fix is not accepted as is.
9. **Adversarial: deadline and budget untouched.** Over the task's closed range, `turn_machine.py` (`tool_repair_timeout_ms` = 3000),
   `live.REPAIR_OPTIONS` (256), `local_astra/bench/thresholds.py` and `docs/03-test-plan.md` have zero diff.

## Implementation notes
- **Placement (H-T101a).** Plugin-at-load, a persisted Triton cache, `astra up` only, and per-`Session.start` warm-ups were rejected (see the
  planner's reasons: payloads not mounted in the container; guessing Triton keys; a `services/` change that also moves vLLM's cold boot; `up`
  skips a healthy engine; `session.py` is T-0100's and per-session warm-ups change harness contention). Chosen: the composition root, once per
  conductor process, before the session accepts input. An engine restarted under a running session is cold again (out of scope; noted).
- **Before `session.start()`** (it starts the STT pump, `session.py:845-862`).
- **VRAM:** no new steady state beyond what the first real repair allocates; B7 unchanged (state it in the write-up).
- **Prefix cache:** the warm-up's prompt differs from the session prefix and invalidates nothing; never toggle `<|think|>`.
- **Engine log:** each warm-up emits an `ASTRA_CD` record with a `warmup:` tag; harnesses counting records filter by tag.
- **What NOT to do:** do not raise `tool_repair_timeout_ms` or `REPAIR_OPTIONS.max_tokens` before this confirmation reads R4; do not drop the
  first sample or call a cold first use an outlier; do not merge warm-ups by bucket or guessed key; do not make the warm-up a session-log record.
- **Guard hook:** guard_bash blocks bash naming `scripts/gpu` or `scripts/locked` (including in commit messages): Edit tool, `git commit -a`.
  The plugin runs inside the container; mypy excludes it; this task does not edit it. Agents create no files outside their owned paths by any
  means.

## Rulings on the test-author's report (orchestrator, 2026-10-15; tests at 3c87c34)
- **W1 (share of the cap).** Each warm-up request's deadline is the remaining total budget at the moment it starts; a request that overruns
  it is aborted and recorded `failed`, and every later tool is `skipped`.
- **W2 (shared automaton).** One request per distinct `automaton_sha256`; if two tools share a sha, the automaton is warmed once and both
  tools are reported with that request's outcome.
- **W3 (interface).** The names the tests pin are adopted: `WarmReport.per_tool[tool]` with `.status`, `.wall_ms`, `.commits`, `.verdict`, and
  `WarmReport.total_ms`; `report["first_use_repair"]` keyed by sha with `{tool, arm, case_id, rep, ms}`; manifest
  `regime.repair_warmup.per_tool[tool]` a dict with `"status"` and `"wall_ms"`.
- **W4.** `build_report` skips `tool_repair` `llm.request` records without `cd` (old run dirs and fixtures) rather than raising.
- Criteria 9–11 are checked by the reviewer by command and the write-up, not by rows.
