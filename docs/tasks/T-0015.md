**Status:** done 2026-10-02 (implementation landed ahead of tests — see Protocol deviation) · **Blast radius:** high (every image request) · **Depends on:** T-0014 (superseded by T-0048, ruling A3)

## Goal
The plugin currently carries a compatibility shim for an upstream vLLM defect that breaks
DiffusionGemma's image path. Today its entire justification lives in commit messages and a
`PROGRESS.md` line. After this task the shim is covered by tests that (a) prove it is still
needed, (b) prove it works, (c) detect a *new* sibling defect after any vLLM bump, and (d) fail
loudly when upstream fixes the bug so the shim is deleted rather than silently kept forever.

## The defect (evidence, 2026-09-13)
`vllm/model_executor/models/diffusion_gemma.py:289-301` does **not** subclass
`Gemma4ForConditionalGeneration`; it borrows seven methods by class-level assignment, with the
comment "architecturally identical to Gemma4. Delegate to avoid maintaining a duplicate copy."

That borrow is safe only while the borrowed methods touch no state that Gemma4's `__init__` sets
and DiffusionGemma's does not. Commit `95c914442` (2026-08-13, `[LoRA][Gemma4] Support vision
tower LoRA` #42662) added `self._enable_mm_lora` in `Gemma4.__init__` (`gemma4_mm.py:1061`) and
read it in `_process_image_input` (`:1317`, `:1364`). Every DiffusionGemma image request now
raises:

```
AttributeError: 'DiffusionGemmaForConditionalGeneration' object has no attribute '_enable_mm_lora'
```

and because it raises inside the model runner it kills the EngineCore (`EngineDeadError`), not
just the request. Observed on this box: `logs/vllm-bf16-4gib.log`.

Working window: 2026-06-12 (#45163 added DiffusionGemma) → 2026-08-12. `v0.29.0` shipped broken
and upstream `main` still is (checked 2026-09-13). There is **no release with a working image
path**, which is why patching beat downgrading — see the options analysis in `PROGRESS.md`.

An AST audit of all seven borrowed methods found **three** missing attributes, not one:
`_enable_mm_lora` (reachable, fixed), `_parse_and_validate_audio_input` and `_process_audio_input`
(audio-only, guarded at `gemma4_mm.py:1244` and `:1623`, so latent for us — we never send audio
to the LLM). That audit is currently a thing a human ran once. Criterion 3 makes it a test.

## Acceptance criteria
1. **The shim works.** A `gpu`-marked test boots nothing but imports inside the pinned container
   and asserts: `AstraDiffusionGemma.__bases__[0] is DiffusionGemmaForConditionalGeneration`;
   `AstraDiffusionGemma._enable_mm_lora is False`; and
   `AstraDiffusionGemma._process_image_input is Gemma4ForConditionalGeneration._process_image_input`
   (the shim must **not** shadow the borrowed method — if it ever does, we have silently forked
   upstream's vision code).
2. **The shim is still needed** — the deletion trigger. A `gpu`-marked test asserts the stock
   `DiffusionGemmaForConditionalGeneration` does **not** define `_enable_mm_lora` anywhere in its
   MRO below our wrapper, i.e. the upstream bug is still present. **When upstream fixes it this
   test fails**, and the correct response is to delete the shim and this test together, not to
   adjust the assertion. The test's failure message must say exactly that.
3. **No new siblings after a vLLM bump** — the audit as a test. A `gpu`-marked test re-derives the
   audit automatically: parse the borrowed-method list off `diffusion_gemma.py` (do not hardcode
   the names — if upstream borrows another method, the test must pick it up), walk each borrowed
   method's AST for `self.<attr>` loads, and assert every such attribute resolves on
   `AstraDiffusionGemma`. Unreachable attributes may be excluded, but the exclusion must be
   **derived from upstream's own declarations, not from our shim** — grounding it in "we stubbed
   that method" would make the test agree with the implementation it is meant to check. The
   correct grounding is `DiffusionGemmaProcessingInfo.get_supported_mm_limits()`, which upstream
   declares as `{"image", "video"}`: audio branches are dead because *the model declares no audio
   support*. If DiffusionGemma ever declares audio, the exclusion evaporates and this test must go
   red. (Corrected after the test-author pointed out the original wording grounded it in our stubs.)
4. **Architecture-name drift.** A pure unit test (no GPU) asserts the architecture string in
   `services/vllm.sh`'s `--hf-overrides` is byte-identical to `ARCHITECTURE` in
   `plugin/astra_vllm_plugin/astra_vllm_plugin/__init__.py`. These two must change together; if
   they drift, vLLM fails to resolve the model at boot.
5. **The load-bearing flags stay.** A pure unit test (no GPU) asserts `services/vllm.sh` still
   passes all four of `--attention-backend`, `--diffusion-config`, `--max-num-seqs` and
   `--override-generation-config`. Reason: overriding `architectures` makes vLLM's
   `MODELS_CONFIG_MAP` lookup (`models/config.py:1006`) miss, so
   `DiffusionGemmaModelForBlockDiffusionConfig.verify_and_update_config()` never runs. Every
   branch it would apply is currently falsified by one of those four explicit flags. Dropping any
   one makes a plugin-on boot silently diverge from plugin-off. The test's message must explain
   this, because the failure looks like pointless strictness otherwise.
6. **Docs.** `.claude/rules/gpu-services.md` records the shim, the upstream commit that caused it,
   and the deletion condition. **Status: DONE 2026-09-13.** Rules entry written; upstream issue filed at
   https://github.com/vllm-project/vllm/issues/56712 (diagnosis, git bisection and report written by Claude,
   reviewed and filed by the repository owner). **Watch it: if it is fixed upstream, delete the
   shim** — `tests/contract/test_vllm_shim_gpu.py::test_upstream_defect_is_still_present` will go
   red and that is the signal, not a test to relax.

7. **`ARCHITECTURE` stays a plain string literal** in the plugin's `__init__.py`, so criterion 4
   is checkable by `ast.parse` without importing vLLM. Added after the test-author flagged that
   the original criteria assumed this without saying it.

## Protocol deviation (recorded deliberately)
CLAUDE.md requires planner → test-author → implementer → reviewer → verifier, with tests written
from acceptance criteria **before** the implementation exists. That did not happen here: the shim
was written and shipped mid-session to unblock a Phase 0 GPU experiment, and this task file was
written afterwards to fit the code. The risk is the usual one — tests written after the fact tend
to assert what the code does rather than what it should do. Mitigation: criteria 2 and 3 are
written as *failure* conditions derived from upstream source, not from our implementation, and
the test-author is instructed not to read `model.py` while writing them.
