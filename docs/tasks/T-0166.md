# T-0166 — HUD reconnect safety: a longer grace, counted from hello, and nothing published reaches a socket before its hello reply

**Status:** done 2026-10-27 (merged bd441205; reviewers A and B, verified at a0c45f69); was in progress (tests f35fa191..efbb29df, activated efbb29df; implementation 49c2509d on T-0166-impl-iso); **Branches from main after T-0165 merges** (T-0165 C9(e) pins `RECONNECT_GRACE_MS = 1000` for the life of T-0165; this task supersedes that pin, see Implementation notes).
Origin: two server-side findings of the T-0165 reviewer (reconnect-gap measurement; live-before-hello probe, 3/25 on main under load).

## Goal

A reloaded HUD page must reconnect to the turn it was watching, and its first message must be the server's hello reply. Two server-side defects break this today, both in `local_astra/conductor/hud_server.py`.

The first is the reconnect grace. `RECONNECT_GRACE_MS = 1000` is too short under load: the reviewer measured close→`open()` gaps with a median of about 100–310 ms and a maximum of 1005 ms (1 of 74 over 1000 ms under heavy CPU load). When the grace expires, `_on_last_gone` clears the journal and submits `ClientDisconnected`. The machine then degrades to text-only, aborts the live turn and cancels the tool loop, all for a reload. The grace also counts any accepted socket as a page, so a socket that never says hello extends it or hides a real departure.

The second is fan-out before hello. `HudServer.publish` fans out to connections that have not yet greeted. While THINKING, `astra.turn.state` publishes at 20 Hz, so a reloaded page can receive a live message before its hello reply. The page's T-0162 D-3 "first message ever" rule then stops the screen capture wrongly. Any live message ahead of the replayed reset is also cleared by it.

After this task:
- the grace is 4000 ms (above the 3000 ms mount ceiling);
- only a connection that has said a valid hello counts as a page for the grace;
- messages published to a connection before its hello are held, then delivered after the hello reply in publication order.

Nothing changes on the wire, in `hello_reply()`'s own order, or for already-greeted connections.

## Acceptance criteria

Citations: docs/02 §5 (T-0037 journal and hello, T-0043 c18, T-0090 U10, T-0162 A-5/A-6/D-3) and T-0028 criteria 4, 12 and 13 ("the last page going away is what `ClientDisconnected` means").

**Grace**

G1. **The grace is 4000 ms and exceeds the mount ceiling.**
- `RECONNECT_GRACE_MS == 4000`, strictly greater than `MOUNT_CEILING_MS`.
- `RECONNECT_GRACE_MS > MOUNT_CEILING_MS`, where `MOUNT_CEILING_MS` is parsed from `hud/src/panels.js` (T-0165 C5).
- With one greeted page that closes at session time t0:
  - no `ClientDisconnected` is submitted at t0 + 3999;
  - exactly one is submitted by t0 + 4001, on the session clock (T-0028 c13).
- Mutation target: 1000 must turn a row red.

G2. **Only a greeted connection is a page for the grace.** "Greeted" means it sent a hello with the right `protocol_version`.
- (a) `open()` of a connection does not cancel a pending grace timer. That connection's valid hello does, if it arrives before expiry.
- (b) An ungreeted connection's close neither starts, restarts nor delays the timer.
- (c) Suppose the last greeted page closes while an ungreeted connection stays open. Then the timer starts, and `ClientDisconnected` fires at its original deadline.
- (d) **Adversarial.** A greeted page closes at t0. A socket that never says hello opens at t0 + 1000 and either stays open or closes at t0 + 2000. Either way, exactly one `ClientDisconnected` fires by t0 + 4001, and none before t0 + 3999.
- (e) A connection whose hello was refused for `protocol_version` counts as ungreeted for (a)–(d).
- (f) A session whose only socket never greeted submits no `ClientDisconnected` when that socket closes. No page ever left. This is a named behaviour change; see Q6.

G3. **Negative: departure semantics are otherwise unchanged.**
- The journal is still cleared when the grace fires (T-0037 c4).
- A greeted reconnect inside the grace still replays the open turn.
- A hello after the grace gets only the live head (`test_hud_hello_replay.py::test_a_client_disconnected_clears_the_journal`, unedited).
- Two greeted clients where one leaves still produce no event (`test_hud_endpoint.py::test_two_clients_both_receive_and_the_last_disconnect_is_one_event`, unedited).

**Hold until hello**

H1. **Nothing published reaches an ungreeted socket.**
- Over a real loopback socket: messages published after accept and before the client's hello are not written to the socket before the hello reply.
- A client that reads with a timeout before sending hello receives none of them.
- This covers every publish path, including the canvas relay (`canvas_relay.py` calls `HudServer.publish` directly; docs/02 §5 "Canvas relay").

H2. **Held messages follow the reply, in order, and are not dropped.** After a valid hello, the connection's sequence is:
1. the `hello_reply()` messages, in exactly today's order: replayed cleared if any, assist state, turn state, log state, `replay_truncated` if any, the journal, and the turn state again (replay);
2. every held message, in publication order, `replay=False` as published;
3. later live messages.

A held message may be lost only through:
- the existing `Outbox` policy: `astra.turn.state` latest-wins, and `astra.canvas.*` at most 8, denoise frames first (T-0128c A6);
- the H4 reset cut;
- the H5 departure cut.

**Adversarial (primary):**
- a spoken line, a tool call and 40 `astra.turn.state` messages (20 Hz for 2 s) published between `open()` and hello;
- after the hello, the first message is the reply head and no held message precedes it;
- the spoken line and the tool call each appear live exactly once after the reply.

H3. **Direct replies are not held.** `astra.error` with code `no_hello`, `protocol_version`, `malformed` or `wrong_direction`, sent to an ungreeted connection about its own frame, reaches the wire before any hello (T-0028 c4, T-0008 c2). Over a real socket: garbage before hello yields `astra.error(code="malformed")` while held published messages are still not received.

H4. **The reset cut (T-0162 A-5/A-6, D-3).** Suppose an `AstraSessionCleared` is published while a connection is ungreeted. Then:
- held messages published before it, and the live cleared itself, are not delivered;
- held messages published after it are delivered.

After the hello, the connection's first message is the replayed cleared. No message published before the latest reset reaches it at any point after that.

**Adversarial:**
- held = [spoken t1, relay canvas `chatcmpl-A` step, cleared(resets=1), spoken t2, turn.state];
- delivered = reply (starting with cleared replay=True), then [spoken t2, turn.state];
- no t1 line and no `chatcmpl-A` frame anywhere; exactly one cleared, and it is the replayed one.

H5. **The departure cut (T-0037 c4 parity).** When the grace fires and the journal is cleared, messages held for still-ungreeted connections are discarded too. A later hello on such a connection gets the post-departure reply plus only the messages published after the departure. See Q2.

H6. **The reply is never truncated or refused because of held messages.**
- Setup: a connection holds `DEFAULT_OUTBOX - 1` non-droppable messages of the open turn, and the journal is full (`REPLAY_MAX_MESSAGES`).
- On hello:
  - the connection stays open;
  - the reply is complete and first;
  - all held messages follow in order.
- The existing invariant `REPLAY_MAX_MESSAGES < DEFAULT_OUTBOX` stays true.

H7. **A socket that never says hello is bounded** (T-0028 c12; ruling A12).
- Held messages are subject to the per-connection bound and the existing drop policy.
- Overflow of a non-droppable kind closes that connection with the named overflow reason, as for a stalled reader. No other connection and no pump step is affected.
- 60 s of virtual time with only 20 Hz `astra.turn.state` keeps a silent connection open, holding at most `DEFAULT_OUTBOX`.
- `publish` stays O(1) per connection in the number of held messages: no scan of the hold per publish beyond the existing `Outbox` canvas rules.

## Implementation notes

**Background**
- **Where the hold sits.** `publish` records into the journal *before* fan-out. A message held for an ungreeted connection is therefore usually also in that connection's reply as a `replay=True` copy, and is then delivered again live. This is accepted.
  - The page's reducers are latest-wins or idempotent per id: transcript, surface per `surface_id`, tool call per `call_id`, turn state.
  - Held messages keep publication order, so a `spoken` / `spoken.played` pair re-applies in the order T-0030 c18 needs.
  - Do not dedupe against the journal (Q3).
  - If a reviewer finds a page reducer that is not idempotent under this, it is a finding against the page, routed as its own task.
- **What the existing tests constrain (N3).** Several rows publish to connections that never greet, then read `conn.outbox.pending()`, `len(conn.outbox)`, `conn.outbox.dropped` and `conn.sent()`:
  - the canvas cap rows;
  - the stalled-reader barge-in row;
  - the wire-tap rows.

  So held messages must stay subject to the same bounded `Outbox` policy and stay visible through those reads. A second unbounded list beside the outbox would also break H7.

**Requirements**
- **Errors are not "published".** `_error()` replies to the connection's own frame and must reach the wire while published messages are held (H3). Today both go through `offer`.
- **The reply is bounded, not the hold.** H6 forbids the reply being refused because held messages fill the outbox. `REPLAY_MAX_MESSAGES < DEFAULT_OUTBOX` (and the row `test_a_full_journal_never_overflows_a_fresh_outbox`) stays true. How the reply gets ahead of the held messages is the implementer's design.
- **Cuts by publication order.** The H4 reset cut is "everything held before the latest `AstraSessionCleared`". Cut by publication order, not by `turn_id` or request id: the relay's canvas ids are vLLM's `chatcmpl-…`, not the session's (T-0162 amendment (a)).
- **The grace timer.** It stays on the session clock (`session.clock.call_at`); the transport has no clock (T-0028 c13).
  - Move the cancel from `open()` to a valid hello.
  - Only greeted connections decide `forget` / `_on_last_gone`.
  - `wire.out`'s `connections` field keeps counting all sockets (N2; Q5).
- **The pump bound.** Nothing here may await or scan per publish in proportion to the hold (`.claude/rules/conductor.md`: 20 ms in the pump). Releasing the hold at hello is O(held), once.

**Side effects to expect**
- **Test wall time.** `test_hud_rehearsal.py` 2(f) sleeps `RECONNECT_GRACE_MS / 2000` s of real time, then waits up to 10 s. A 3000 ms grace adds about 2 s to that integration row. That suite is outside the fast suite, so the fast suite's 120 s ceiling is untouched.
- **Spec supersession, named.** T-0165 C9(e), "`RECONNECT_GRACE_MS` stays 1000", was scoped to T-0165. This task changes it. Docs/02 §5 and the T-0028 c13 wording change with it (orchestrator).
- **The cost of a longer grace.** A tab that is really closed keeps the live turn (and tool loop) running up to 2 s longer before `Degrade(text_only)` and the abort. This is accepted per the reviewer's recommendation.

**Out of scope**
- The T-0162 D follow-up "a relay id whose first frame arrives after the echo can paint".
- T-0165 Q2 (keep the closed turn across a reload).
- The page's D-3 rule itself: the fix is server-side; the page is untouched.

**Open questions**
- Q1 (orchestrator/James): the grace value. 3000 ms per the reviewer, equal to `MOUNT_CEILING_MS`. Because grace = ceiling, a reload that hits the mount ceiling (a hung panel) still loses the journal. The alternative is 4000 ms, which buys slack beyond the ceiling but means one more second of a closed tab's live turn. G1 pins `>=` the ceiling, so either passes the parity row.
- Q2 (reviewer): H5, discarding held messages at a departure. Recommended yes, for parity with the journal clear (T-0037 c4: "nothing survives the session being told its last page is gone"). The alternative is to keep them, which would show an aborted turn's lines live after the reply.
- Q3: dedupe held messages already covered by the reply? Recommended no. It is more code in the hold path, and it risks dropping a message the journal evicted.
- Q4: close a socket that has not said hello within N seconds? Recommended not here. H7 bounds it, and the origin fence and loopback already limit who can connect.
- Q5: should `wire.out.connections` count greeted connections only? Recommended unchanged, so session-log readers keep their meaning.
- Q6 (James): G2f. A session whose only socket never greeted no longer gets `ClientDisconnected` when it closes. Confirm this is acceptable: nothing was ever shown, so nothing was abandoned.

## Blast radius

**High.** The task changes the HUD transport's fan-out and hello path, which every page relies on. It also changes when the session is told its last page left, and that decides whether a live turn is aborted and the tool loop cancelled. A wrong hold silently loses spoken lines or tool cards; a wrong grace rule either kills turns on reload or never reports a departure. **Two reviewers.**

Mutations each reviewer must run, each of which must turn a row red:
- fan-out to ungreeted connections restored;
- held messages flushed before the reply;
- `_cancel_lonely()` back in `open()`;
- an ungreeted close restarting the timer;
- the grace at 1000;
- the reset cut removed;
- the departure cut removed;
- `_error` routed through the hold;
- the reply counted against a full outbox (H6).

Size: about one implementer day (one server file and four new test modules). It is one task, because both findings live in `hud_server.py` and would otherwise share a file. The protocol cannot be skipped: there are two behaviour changes on the transport and a spec change to T-0028 c13.
