## Goal

The T-0131 A/B at c70baf0 measured these arms:

| Arm | Success | Hit rate | Step done p95 | ReGround p50 |
|---|---|---|---|---|
| 280/off | 5/25 | 0.35 | 1523 ms | – |
| 280/on | 15/25 | 0.88 | 1157 ms | 407 ms |
| 1120/off | 15/25 | 1.00 | 1901 ms | – |
| 1120/on | 18/25 | 1.00 | 1756 ms | 762 ms |

Regime: lean, CL 256, 48 steps, thinking on, NVFP4 diffusiongemma-26B-A4B rev 2ea8372, vLLM 0.29.0, 25 turns per arm, order seed 0.

The pre-registered rule labelled this "no change". The human overruled that label on 2026-10-22: live mode defaults to 1120 visual tokens with ReGround on.

This task does three things:
- **(A) The live default.** With `tools = live`, an unset budget becomes 1120 and an unset ReGround becomes on. A flag or the profile still overrides either. The startup line and the turn line say which value is in effect and where it came from. Every other mode is unchanged.
- **(B) A separate pass-2 budget** (`reground_visual_tokens`). Its default is the main budget, so nothing changes until the A/B rules.
  - It applies only when pass 2's prompt carries exactly one image. The engine applies one budget to every image of a request, and the budget is part of each image's cache key.
  - The `tool.reground` record gains the budget actually sent, the image count, and pass 2's first-commit and tool-commit times.
- **(C) A locked 3-arm GPU A/B**, n = 100 per arm: 1120/off, 1120/on with a 1120 crop, 1120/on with a 280 crop. It comes with a decision rule (H-T132-1) for whether ReGround stays on at 1120 and whether the crop budget defaults to 280.

It also records that T-0131's D5 gate "step done p95 ≤ 1.5 s" was mis-calibrated: the 280/off control fails it at 1523 ms. That gate is not reused.

**A6. The effect of 1120 elsewhere, and its pins.** The investigation is done; findings are below. The implementer states them in the docs/02 delta, and the tests pin them.
- **Step 1 is bounded by the engine's own count.** `PromptBuilder.fit` runs against `max_prompt_tokens = 14 336`, using the engine's count. Larger images are therefore paid for automatically: history pixels are spent first. Nothing in `fit` assumes 280.
- **Steps k > 1 have no token check.** A step is the step-1 prompt plus a continuation of at most `MAX_CONTINUATION = 14 000` characters. A step over the window is an engine 400, which becomes an `llm.error`: loud, not silent.
  - This gap exists at any budget.
  - At 1120 it narrows: up to `Budget.max_images = 4` images, each about 1094 tokens instead of 275, adds up to about 3.3k tokens to every request of a turn.
  - P4 (group C) measures the worst case. This task does not change the bound.
- **Compaction (T-0120b) has no image term.** `loop.compact` and `MAX_CONTINUATION` count continuation characters. The live payload carries `screenshot: "updated"|"unchanged"` as a word, and images never enter the continuation. Nothing there assumes 280.
- **Timeouts.** `REGROUND_TIMEOUT_MS = 4000` against the measured pass-2 p95 of 2348 ms at 1120 (n = 39). `TOOL_EXEC_TIMEOUT_MS = 10 000` covers pass 2 plus the action. Neither changes.
- **The window tripwire, a CPU row.** It pins the inputs of the window arithmetic:
  - `Budget.max_images == 4` and `Budget.max_frames_per_turn == 3`;
  - `MAX_CONTINUATION == 14_000` and `COMPACT_KEEP_LAST == 2`;
  - `services/vllm.sh` carries `--max-model-len 16384` and `"image": 4`;
  - `LIVE_DEFAULT_VISUAL_TOKENS == 1120`;
  - `policy.expected_soft_tokens(1280, 800, 1120) == 1092`.

  Its failure message says "re-measure the worst-case window (T-0132 P4)". It contains no characters-per-token estimate (B10; `test_prompt_budget.py` guards against that guess).
- **Captions and prefills.** Caption and anticipatory-prefill bodies carry the live budget too (T-0131 A2). Their extra encoder load at the desk, with three sequences in flight, is unmeasured: see H-T132-3.

### Group B — the pass-2 (crop) budget

**B1. Configuration.**
- `Profile.reground_visual_tokens: Literal[280, 560, 1120] | None = None`, with the same junk refusal as `visual_tokens`.
- It is refused at load when set with `tools != "live"`, or with `reground = false` explicitly. Otherwise it would be a silent no-op (`.claude/rules/conductor.md`).
- `astra session --reground-visual-tokens {280,560,1120}` overrides the profile.
- `cli` exits 2 if the resolved value is set while the resolved ReGround is off or the mode is not live. The message names why.
- Resolution: flag, else profile, else the resolved main budget (source `"default"`).

**B2. Wiring, with no protocol change.**
- `Session` gains `reground_llm: LlmBackend | None = None` and `reground_visual_tokens: int | None = None`. Both are given or neither is (`ValueError` otherwise), and both are refused without `reground`.
- `cli` passes the main client itself when the two budgets are equal. Otherwise it passes a second `VllmClient(endpoint, detokenizer=<same>, visual_tokens=<pass-2 budget>)`.
- `LlmBackend` (`contracts/protocols.py`), `VllmClient` and `tests/fakes/**` do not change.
- Closing the session closes a second client that `cli` built; no connection pool is leaked.

**B3. When the pass-2 budget applies.**
- Pass 2 goes through `reground_llm` only when the pass-2 prompt (after `replace_frame_image`) carries **exactly one** `ImagePart`, the crop.
- With two or more images it goes through `self.llm`, at the main budget, and is byte-identical to T-0131's pass 2.
- The reason, verified in v0.29.0: `max_soft_tokens` is one value per request, applied to every image, and it is part of every image's cache hash. A lower budget would therefore re-encode the older images (history images and earlier frames of the turn), which all precede the call's frame. Pass 2 would then see them at a lower resolution than pass 1 did (against R-a), and they would miss the prefix cache.
- With `reground_llm is None`, or both budgets equal, nothing changes.

**B4. Abort on the issuing client.** A pass-2 abort (B7 of T-0131) goes to the client that issued the request.

**B5. Logging.**
- The `tool.reground` record gains:
  - `budget`: the `max_soft_tokens` actually sent, or `null` when unset;
  - `images`: the pass-2 prompt's image count;
  - `first_ms` and `tool_ms`: ms on the session clock from the request start to pass 2's first commit and to its `tool` commit; `null` when absent.
- All T-0131 keys are kept.
- The turn line's `reground` dict and the span set do not change.

**B6. Negative.**
- With the pass-2 budget equal to the main budget, live request bodies, records (apart from B5's added keys) and turn lines match the group A state.
- No pass-2 commit reaches the machine, the speech gate, TTS, history, the HUD or an `Episode`. All of T-0131 B1–B10 still holds.

### Group C — the follow-up GPU A/B (report-only, plus a decision rule awaiting H-T132-1)

**C1. Harness:** `scripts/gpu/t0132_crop_budget_ab.py`.
- **Imported from T-0131's harness, never edited:**

- **Its own:** a turn runner, because it builds the second client.
- `ARMS = ((1120, False, None), (1120, True, 1120), (1120, True, 280))`, pinned by an arm-table sha.
- `REPEATS = 20` per task: 3 arms × 5 tasks × 20 = 300 turns, shuffled jointly with seed 0, concurrency 1.
- Every arm sets `visual_tokens`, `reground` and `reground_visual_tokens` explicitly, so the defaults never decide an arm.
- Every client, the second one included, is wrapped in a `LoopMeter`, so every body is scanned and timed.
- It keeps every T-0131 refusal, exiting 2 before any socket opens.

**C2. Probes.**
- P1–P3 as in T-0131. Any failure exits 3 with a void or inconclusive report.
- **P4, the worst-case window.** It runs after the arms, so it cannot void them.
  - The prompt: 4 distinct 1280×800 frames at 1120, plus the live system message (tools and guidance), plus a continuation of `MAX_CONTINUATION` characters built with `loop.render_call` and `loop.render_response` from realistic live payloads.
  - Its `/tokenize` count is reported against 16 384 − 256.
  - One generate on it must return 200, and the engine must stay healthy.
  - The result is report-only (`window: ok | over | failed`).
- **Run budget.** T-0131 ran 150 turns in about 18 min. The estimate here is 35–45 min. `RUN_BUDGET_S = 85 * 60` and the locked script's `timeout 90m` give at least 1.9× headroom.

**C3. Metrics per arm (report-only).**
- **Success:** per task out of 20, total out of 100, with a Wilson 95 % interval.
- **Hit rate** (with the pass-1 counterfactual in the on arms), click error p50/p95/mean, and box `read_errors`.
- **False claims.**
- **Steps:** steps per turn and statuses, plus scrolls per S4 and per S5 turn. S4 is expected to stay at 0; that is out of scope here and reported only.
- **Step latency:** first-commit and done p50/p95, reground requests excluded.
- **ReGround:**
  - request count and outcome counts;
  - pass-2 latency p50/p95, split into first commit, tool commit (`tool_ms`) and done (LoopMeter `done_ms`), plus the session `ms`;
  - extra execute time per coordinate step;
  - the distribution of pass-2 `images` and `budget`.
- **Prefix cache:** hit and query tokens per step, and separately for pass-2 requests.
- **Turn wall time**, and the minimum free VRAM.
- **Acceptance** and all T-0131 safety counts, each expected 0.
- **Configuration evidence:**
  - each trial's non-reground bodies all carry 1120;
  - each pass-2 body carries the arm's crop budget when `images == 1`, and 1120 otherwise;
  - `guidance_sent` holds for every trial.
- **Difference intervals** (Newcombe 95 %) for success: on-arms against off, and 280-crop against 1120-crop.

**C4. Decision rule (proposed numbers; H-T132-1).**
- **Eligibility.** An arm is eligible only if acceptance is 100 %, every safety count is 0, and the engine stayed up.
- **(b) Crop budget,** decided first, between the two on arms. The crop default becomes 280 only if all of these hold:
  - success(280-crop) ≥ success(1120-crop) − 5 (of 100);
  - hit(280-crop) ≥ hit(1120-crop) − 0.03;
  - pass-2 done p50 at 280 ≤ 0.8 × its p50 at 1120, and p95 at 280 ≤ p95 at 1120.

  Otherwise the crop stays at the main budget.
- **(a) ReGround at 1120.** ReGround stays on only if both hold for the on arm (b) chose, against 1120/off:
  - success(on) − success(off) ≥ 5 (of 100);
  - hit(on) ≥ hit(off) − 0.02.

  Otherwise the label is "reground off".
- **Labels:** `reground on, crop 280` · `reground on, crop 1120` · `reground off` · `inconclusive` (P1 failed) · `void` (P2 or P3 failed) · `incomplete` (stopped early).
- **Power, stated in the report.** At n = 100 and p ≈ 0.7, one arm's success has a standard error of about 4.6 pp, and a difference about 6.5 pp. The 5-point margins therefore resolve true gaps of about 13 pp with roughly 0.9 probability, and pass a zero gap about 22 % of the time.
- **No absolute latency bar.** The T-0131 D5 bar was not derived from a measured baseline, and its own control failed it. Latency is reported, and enters only (b)'s relative "faster" clause.
- Adopting a default from the label is a later one-line task.

## Implementation notes

- **Verified in v0.29.0** (planner, read-only):
  - one `max_soft_tokens` per request, applied to every image;
  - the cache hash of each image includes the kwargs;
  - an encoder cache of max(4096, largest item).

  A 4-image prompt at 1120 (4 × 1094 = 4376 tokens) exceeds the encoder cache, and is expected to be scheduled across steps. This is unmeasured: P4 measures it.
- **Where the call's frame sits.** In every live step prompt, the call's frame is the last image. `swap_newest_image` and `show_current_image` replace or place the newest frame, and history images precede it. So with a lower pass-2 budget, the cache misses only from the crop onward when there is one image, but from the first image onward when there are several. That is why B3 applies the pass-2 budget only to single-image prompts.
- **Image counts.** In the A/B every turn is a fresh Session, so pass 2 almost always carries one image. Desk sessions from turn 2 on usually carry two or more, and fall back to the main budget under B3. The report states the `images` distribution.
- **Possible follow-up, not in this task.** If `tool_ms` is much smaller than `done`, pass 2 could abort its stream at the tool commit.
- **Keep the default in `cli`.** Rigs and the GPU harnesses build Sessions with explicit values.
- **No characters-per-token arithmetic anywhere** (B10).
- **Tool use.** The implementer never edits `tests/`. No heredocs to get around a blocked Write. Never export `GIT_DIR` for test runs (T-0131 incident).
