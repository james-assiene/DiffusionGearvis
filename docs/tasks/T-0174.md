## Goal

At step ≥ 2 the model often doubts it has the post-action screenshot and quotes `LIVE_TOOL_GUIDANCE`'s "After an action, the next screenshot shows the screen as it is now" as its reason to wait. W1-1 (`logs/t0160-web-smoke-abcf17d/turns/W1-1/sessions/20261027-160346-469597.jsonl`, seq 200): "I don't have the new screenshot yet … Wait, the prompt says "After an action, the next screenshot shows…"". W2-0 step 2 (`…/W2-0/sessions/20261027-160402-470048.jsonl`, request seq 53) shows the same doubt. In `logs/t0136-outcome-ab-97c444a/thoughts.jsonl` the pre-registered regex (C2) matches 29/100 trials in arm A and 24/100 in arm B.

The task: (1) a v2 guidance whose screenshot sentence points backwards and is true at every step, selectable per session (`--live-guidance v1|v2`, default v1); (2) an executor fact saying whether the action loaded a new page (in W1-1, Go was clicked on an empty field, `web.html` refused it, nothing loaded); (3) a GPU A/B of v1 vs v2 with pre-registered ADOPT / REJECT / INCONCLUSIVE; (4) the default flips to v2 only on ADOPT.

### Group B: the navigated fact

**B1-1. Executor key (B1, may start now).** For an `executed` `click_at`, `type_at` or `press_key` in live mode, `resolved["navigated"]` is a `bool`: `True` iff the active page after settle shows a different main-frame document than at dispatch (a cross-document main-frame commit observed after dispatch began and before settle returned, back/forward restores, a switch to a newly opened page — H-T174-1). Fragment/hash changes, `pushState`/`replaceState`, subframe navigations and popups closed by the `MAX_PAGES` cap that never became active give `False`. The key is absent when the driver lacks the capability (a narrow capability protocol beside `_FocusDriver`), for every other tool, for `refused` and `failed` outcomes, and in dry-run. `hosts` is not read to decide it.

**B1-1b. Commit signal and pending navigations (amendment 2026-10-27, B1 reviews A and B).** `domcontentloaded` is not a commit signal: `settle()` regularly returns before DCL (early-flushed HTML, a blocking script, TTFB over the 2 s settle bound), so a DCL counter reads False after a real commit and moves the fact to the next action. The driver counts a cross-document main-frame commit as: a main-frame navigation request (`page.on("request")`, `request.is_navigation_request()`, `request.frame == page.main_frame`) followed by a main-frame `framenavigated` whose URL equals that request's URL; a DOMContentLoaded counts only for a document not already counted by that match (so a late DCL of an earlier commit never counts again in a later action). Same-document navigations issue no request and never count. At the read: a commit since the mark (or a different active page) gives `True`; a main-frame navigation request still pending gives `None` (the key is absent — never a guessed "no new page loaded"); otherwise `False`. No page script, no CDP. A non-active page's commit never counts; a closed page's state is dropped.

**B1-2. Negative.** Every other `resolved` key, its value and every `action` string unchanged. A driver without the capability yields `resolved` byte-identical to BASE. No new page event in `_report`. No JS runs in the page to decide navigation (protocol- or driver-level only); nothing the page can observe changes.

**B2-1. Page key (B2, after Merge T-0173 and Merge T-0174-a/b1).** `Session(page_fact: bool = False)`; when `True` and an executed live action's `resolved` carries a `bool` `navigated`, the settled step response gains `page: "new page loaded"` or `page: "no new page loaded"`; no key when `navigated` is absent. cli passes `page_fact=True` iff the resolved live guidance is `v2` (H-T174-2).
