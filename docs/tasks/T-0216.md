## Goal

`contracts/codec.py` `decode` promises it never raises (its module docstring; docs/03 §3 "Protocol codecs": "malformed ones produce an `error` event, never a crash"; docs/02 §5 "codec (total decode)"). It calls `json.loads` and catches only `JSONDecodeError`:
- an int literal longer than Python's 4300-digit int-from-string limit raises `ValueError`;
- deep nesting such as `'['*100000`, well under the 8 MB size limit, raises `RecursionError`.

Both escape `decode` and `HudConnection.receive`. After this task both become `Malformed` like other bad JSON: the connection answers `astra.error(code="malformed")`, and the `wire.in` row records only the codec's fixed reason, never the payload. Nothing else changes.

## Acceptance criteria

1. `decode` on a message with an int literal of 4301 or more digits, as `str` or `bytes`, at top level or nested in an `astra.*` or a Realtime message, returns `Malformed` and does not raise.
2. `decode` on JSON nested deeper than the parser's recursion limit (for example 100 000 `[`, or `{"type":"x","a":[[[…]]]}`) returns `Malformed` and does not raise.
3. The `Malformed.error` of both cases is a fixed text containing none of the input's characters beyond a digit count or position. The `wire.in` row's `msg` (`hud_server._malformed_row`) holds no digit run or bracket run from the input.
4. `HudConnection.receive` on either input counts one `malformed`, queues one `astra.error` `malformed`, and keeps the connection open.
5. Negative: an int literal of exactly 4300 digits still decodes as today. Every existing `Malformed` reason text, the size-check order (before `json.loads`), and encode are unchanged. No global `sys.set_int_max_str_digits` or recursion-limit change.
