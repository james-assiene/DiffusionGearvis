## Goal

Twice at the desk the model built a complete, correctly fenced, root-bearing A2UI surface — 15 components, `createSurface` + `updateComponents` — **entirely inside its reasoning channel**, then wrote, still inside the thought, `I will say "I have created a flight booking interface for you."`, and said exactly that aloud. There is no `ui.gate` record anywhere in the 21:52 log: thinking is discarded by design, so the client never saw a `ui` segment. The human heard a fluent, confident claim and looked at an empty panel — the worst failure shape this product has, because the assistant sounds correct while being wrong about the present.

**The model is not at fault, and that is the heart of this task.** The system prefix it was given is 2249 characters, quoted in full in the log's `llm.request` record. It contains exactly one placement rule that mentions the thinking channel, and that rule is about *speech*: "Never leave the **answer** inside the thinking channel." The surface is never mentioned in a placement rule at all. Meanwhile the sentence the model followed most literally is the one that is about the fence: "Open and close the fence in the same message: begin `<a2ui>` only when you can finish the whole surface and `</a2ui>` in that one reply." It did exactly that — one fence, opened and closed. Nothing in the prefix says the fence must come **after the thought closes**, and from the model's position the fence *is* the shown channel, so writing it while reasoning satisfies every word it was given. The model's own thought even names the framing back at us: *"I should use the `a2ui` tool to create this UI"* — it read "you have a second channel" as a tool callable from anywhere, including from inside a plan.

After this task the block says, adjacent to the fence and in the same breath as the rule that governs it, **where** the surface goes: in the reply the user receives, after the thinking has ended — and it stops describing the surface as a second channel the model may write to whenever, describing it instead as part of the one reply, alongside the spoken words. The example payload, the advertised component list and the fence constants do not change; only the prose around them does. The block's structure, its size and the fact that the cached prefix changes exactly once are pinned by the fast suite. Whether the model *complies* is a measured eval with an A/B arm against today's block, an n and a regime — and it has never run.

### The one sentence the block has never said, and it is literally true

The pinned chat template (`chat_template.jinja`, `services/versions.lock` `chat_template_revision = sha256:36e3a42e…`) carries a macro named `strip_thinking`, and the template applies it to **every** assistant message it re-renders: it deletes the span `<|channel>…<channel|>` outright. A surface written inside the thought is therefore erased from the conversation **by the model's own template**, before our client's policy, before the session log, before anything we wrote. "What you write while you are thinking is thrown away; only what you write in your reply exists" is not a threat, not a house rule and not an approximation — it is a description of the machinery, and it is the sentence this block has never contained. It is available as English, and it is the strongest elicitation this task has.

### This fix is necessary and not sufficient — read this before believing the panel will appear

In the 21:52 log the thought-fence **itself straddled a canvas boundary**: `<a2ui>` opened in `canvas_idx 1` and `</a2ui>` closed in `canvas_idx 2` (`llm.commit` records at seq 238 and 251, both `segment: "thought"`). So even if this task's wording had worked perfectly that night and the model had written the identical fence in its reply, `split_segments` — called with `in_ui=False` per chunk under the rule T-0052 is withdrawing — would have classified the 750-character tail as `answer` and Pocket TTS would have read JSON aloud. That is exactly the failure T-0052 exists for. **T-0055 moves the surface into the channel the client reads; T-0052 makes the client able to read it when it spans more than one canvas. Neither produces a panel alone.** This is why the orchestrator sequenced T-0052 groups A and B ahead of this task, and why a reviewer of T-0055 must not read "the model wrote the fence in its reply" as "the human saw an interface".

## Implementation notes

**F1 — how the thinking channel is actually delimited, which the task was asked to establish.** From the pinned chat template (`chat_template.jinja`, `services/versions.lock` `sha256:36e3a42e…`): `enable_thinking` injects `<|think|>\n` as the first token of the **system** turn — it is an *enable* flag, not an opening tag. The thought itself is the span `<|channel>thought\n … <channel|>`; when thinking is **off** the template writes that span already closed and empty after `<|turn>model\n`. So the concrete boundary the model crosses when it stops thinking is the token `<channel|>`, and everything after it, inside the same model turn, is the reply. Two further facts are usable as *English* in the block. First, **the template's own `strip_thinking` macro deletes exactly `<|channel>…<channel|>` from assistant content whenever history is re-rendered** — a surface written inside the thought is erased by the model's own machinery, not merely by our client's policy; that is the Goal section's sentence and it is the strongest true thing this block can say. Second, our client classifies the whole reasoning delta as `thought` before any fence is looked for (`llm_client.split_segments`: `if reasoning_delta: pieces.append(("thought", …))`), which T-0052 criterion 14 keeps true.

**F2 — and why the block must *not* name that boundary literally. This is the trap F1 sets for you.** `<|think|>`, `<|channel>`, `<channel|>`, `<|turn>`, `<turn|>` are **added tokens with `special: true`** in the pinned tokenizer (ids 98, 100, 101, 105, 106 of 24 added tokens). Text in a chat message is encoded with added tokens matched, so pasting `<channel|>` into the block puts control token 101 **inside the cached system turn**: the `gemma4` reasoning parser sees a channel close that opens nothing, the prefix carries a control token in a text field, and — the subtler harm — the model is shown a control token in a position that invites it to echo it. `llm_client.THOUGHT_MARKERS` protects against an echoed `<|think|>` (M9 reclassifies the whole content as thought) but knows nothing about `<channel|>`. **Name the boundary behaviourally**, in the model's own terms ("once you have finished thinking", "in the reply the user receives"). Criterion 4 makes this a red row in the fast suite and criterion 12 checks it again at the token layer. If someone wants the literal token, criterion 12's `/tokenize` run is the cheap way to find out what it becomes — post a candidate string, read the ids — and that is *Ambiguity 2*, not a thing to try blind.

**F3 — framing beats prohibition, which is the human's explicit instruction: elicit, do not constrain.** Three observations from the two logs, all pointing the same way. (i) The model's thought says "I should use the `a2ui` tool" — "a second channel" reads as a callable thing, available from wherever it is standing. (ii) Its thought is a *design process*: "I will design a simple layout using the available components", then a bullet sketch, then "Let's structure the JSON for A2UI:" — drafting in the thought is the model working correctly; the failure is that the draft was the only copy. (iii) It then narrated the speech act it was about to perform. So the framing that fits what the model is already doing is: **the reply has two parts — what you say, and, when it helps, one surface — and the reply begins when the thinking ends.** Sketching in the thought is fine; the surface exists only if the fence is written in the reply. Whether to invite the sketch explicitly ("plan it while you think if you like, then write it once, in your reply") or to discourage it ("write it once, in your reply, not in your thinking") is a real fork: the first accommodates the observed behaviour and costs tokens twice; the second is shorter and risks the model treating the draft as the deliverable again. Pick one, say in the report which and why, and write the other into this file as the alternative arm for the next `/launch` run — criterion 13's numbers decide between them, not taste.

**F4 — ordering inside the system message, which the implementer cannot fully control.** The join is `system_prompt, CLOSE_THE_THOUGHT, SPOKEN_STYLE, UI_INSTRUCTIONS` and `prompt_builder.py` belongs to T-0053, so the block stays last. In today's block the fence and the whole example arrive on line 6, before any rule at all.

**F5 — the headroom is 221 code points.** 1 779 of 2 000 are used, and 470 of those are the frozen example. If the new prose does not fit, shrink prose, not the example, and not the component list. Do **not** raise `MAX_BLOCK_CODE_POINTS` — it is a bound the task chose, and moving it needs its own `docs/tasks/` entry (CLAUDE.md).

**F6 — two things in the 21:52 evidence that are *not* this task's, recorded so nobody fixes them here.** The thought-fence straddled canvases 1→2 (seq 238 → 251), which is T-0052 group A and which is why this fix is necessary and not sufficient — see the Goal section. Both are owed drift against `ui_instructions.py`, which this task now owns; neither is in scope, and adding property hints now would spend the 221 code points that criterion 1 needs.

**F7 — prefix-cache consequence, to be stated in the report and in the PROGRESS *Runs* line.** Changing the block changes the cached system prefix: one extra prefill of the whole prefix per **engine process** plus eviction of the old prefix's blocks — not one per session (T-0044 ruling A8 corrected the pessimistic version). ## Ambiguities (decide before `/implement`; each names who decides)

1. **Invite the sketch, or discourage it?** F3's fork: "plan it in your thinking, then write it once in your reply" versus "write it once, in your reply, not in your thinking". 2. **Name the boundary literally, or behaviourally?** This task rules **behaviourally** (F2: the boundary strings are special tokens and would be encoded as control tokens inside the cached prefix). 3. **Is n = 5 per case enough to tell two wordings apart?** No, and the task does not claim otherwise. n = 5 with an A/B arm can show a large effect (2-of-2 at the desk → ≤ 2-of-20) and cannot resolve a small one. 4. **Does the eval belong in `tests/eval/` at all, given it can never run unattended?** Precedent says yes (T-0044's four rows have been `pending` since the task merged and the pending warning is "a true statement, not a bookkeeping slip"). The cost is another module in the pending backlog. *Decider: the orchestrator; if the answer is no, it becomes a `scripts/demo/` rung and criteria 13–14 are reported by hand.*
5. **A safety net that is not a prompt.** The human has ruled that extraction is out and that is not re-litigated here. Recorded for them, not proposed: if the eval shows residual thought-fences after a wording iteration or two, the option that is *not* extraction is **prevention at decode time** — a length-bounded / channel-aware grammar on the thought channel, already on the roadmap as the constrained decoder's first production grammar (docs/01 D11, docs/07). It forbids the fence from being generated inside the thought rather than harvesting one that was. 6. **What to do about the leaf-property gap (T-0052 ruling A7) and the stale one-canvas sentence.** Both are owed drift against the block this task now owns, and both want code points this task does not have. *Decider: a successor task after T-0052 merges; named here so it is not silently absorbed.*
