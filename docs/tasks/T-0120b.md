## Goal

Today, a tool-loop continuation over `MAX_CONTINUATION` (14 000 chars) ends the turn with `over_budget`. On the GPU, S6 reached it at step 8 with 16 987 chars. After this task, the session first calls `loop.compact(turn.loop_steps, MAX_CONTINUATION)` and keeps the compacted steps as the turn's steps, so later step prompts extend the same bytes (prefix stability). It logs a `tool loop compacted` note and counts compactions on the turn line. Only a loop that still does not fit after compaction ends `over_budget`.

The stub an elided search result becomes now tells the model it can search again (human, 2026-10-18: "search again seems simpler"). The reason: in T-0115a's exploratory re-read, when the needed result had been elided the model said "I couldn't find it" 30/40 times and searched again only 9/40. It never invented the fact.

Loop-off sessions and loops that fit do not change.

## Acceptance criteria

1. **Wiring order.** In the step-request path (`_run_step`), `turn.loop_steps` is replaced by `list(loop.compact(turn.loop_steps, MAX_CONTINUATION))` before `step_prompt` is built and before the size check. The size check, the `over_budget` end, its note, its `LlmError(OVER_BUDGET_MESSAGE)` and its HUD publication (T-0114 criterion 11) are unchanged in form. They fire only when the compacted continuation is still over `MAX_CONTINUATION` (T-0120 criterion 6).
2. **The stub (re-scope of T-0120 criterion 4; H-T120b-0, H-T120b-1).**
   - A mapping with a `results` list (a search response) becomes `{"note": ELIDED_SEARCH_NOTE, "results": N}` with `ELIDED_SEARCH_NOTE = "earlier result omitted; search again if you need it"`. Hand-typed expected render: `<|tool_response>response:google_search{note:<|"|>earlier result omitted; search again if you need it<|"|>,results:5}<tool_response|>` (132 chars).
   - The `status` form and the bare form keep `ELIDED_NOTE = "earlier result omitted"`, with no invitation: calling an action again would repeat the action.
   - `_is_stub` recognises both notes, so neither is ever elided again (T-0120 criterion 5).
   - Stubs render through `render_response`. "A response whose stub is not shorter is never elided" is kept. The not-connected search response (146 chars) is still longer than its stub (132), and the test pins that.
3. **Prefix stability (T-0120 criterion 5, now at session level).** After a compaction at step k, the continuation sent for step k+1 starts with the continuation sent for step k, byte for byte, unless a further compaction occurs at step k+1; then every response elided at step k is still elided, with identical bytes.
4. **The note.** Each `compact` call that elides at least one step writes one `note` with exactly the keys `what: "tool loop compacted"`, `request_id` (the machine id, as in the over_budget note), `step` (the step about to be requested), `elided` (the sorted 0-based indices newly elided by this call), `chars_before` and `chars_after` (each equal to `loop.continuation_chars` of the steps before and after the call). No note when `compact` returns the steps unchanged. The note carries no tool-result or step text.
5. **The turn line.** Loop-on turn lines gain `tool_compactions`, an int: the number of `compact` calls in the turn that elided at least one step, including one that still ended `over_budget`. It appears on every loop-on line, 0 when nothing was compacted (H-T120b-3). Loop-off lines do not gain the key.
6. **The worst case (re-scope of T-0114 criterion 11 and its row).** With maximal steps (as in `_worst_case`), every sent continuation stays ≤ `MAX_CONTINUATION`, and the bounds on step text, argument and response hold on every sent request. The turn still ends `over_budget` at the first step whose compacted continuation does not fit. The planner's unverified arithmetic: requests 2–7 are sent, `LlmError` on `t1-gen-s8`, `tool_compactions` 3. The test-author derives the exact numbers from `loop_constants()` and the rendered lengths, not from this paragraph.
7. **Negative: loop-off is byte-identical.** On marker-free loop-off fixtures (a plain turn, a tool turn with the loop off, a turn with history), every session-log line, `llm.request` prompt, publication and history row is byte-identical to literal `791dc54` (or T-0121's merge commit, H-T120b-5), with volatile fields normalised as the tools-off golden does. `tests/unit/test_session_tools_off_golden.py` passes unedited.
8. **Negative: fitting loops are byte-identical.** For loop-on fixtures whose every continuation fits (an S1-like 3-step search, a 2-step action loop), every `llm.request` and every note is byte-identical to the base. The turn line is identical except for the added `tool_compactions: 0`. No `tool loop compacted` note is written.
9. **Negative: scope.** Over BASE..TIP (BASE = T-0121's merge commit, TIP = this branch's head, both literal pins) these are unchanged: `MAX_CONTINUATION`, `MAX_STEP_TEXT`, `MAX_ARG_TEXT`, `MAX_RESPONSE`, `COMPACT_KEEP_LAST` and the default target `budget * 2 // 3`; `turn_machine.py` and `contracts/**`; the outputs of `render_call`, `search_payload`, `action_payload`, `status_payload` and `step_prompt` (every T-0113 row passes unedited); `prompt_builder.py`. `loop.py`'s import rule (T-0120 criterion 7) holds. The fast suite stays under its budgets.

## Implementation notes

- Compare with `is` per element to tell whether `compact` acted (identity under budget, T-0120 criterion 1), so a fitting loop does no extra rendering beyond one `continuation_chars`. The size check may reuse `continuation_chars` of the compacted steps, which equals `len(prompt.messages[-1].text())`.
- `loop_steps` is read only by `_run_step`; keep appends going to the stored, compacted list.
- Compaction does not switch anything off, so it publishes nothing to the HUD (H-T120b-2).
- Compaction never touches step `text`; T-0122 (spliced thought text in step requests) is separate.
- No config knob and no new threshold constant: the trigger is `MAX_CONTINUATION`.
- The turn machine is not involved.

## Threshold

The trigger stays at `MAX_CONTINUATION` = 14 000 chars, target 9 333. At c398fdf: chars per token of continuation growth p50 3.625, p95 4.733 (n 224); step-1 prompt 1 652–2 312 tokens without history; largest step prompt 5 579 tokens; 13 904 chars of continuation came to 5 363 prompt tokens. At p50, 14 000 chars ≈ 3 862 tokens, so the largest step prompt that can be sent is about 6 174 tokens, about 8 160 below `max_prompt_tokens` 14 336. The trigger is set by keeping compaction rare, not by the context window.
