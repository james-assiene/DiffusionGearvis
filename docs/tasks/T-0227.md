## Goal

Two values are fixed today:

- **Images per turn.** One spoken turn shows the model at most 3 screens: the onset screen plus screens that changed while the user spoke (T-0059). The cap is `prompt_builder.Budget.max_frames_per_turn = 3`, the authoritative one per `session._append_frame` (`session.py:4057-4072`). `TurnPolicy.max_frames_per_turn = 3` exists but only feeds the machine's de-duplication.
- **Capture interval.** The HUD sends at most one `astra.frame` per source per second (`hud/src/frames.js` `MAX_FPS = 1.0`, mirrored from `perception/policy.MAX_FPS`). The capture loop offers a frame every `CAPTURE_TICK_MS = 250` (`hud/src/main.js:20`).

After this task both are settings:

- They are catalog rows with their own explanation and costs.
- They can be changed from the Settings panel and apply at the next turn boundary (the T-0213 A2-apply path).
- They can be set at launch with `--max-frames-per-turn` / `--frame-interval-ms` or the profile keys of the same names.
- The README "Options at a glance" table is regenerated with them.

The interval applies only to the HUD's own capture (shared screen and camera). In live computer use the agent browser's screenshots come from `LiveBrowser.frame()`, one per step, not from the HUD stream, so they are unaffected (`BrowserFrameSource` holds the HUD's frames despite its name). With the defaults, every request body, the turn machine and every golden are byte-identical to today.

**What the numbers allow (computed, not measured):**

- At 1120 visual tokens, a screen costs about 1,094 prompt tokens (T-0131 P1). `expected_soft_tokens` gives 1064 soft tokens for the 1568x1176 screen bucket and 1092 for 1280x800.
- The prompt budget is 14,336 tokens: `Budget.max_prompt_tokens` = 16,384 `--max-model-len` minus 2,048 of answer headroom. By context alone, floor(14336 / 1094) = 13 images would fit with no text at all.
- The binding limit is the engine's `--limit-mm-per-prompt '{"image": 4}'` (`services/vllm.sh:188`, = `Budget.max_images`); a request over it is an HTTP 400. So N = 4.
- At 4, the turn's own screens take every image slot:
  - no history image remains; each one degrades to its caption line (T-0059 ruling B3);
  - a fourth screen arriving mid-turn evicts the newest history image (ruling A5, one prefix miss).
- 4 screens is about 4,376 tokens (31 % of the prompt budget); 3 is about 3,282 (23 %).
- Going past 4 means changing the launcher's image limit (encoder cache, VRAM). That is its own task with a bench, never this one.

**B-3. The offer tick never quantises the interval.**

- The tick is 250 ms when the interval is 1000 ms (as today).

  - every gap is ≥ the interval (the throttle is strict);
  - the median gap is ≤ 1.3 × the interval.
- The landmine: at a 250 ms tick and a 250 ms interval, a tick that fires a fraction early drops alternate frames and halves the rate.

## Implementation notes

- **The session cap counts; the machine's does not.**
  - `TurnPolicy.max_frames_per_turn` stays 3. The machine emits a `SnapshotFrame` for every phash its tuple does not hold, and `session._append_frame` de-duplicates by phash and caps on the builder's `Budget`.
  - So a builder cap of 4 above the machine's 3 still fills four slots, and a cap of 1 below it gives "the last snapshot wins".
  - Do not touch `turn_machine.py`, `TurnPolicy` construction in `cli` (`cli.py:2705`), or the docs/02 §4 Hypothesis properties.
- **Where the budget changes.**
  - `Session.__init__` builds `PromptBuilder(...)` with the default `Budget`. Keep that, so a session built without `cli` is BASE.
  - A new `Budget` comes only from `init_settings` (called once by `cli`, `cli.py:2769`) and the A2-apply builder rebuild (`session.py:~9184`, which today passes `old.budget`).
  - Build before mutating (T-0213 R-19 f).
- **The 4-image ceiling.**
  - `Budget.max_images = 4` is the engine's hard limit, and `_image_turns` gives history `max_images - current_images` slots.
  - `toolcall/loop.show_current_image` can add an image when the turn's frame rode on a history image. At cap 4 with history images present, prove the count stays ≤ 4 (A-6).
  - The overview checks (`session.py:4103-4147`) already compare against `max_images`. Keep them as the refusal; never evict.
- **Prefix cache.**
  - Neither setting touches the system message.
  - A cap change can change which history images stay as pixels on the next turn, so its first request may miss from the first history image on. Hence `next_turn_cold`.
  - The interval changes nothing in the prompt, hence `next_turn`.
  - The thinking flag is never touched (CLAUDE.md: toggling it misses the whole prefix).
- **Why the interval is applied at the boundary, though it has no prompt effect:** there is one apply path (T-0213 A2a-3), and a turn's screens never change cadence mid-utterance. The page follows `item.value` (the value in force), not `pending`.
- **Why 250 ms is the minimum.**
  - **Ring:** 60 s / 250 ms = 240 frames, inside `MAX_RING_FRAMES = 600` with 2.5x margin. Below 100 ms the frame cap would cut the 60 s window that `get_frame(at=onset)` and `clip()` rely on.
  - **Pipeline:** the page encodes a 1568x1176 JPEG at q85 and sends it single-flight. A slow encode drops frames rather than queueing, so a faster interval is safe but can be lossy on a loaded box.
  - **Prefill:** scene changes re-warm the prefill at most once per 1000 ms (`prefill.reissue_min_interval_ms`). A faster cadence adds `SceneChanged` events but not prefills.
  - **Scene hysteresis:** `SCENE_MEMORY_KEYS = 8` covers 2 s at 250 ms, which still suppresses A/B flicker.
  - **Logging:** each frame is one `wire.in` record (the image as a digest) when logging is on.
- **Why 10,000 ms is the maximum:** it stays well under the 60 s ring, which is pruned on read, so a sharing page never yields `None`. Above it, the onset screen can be older than the user's question by more than a sentence.
- **The capture tick (B-3).** Today the 250 ms offer tick equals the minimum interval, so jitter would halve the rate. The implementer designs the fix: derive the tick from the interval (keeping 250 ms at the default), or give the gate a tolerance that cannot break the "never faster than the interval" bound. `throttle.test.mjs` must pass unedited.
- **Presets, not a free integer.** The panel has only checkbox and select controls, and `CatalogEntry` mirrors `SettingEntry` field for field. A free range would need min/max fields (a wire change) and a number input (a page change). Presets keep the wire and `hud/src/settings/**` byte-identical, and keep the drift guard's "values equal a config constant" rule. The values are in milliseconds, as James asked.
- **Persistence.** There is no `ui_settings.toml`: T-0213 D (save as my defaults, Q6) was never built. A panel change lasts for the process (T-0213 Q7); a relaunch returns to the flags and profile. Do not build D here.
- `.claude/rules/perception-memory.md`: frames stay downscaled to the same buckets, so B2 need not re-run. "1 fps" in that rule and in docs/02 §2.1 becomes "1 fps by default (`frame_interval_ms`)"; docs/02 changes in the A delta. The rules file is not owned; the orchestrator updates it after merge.
- **No consumer.** With no HUD connected the interval has no consumer. It is still accepted, because it applies to the next page that connects (the hello state carries it); the help says so. This does not break the rule in `.claude/rules/conductor.md` that a setting which would silently do nothing is refused.
