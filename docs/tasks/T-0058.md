## Goal

On 2026-09-16 at 22:17 the engine was started on a box where Kyutai STT had moved onto the GPU, and it died **21 s after launch** — before weight load, before KV reservation, before graph capture — with `ValueError: Free memory on device cuda:0 (27.23/31.33 GiB) on startup is less than desired GPU memory utilization (0.92, 28.83 GiB)`, raised by `vllm/v1/worker/utils.py:526 request_memory` from `gpu_worker.py:440 init_device`. `services/vllm.sh` has never passed `--gpu-memory-utilization`, so vLLM's **0.92 default** applies and the engine demands 0.92 × 31.33 = 28.83 GiB of the device be *free at startup*. The recogniser holds 3 180 MiB, which leaves 27.23 GiB: 1.60 GiB short, every time. **Why nobody hit this before, and the sentence that makes it a release blocker rather than a curiosity:** the engine that ran for 23 hours was started when the GPU was **empty** (30.43 GiB free, comfortably over 28.83) and the recogniser moved onto the card afterwards — it has been running on conditions that can no longer be reproduced, and **every restart in this configuration fails**. The workaround is only the boot order (engine first, recogniser second — precisely the accidental order that produced the working setup), and `astra up` does not know it: on a box where the recogniser is already healthy, `up` skips it (T-0049 D1) and starts the engine into 27.23 GiB. After this task the engine passes a derived `--gpu-memory-utilization` that reflects what it actually uses; its launcher refuses in about a second, with the arithmetic and the remedy, rather than letting the container burn 21 s; `astra doctor` carries a row that predicts the refusal from a read-only box description — including the case that matters most, *a healthy engine that could not be restarted where it stands*; and one `/launch` boot proves the flag did not touch the KV pool and yields, for the first time, free device memory sampled **during denoising**.

**Established from vLLM's source, and it corrects the *Runs* line's wording:** with `--kv-cache-memory-bytes` set, `GPUWorker.determine_available_memory` returns the specified bytes immediately and logs *"reserved N GiB memory for KV Cache as specified by kv_cache_memory_bytes config and skipped memory profiling. **This does not respect the gpu_memory_utilization config**"*. On our path `requested_memory` therefore gates **only** the startup free-memory check: it sizes no arena, caps no allocation, and never reaches `available_kv_cache_memory_bytes`. Consequences, stated rather than glossed: the flag **cannot** shrink the KV pool, **cannot** change prefix-cache headroom, and **gives the sampler neither more nor less room** — so ruling A13's open question ("the sampler transient is ten assumed copies of a 0.25 GiB tensor, and nobody has measured it") is left exactly as open as it was, and group C is the first chance to answer it. The one thing lowering the figure does cost is *guard strength*: the startup check is the only thing standing between a hopeless configuration and a 21 s failure, so a value below the engine's own measured footprint stops protecting anything. That is why the recommended value is not the *Runs* line's "~0.85 with margin" (see criterion 1 and ambiguity 1).

**This is not a one-sentence diff and the protocol is not skipped:** it changes the engine's launcher, adds a refusal that can stop a start, and produces a number that goes into `PROGRESS.md` under *Runs*.

## The arithmetic, once, with its provenance

Every figure below is read from `logs/vram-coldboot-73a85dd.before.txt`, `logs/vram-coldboot-73a85dd.csv` (390 samples at 200 ms) and `logs/vllm-coldboot-73a85dd.log`, 2026-09-16 22:17, commit 73a85dd, clean tree.

| quantity | MiB | GiB | source |
|---|---|---|---|
| device total, `nvidia-smi` | 32 607 | 31.84 | `before.txt` |
| device total, vLLM's own denominator (`mem_get_info`) | ≈ 32 082 | **31.33** | the ValueError |
| free before launch, `nvidia-smi` | 28 391 | 27.73 | `before.txt` |
| free at the engine's check (`init_snapshot.free_memory`) | 27 882 | **27.23** | ValueError + csv minimum |
| the engine's own pre-check footprint (CUDA context, torch init) | **≈ 509** | 0.50 | 28 391 − 27 882, same run |
| recogniser (`moshi-server`) | 3 180 | 3.11 | `--query-compute-apps` |
| Chrome GPU process | 50 | 0.05 | idem (a live confound) |
| demanded at the 0.92 default | 29 522 | 28.83 | 0.92 × 32 082 |
| **deficit** | 1 640 | **1.60** | 29 522 − 27 882 |
| engine's steady footprint at KV 4 GiB | ≈ 27 434 | 26.79 | 27 484 device-used minus Chrome, T-0014/T-0048 c11 |

Two denominators differ by 525 MiB and **the free readings agree exactly** (27 882 MiB both ways). The demand must be computed against vLLM's 32 082, not `nvidia-smi`'s 32 607: at 0.86 the difference is 452 MiB, enough to FAIL a box that would in fact boot.

Candidate values, against free-at-check 27 882 and footprint ≈ 27 434:

- **0.87** → demands 27 911 MiB. Still 29 MiB short. Excluded.
- **0.869** = 27 882/32 082 is the exact ceiling with the recogniser resident. No margin at all.
- **0.86** → demands 27 591 MiB: **291 MiB below** the observed free (so it boots) and **157 MiB above** the engine's own footprint (so the check still refuses a configuration the engine could not survive). **Recommended.**
- **0.85** → demands 27 270 MiB: 612 MiB of apparent slack, but **164 MiB below what the engine actually uses**, so the check would pass boots that then die later, deeper and more confusingly. The *Runs* line's "~0.85 with margin" is wrong in the direction that matters: the margin it buys is margin on the *check*, not on the *physics*, and the physics is unchanged either way.

Physical fit at 0.86, for the record: 27 882 free against ≈ 26 925 MiB still to allocate (27 434 − 509 already taken) leaves ≈ 957 MiB spare, consistent with the warm engine's measured 1.9 GiB free with the recogniser resident (32 607 − 27 434 − 3 180 = 1 993).

## Acceptance criteria

### Group A — the flag and the launcher's own refusal (`services/vllm.sh`)

1. **The startup gate is passed explicitly, with the derived value and its arithmetic.** `services/vllm.sh` passes `--gpu-memory-utilization 0.86` (or the value ruling on ambiguity 1 selects) and carries a comment block giving: the failure it fixes (date, log path, the ValueError verbatim), the ceiling 27 882/32 082 = 0.869, the engine's own footprint as a fraction (≈ 0.855), and the sentence that a value *below* the footprint stops being a guard. *Checkable:* a unit row parses the flag out of the script, asserts `0.855 < value <= 0.869` against bounds **written out in the test** from the table above, and asserts the comment names the log file. Satisfies the *Runs* consequence (i) of 2026-09-16.
2. **The pool is untouched and so is everything else.** `--kv-cache-memory-bytes 4294967296` is byte-identical (ruling A13: the shrink's premise is gone), and so are `--max-model-len 16384`, `--max-num-seqs 3`, `--max-num-batched-tokens 4096`, `--kv-cache-dtype bfloat16`, `--enable-prefix-caching`, `--attention-backend TRITON_ATTN`, `--diffusion-config`, `--override-generation-config`, `--limit-mm-per-prompt`, the `--hf-overrides` architecture line and the `$GEN_FLAGS`/`$PLUGIN_FLAGS` composition. **Negative, and load-bearing** (`.claude/rules/gpu-services.md`, T-0015): dropping any of the four explicit flags makes plugin-on diverge silently from plugin-off. The whole diff to the argv is one flag.
3. **The launcher refuses before `docker run`, with the arithmetic.** Before the `exec`, the script reads free device memory (`nvidia-smi --query-gpu=memory.free`), computes `required = util × VLLM_TOTAL_MIB` and `predicted_free_at_check = free − ENGINE_INIT_OVERHEAD_MIB`, and when the prediction is short it exits non-zero having printed: free, required, the deficit, the processes holding device memory (`--query-compute-apps=process_name,used_memory`), and the remedy — *stop the recogniser, boot the engine, start the recogniser second; `ASTRA_STT_CPU=1` is the documented fallback*. It costs ~1 s against the container's 21 s. *Negative:* it never stops, kills or signals anything; it only refuses to start. (Same shape as T-0048 criterion 12 for `services/stt.sh`; that file is not touched here.)
4. **The guard fails open, never closed.** A missing, erroring, timing-out or unparseable `nvidia-smi` prints one warning line and **proceeds**: the engine's own check is authoritative and costs 21 s, while a launcher that refuses on an unreadable status query bricks the box. *Adversarial rows required:* nvidia-smi absent; exit 1; empty stdout; `N/A`; a value with unexpected units. *Negative:* the guard has **no `ASTRA_DRY_RUN` branch** — a dry run that skips the guard cannot test it; the dry-run rows supply a fake `nvidia-smi` instead.
5. **Nothing runs docker to decide.** Under `ASTRA_DRY_RUN=1` with a refusing fake `nvidia-smi` on PATH, a fake `docker` placed first on PATH is **never invoked** (sentinel file absent) and the exit status is non-zero; with a permissive fake the argv is printed exactly as criterion 2 requires. Keeps `astra up`'s classification as a *routine service start* unchanged (`.claude/rules/gpu-services.md`).

### Group B — the doctor row (`local_astra/preflight.py`)

6. **`vram.engine_start` reproduces the 2026-09-16 refusal from a box description alone.** A new row, pure in `evaluate` as every row is (T-0033 criterion 1), fed the recorded facts — free 28 391 MiB, the three compute-apps rows, the script's util — returns **FAIL** and its detail states: free now, the engine's own init overhead subtracted, the predicted free at the engine's check, the demand with its denominator named, the deficit in MiB and GiB, and which processes hold the memory. The stated deficit agrees with the engine's own message to within 50 MiB (1.60 GiB). Severity per T-0033: engine **not** healthy and short ⇒ **FAIL** (the first live run cannot succeed).
7. **The row that would have predicted the failure a day early: a healthy engine that cannot be restarted where it stands.** When the engine *is* healthy and free is below the demand, the row is **WARN**, says plainly that the engine is running but could not be restarted in place, and gives the boot order as the fix. A running box is not broken, so it is not a FAIL; a human about to `astra up --restart vllm` is about to lose the engine for nothing, so it is not silence either. *Negative:* the existing `vram.free` row's name, verdicts and wording are unchanged, and `VRAM_FLOOR_MIB` stays `3 * 1024`.
8. **The denominator and the overhead are named, not guessed.** The row prints the denominator it used and where it came from (vLLM's `mem_get_info` total, 31.33 GiB, recorded from the 2026-09-16 ValueError; `nvidia-smi` says 31.84 and the two disagree by 525 MiB), and subtracts a documented `ENGINE_INIT_OVERHEAD_MIB ≈ 512` with its provenance (28 391 → 27 882 across that boot). **Two adversarial rows, each pinning a false verdict:** using `nvidia-smi`'s total over-demands 452 MiB at 0.86 and FAILs a box that boots; forgetting the init overhead under-predicts by ~509 MiB and PASSes a box that dies — which is the failure that makes the row worthless. ## The boot-order decision: `astra up` is not changed, and here is why

The brief offered two ways to record the boot-order fact "where `astra up` can act on it". **Decision: no change to `astra up`, and no criterion about its ordering**, for three reasons. (1) **It already does it.** `cli.py:104` puts `services/vllm.sh` first in the plan, and after T-0049 group B each start waits for health before the next begins (T-0049 ruling B19: the recogniser starts only after the engine answers, about 68 s in). A criterion asserting engine-before-recogniser would pin behaviour that exists and would be green the day it is written — the worst kind of coverage. (2) **The failing case is not an ordering bug.** It is the *partial* box: the recogniser is already healthy, `up` correctly SKIPs it (T-0049 D1), and the engine is then started into 27.23 GiB. No ordering rule inside `up` fixes that; only the flag does, and only the launcher's refusal explains it when it still cannot. (3) **Ownership.** `cli.py` and `supervisor.py` are T-0049's, whose group B is freshly merged and group C is an unrun `/launch`; taking them for a behaviour that already exists would be a conflict bought for nothing.

So the fact is recorded in the three places this task owns or triggers: the comment block in `services/vllm.sh` (criterion 1), the launcher's refusal text (criterion 3) and the doctor row's fix line (criteria 6–7) — and, for the next agent who reads a rule rather than a script, in `.claude/rules/gpu-services.md` (criterion 10). The refusal composes with T-0049 by design: a non-zero launcher exit inside the settle window is exactly what T-0049 criterion 4 observes, so `astra up` will print a FAILED row quoting the refusal instead of a 21 s mystery. That composition is worth one row in group A's tests (below) and needs no code in T-0049's files.
